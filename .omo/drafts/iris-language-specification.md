## Findings (cited - path:lines)

- The review is explicitly a discussion baseline rather than a specification and separates facts, recommendations, and unresolved decisions (`Document/Iris Revival Design Review.md:9`).
- The intended identity is a fully object-oriented dynamic message language, not a Rust/Kotlin/TypeScript surface imitation (`Document/Iris Revival Design Review.md:224`).
- The current unresolved list is incomplete: repository examples additionally expose literal forms, identifier sigils, operator precedence, qualified-name resolution, destructuring, collection iteration, and call/block interaction (`Iris Library Test/test script/expression/`; `Iris Library Test/test script/statement/`).
- The syntax highlighter contains legacy keywords not established by the review or behavior corpus, including `alias`, `retry`, `redo`, `goto`, `const`, `global`, and `static` (`Document/IrisLangHighLight(for NP++).xml`).
- Missing grammar sources mean historical generated parser code cannot safely serve as the normative grammar (`Document/Iris Revival Design Review.md:208`).

## Decisions (with rationale)

- **D-000 — Specification output directory: frozen.** All formal Iris v1 specification, grammar, core-library/ABI boundary, migration, and conformance documents will live under `spec/iris-v1/`. Existing historical artifacts in `Document/` remain archaeology inputs and are not moved or rewritten. Owner decision: 2026-07-24.
- **D-001 — Compatibility identity: frozen.** Revived Iris is a modern successor to legacy Iris, not a source-compatible restoration and not an unrelated new language. Preserve its defining language identity while allowing syntax and problematic semantics to be redesigned. Every intentional incompatibility must be documented in a migration/divergence ledger. Owner decision: 2026-07-24.
- **D-002 — Core language identity: frozen.** The revived language must preserve all of these constraints: every value is an object; operators are dynamically dispatched messages/methods; method dispatch remains runtime-dynamic; composition uses single inheritance plus modules and explicit interfaces/protocols; lexical closures and trailing blocks remain core; classes and methods have runtime identity and support constrained dynamic mutation; any object may be raised as an exception; and the language remains designed for host embedding and native extensions. Exact syntax and mutation/ABI boundaries remain separate decisions. Owner decision: 2026-07-24.
- **D-003 — Integer model: frozen.** `Integer` is semantically arbitrary precision. Implementations may represent common values as immediate/fixed-width SmallInt and promote losslessly to BigInt, but this representation split is not observable as different Iris types or dispatch behavior. Integer arithmetic therefore has no fixed-width overflow or wrapping semantics; resource exhaustion is a separate runtime failure. Native boundaries must perform explicit checked conversions when targeting fixed-width host integers. Owner decision: 2026-07-24.
- **D-004 — Float width model: frozen in principle.** Iris exposes multiple floating-point widths as observably distinct language types rather than specifying one universal `Float` representation. The initial width set, literal defaults, conversions, mixed-width arithmetic, equality, NaN behavior, and any shared `Float` supertype remain separate decisions. Owner decision: 2026-07-24.
- **D-005 — Initial float types: frozen.** The first language specification exposes exactly `Float32` and `Float64`, each with the corresponding IEEE-754 binary interchange semantics and observable through annotations, reflection, and dispatch. `Float16` and `Float128` are not built-in first-version types. Literal defaults, suffixes, conversions, promotion, and mixed arithmetic remain separate decisions. Owner decision: 2026-07-24.
- **D-006 — Unsuffixed float literals: frozen.** A floating-point literal without an explicit width suffix, including exponent notation, has type `Float64`. This decision does not imply an implicit narrowing conversion when the surrounding context expects `Float32`; contextual conversion remains a separate decision. Owner decision: 2026-07-24.
- **D-007 — Explicit float literal suffixes: frozen.** `f32` and `f64` suffixes select `Float32` and `Float64` respectively, including exponent-form literals (for example `1.0f32` and `1e10f64`). Suffix case sensitivity follows the future global case-sensitivity decision. A suffix establishes literal type only and does not imply any implicit numeric conversion. Owner decision: 2026-07-24.
- **D-008 — Operator dispatch and optimization freedom: frozen.** `a OP b` has the same observable semantics as sending selector `OP` to the runtime class of the evaluated left operand with the evaluated right operand as its argument; this equivalence does not require a physical generic method lookup or call. Evaluation and dispatch order is fixed: evaluate the left operand, evaluate the right operand, then resolve and invoke the operator method visible at that point. Arithmetic has no language-wide implicit conversion or promotion table: the selected receiver method declares whether it accepts the other operand, how it interprets or converts it, and its result type. Heterogeneous arithmetic need not be symmetric or commutative. Implementations may use primitives, representation-specialized fast paths, inline caches, unboxing, specialized machine code, or eliminated/hoisted guards when behavior remains observationally equivalent. Such optimized code must guard or depend on every relevant receiver class, operand representation, resolved method identity/version, lookup hierarchy version, and dynamic dispatch hook; changing any dependency must invalidate the optimized code or force fallback/deoptimization before a later affected send executes. Hidden `SmallInt`/`BigInt` representations remain the visible `Integer` class and cannot alter user-visible dispatch. Static checking uses the selected receiver method contract when provable; unsupported dynamic sends fail through the normal Iris message/type error mechanism. Owner decision revised and confirmed: 2026-07-24.
- **D-009 — Built-in heterogeneous numeric methods: frozen in principle.** The built-in `Integer`, `Float32`, and `Float64` classes may accept operands from the other built-in numeric classes in their operator methods. Each receiver class defines its own conversion, precision, exceptional-value, and result-type contract; accepting heterogeneous operands does not introduce a global promotion rule or symmetry requirement. Exact directional contracts remain separate decisions. Owner decision: 2026-07-24.
- **D-010 — `Integer OP FloatN` arithmetic: frozen.** For built-in arithmetic methods where the receiver is `Integer` and the argument is `Float32` or `Float64`, convert the receiver to the argument's floating-point width using the corresponding IEEE-754 rounding rules, perform the operation at that width, and return that same floating-point type. Loss of integer precision during conversion is permitted and observable. Conversion beyond the finite range is governed by the future exceptional-float-value decision. This is the contract of the built-in `Integer` operator method, not a language-wide promotion rule. Owner decision: 2026-07-24.
- **D-011 — `FloatN OP Integer` arithmetic: frozen.** For built-in arithmetic methods where the receiver is `Float32` or `Float64` and the argument is `Integer`, convert the argument to the receiver's floating-point width using the corresponding IEEE-754 rounding rules, perform the operation at that width, and return the receiver's floating-point type. Loss of integer precision is permitted and observable. Conversion beyond the finite range is governed by the future exceptional-float-value decision. This remains the independent contract of each built-in float operator method. Owner decision: 2026-07-24.
- **D-012 — Mixed float-width arithmetic: frozen.** Built-in arithmetic between `Float32` and `Float64` always converts the `Float32` operand to `Float64`, executes at `Float64` width, and returns `Float64`, independent of operand order. Same-width arithmetic returns the same width. The two receiver classes declare matching directional method contracts; this consistency does not create a language-wide promotion mechanism for user-defined numeric classes. A `Float64` operand is never implicitly narrowed merely because the receiver is `Float32`. Owner decision: 2026-07-24.
- **D-013 — Floating-point division by zero: frozen.** `Float32` and `Float64` division follows non-trapping IEEE-754 semantics. Division of a nonzero finite value by positive or negative zero produces the correspondingly signed infinity; zero divided by zero produces NaN. These outcomes do not raise an Iris division-by-zero exception. Signed zero, infinities, and NaNs are observable float values. Integer division by zero remains a separate decision. Owner decision: 2026-07-24.
- **D-014 — Floating-point overflow: frozen.** When finite `Float32` or `Float64` arithmetic exceeds the target format's maximum finite magnitude, the result is the correspondingly signed infinity under IEEE-754 rounding semantics. Converting an arbitrary-precision `Integer` beyond the target float format's finite range likewise produces signed infinity. Neither case raises `FloatOverflowError` or `NumericConversionError`, and values are not saturated to the maximum finite float. Owner decision: 2026-07-24.
- **D-015 — NaN equality: frozen.** Numeric equality for `Float32` and `Float64` follows IEEE-754 unordered NaN semantics: every comparison `nan == value` is `false`, and every `nan != value` is `true`, including comparisons with the same NaN value or another NaN. Object identity, hash-key equivalence, ordering, and NaN-payload inspection are separate protocols and must not be inferred from numeric `==`. Owner decision: 2026-07-24.
- **D-016 — Signed-zero equality: frozen.** Positive and negative floating-point zero are numerically equal under `==` and unequal under neither same-width nor mixed-width comparison. Mixed `Float32`/`Float64` comparison first follows the established widening rule. Their IEEE-754 bit patterns and signs remain observable through dedicated bit/sign APIs and operations such as reciprocal division; numeric equality is not bit equality or object identity. Owner decision: 2026-07-24.
- **D-017 — Cross-type numeric equality: frozen.** Built-in `Integer`, `Float32`, and `Float64` values compare by exact mathematical value across type boundaries. Comparison must not first round an arbitrary-precision `Integer` into a float: a float equals an integer only when its finite numeric value is exactly that integer. Equality is symmetric even though arithmetic dispatch is receiver-directed. Mixed float widths compare after exact interpretation/widening. NaN remains unequal to every value under D-015, and signed zeros remain equal under D-016. Hash-key equivalence remains a separate decision but must later respect the chosen equality contract where applicable. Owner decision: 2026-07-24.
- **D-018 — Ordered comparisons involving NaN: frozen.** If either operand is NaN, each ordinary numeric ordering operator `<`, `<=`, `>`, and `>=` returns `false` and does not raise an exception. These operators therefore do not define a total order over floats. Sorting, ordered containers, and deterministic serialization that require a total order must use a separately specified total-comparison protocol. NaN inequality remains governed by D-015. Owner decision: 2026-07-24.
- **D-019 — Integer division by zero: frozen.** Every built-in `Integer` division, integer-division, modulo, or remainder operation whose divisor is zero raises the ordinary catchable Iris exception `DivisionByZeroError`. `Integer` has no infinity or NaN values for this case, and the operations do not return `nil` or a result wrapper. The eventual exception-object fields and hierarchy remain part of the exception specification. Owner decision: 2026-07-24.
- **D-020 — `Integer / Integer` result: frozen.** Built-in `/` between two `Integer` values performs real-number division and always returns `Float64`, including exactly divisible operands. Both arbitrary-precision integers are interpreted under the established `Float64` conversion and IEEE-754 rules, so precision loss and signed infinity are permitted. Integer quotient division is a separate operation, and this decision does not introduce a built-in `Rational` type. Owner decision: 2026-07-24.
- **D-021 — Named infix method calls: frozen.** Every method with exactly one ordinary argument may be invoked either with member-call syntax `receiver.method(argument)` or named infix syntax `receiver method argument`; therefore `a.div(b)` and `a div b` are equivalent observable sends. Parsing never consults method tables, declarations, arity metadata, or runtime state: syntactically valid `expression identifier expression` is parsed as a named infix send, while method existence and the one-argument contract are checked statically when provable and otherwise by normal runtime dispatch. Defining, removing, or replacing a method cannot change how already-valid source text parses. Eligibility and parsing do not imply a physical generic call, under D-008. Precedence, associativity, newline boundaries, and interactions with trailing blocks remain separate grammar decisions. Owner decision: 2026-07-24.
- **D-022 — Named infix precedence and integer-division surface: frozen.** All named infix calls share one grammar-defined, left-associative precedence level. That level is lower than symbolic arithmetic and comparison operators, but higher than logical `&&`/`||` and assignment. Thus `a div b + c` parses as `a div (b + c)`, while `a div b div c` parses as `(a div b) div c`; parentheses are required for other grouping. Method declarations cannot customize precedence or associativity. Built-in integer quotient division is the one-argument `div` method and may be written as either `a.div(b)` or `a div b`. Its negative-number rounding and paired remainder semantics remain separate decisions. Owner decision: 2026-07-24.
- **D-023 — Integer quotient rounding: frozen.** `Integer.div` computes floor division for every nonzero integer divisor: the quotient is the mathematical floor of the exact rational value `a / b`, including negative operands. Consequently `-5 div 2 == -3`, `5 div -2 == -3`, and `-5 div -2 == 2`. Division by zero raises `DivisionByZeroError` under D-019. The paired remainder operation must later satisfy `a == (a div b) * b + remainder`; its surface name and complete sign contract remain separate decisions. Owner decision: 2026-07-24.
- **D-024 — Integer modulo surface: frozen.** The remainder operation paired with floor `Integer.div` is the one-argument built-in method `mod`, callable as either `a.mod(b)` or named infix `a mod b` under D-021/D-022. The first specification does not provide `%` as an alias and does not define a separate truncating `rem` operation. Division by zero raises `DivisionByZeroError`. Exact negative-operand result signs remain a separate decision. Owner decision: 2026-07-24.
- **D-025 — Integer modulo semantics: frozen.** For nonzero `b`, `a mod b` is defined exactly as `a - (a div b) * b`. It therefore satisfies `a == (a div b) * b + (a mod b)` and `abs(a mod b) < abs(b)`; every nonzero result has the same sign as divisor `b`. Thus `-5 mod 2 == 1`, `5 mod -2 == -1`, and `-5 mod -2 == -1`. Exact division produces zero. A zero divisor raises `DivisionByZeroError`. Owner decision: 2026-07-24.
- **D-026 — Integer exponent sign: frozen.** Built-in `Integer ** Integer` returns arbitrary-precision `Integer` for every nonnegative exponent. A negative integer exponent converts the computation to `Float64` reciprocal-power semantics and returns `Float64`, subject to the established IEEE-754 rounding, underflow, overflow, infinity, and NaN rules. Result type therefore depends on exponent sign. This decision does not introduce `Rational`. Zero-base edge cases remain separate decisions. Owner decision: 2026-07-24.
- **D-027 — Integer zero to zero power: frozen.** `Integer(0) ** Integer(0)` raises the ordinary catchable Iris exception `DomainError`; it does not return `Integer(1)`, NaN, or `nil`. Positive integer exponents of zero still return `Integer(0)`. Negative-exponent zero behavior and floating-point zero-power behavior remain separate decisions. Owner decision: 2026-07-24.
- **D-028 — Integer zero to a negative power: frozen.** For every negative `Integer` exponent, an `Integer(0)` base follows D-026's `Float64` reciprocal-power path and returns `Float64(+Infinity)` under non-trapping IEEE-754 division-by-zero semantics. It does not raise `DivisionByZeroError` or `DomainError`. Iris `Integer` has no signed zero, so no negative-infinity case exists for this operation. Owner decision: 2026-07-24.
- **D-029 — Floating zero to floating zero power: frozen.** For both `Float32` and `Float64`, every combination of positive or negative zero base and positive or negative floating-point zero exponent raises the ordinary catchable Iris exception `DomainError`. The operation does not return one, NaN, or infinity. This establishes a uniform cross-numeric rule that zero raised to zero is a domain error. Floating zero with a negative nonzero exponent remains a separate decision. Owner decision: 2026-07-24.
- **D-030 — Signed floating zero to a negative integer power: frozen.** For `Float32` and `Float64` zero bases with a negative nonzero `Integer` exponent, use IEEE/libm signed-zero parity behavior and retain the base width: positive zero produces positive infinity; negative zero with an odd-magnitude exponent produces negative infinity; negative zero with an even-magnitude exponent produces positive infinity. These operations do not raise an exception. Non-integer exponent cases remain separate decisions. Owner decision: 2026-07-24.
- **D-031 — Negative finite float to a non-integer float power: frozen.** When a negative finite `Float32` or `Float64` base is raised to a floating-point exponent that is not an integer-valued number and no real result exists, the operation returns NaN at the established result width and does not raise `DomainError`. Same-width operands retain that width; mixed float widths follow D-012 and return `Float64`. Ordinary floats never change their runtime result type to `Complex` based on operand values; any future complex exponentiation requires an explicit `Complex` receiver. The zero-to-zero exception in D-029 remains unchanged. Owner decision: 2026-07-24.
- **D-032 — Floating exponentiation result width: frozen.** Built-in float exponentiation follows the same width policy as other floating arithmetic: `Float32 ** Integer` and `Float32 ** Float32` return `Float32`; `Float64 ** Integer` and `Float64 ** Float64` return `Float64`; any operation mixing `Float32` and `Float64` widens the `Float32` operand and returns `Float64`, independent of operand order. This width rule does not override the separately frozen zero, infinity, NaN, or real-domain behavior. Owner decision: 2026-07-24.
- **D-033 — Exponentiation grammar: frozen.** Symbolic `**` is right-associative and binds more tightly than prefix unary negation. Therefore `2 ** 3 ** 2` parses as `2 ** (3 ** 2)`, while `-2 ** 2` parses as `-(2 ** 2)`; a negative base requires parentheses, as in `(-2) ** 2`. Unary negation is accepted directly in exponent position, so `2 ** -3` parses as `2 ** (-3)`. Owner decision: 2026-07-24.
- **D-034 — Integer bitwise operator surface: frozen.** The first revived specification provides symbolic `Integer` bitwise operators `&`, `|`, `^`, prefix `~`, `<<`, and `>>`. Legacy `<<<` and `>>>` rotate operators are intentionally removed because arbitrary-precision `Integer` has no intrinsic rotation width. A future fixed-width `BitVector` family may define rotation operations independently. This incompatibility must appear in the legacy divergence ledger. Negative-integer bit semantics and shift-count behavior remain separate decisions. Owner decision: 2026-07-24.
- **D-035 — Negative arbitrary-precision bit semantics: frozen.** Bitwise operations on `Integer` are defined through an abstract infinite sign-extended two's-complement model, independent of physical BigInt storage. Consequently `~x == -x - 1`, `~0 == -1`, and right shift is arithmetic: for example `-1 >> n == -1` for nonnegative `n`, and `-3 >> 1 == -2`. Implementations may use sign-magnitude or any other representation when results are observationally equivalent. Shift-count validation remains a separate decision. Owner decision: 2026-07-24.
- **D-036 — Negative shift counts reverse direction: frozen.** `Integer` shifts accept counts of any sign. A negative count reverses the shift direction and uses the exact arbitrary-precision absolute value of the count: `x << -n` is equivalent to `x >> n`, and `x >> -n` is equivalent to `x << n`, for every positive `n`. Zero remains an identity shift. Negative counts do not raise `RangeError`. All mathematical, sign-extension, and resource rules of the resulting opposite-direction operation apply unchanged; therefore a huge negative right-shift count may require a huge left-shift allocation and raise `ResourceError`. Owner decision revised and confirmed: 2026-07-24.
- **D-037 — Large arithmetic right shifts: frozen.** For every nonnegative shift count, `Integer >> count` has a mathematical result and does not raise merely because the count exceeds the operand's finite magnitude bits. Under infinite sign extension, every nonnegative value eventually stabilizes at `0`, while every negative value eventually stabilizes at `-1`. Implementations may compute these stable results without iterating or allocating in proportion to the count. Resource policies do not alter this result. Owner decision: 2026-07-24.
- **D-038 — Arbitrary-precision allocation failure: frozen.** An operation such as a huge left shift remains mathematically valid regardless of result size. If the runtime or a host-configured quota cannot allocate the result, it raises the ordinary catchable Iris exception `ResourceError`, with `MemoryLimitError` available as a more specific subtype. Resource exhaustion must not surface as `RangeError`, `nil`, a host panic, process abort, or undefined behavior. Host limits may determine whether an operation succeeds, but never alter the mathematical result of a successful operation. The same principle applies to other controlled allocations such as huge integer powers, strings, and containers. Owner decision: 2026-07-24.
- **D-039 — Integer literal radices: frozen.** Integer literals support binary `0b`, octal `0o`, unprefixed decimal, and hexadecimal `0x` forms. A leading zero alone never selects octal, so values such as `0755` are decimal subject to the future leading-zero lexical rule. Legacy or host-style implicit octal notation is intentionally unsupported. Prefix case sensitivity and digit separators remain separate lexical decisions. Owner decision: 2026-07-24.
- **D-040 — Numeric digit separators: frozen.** Integer and floating-point literals permit a single underscore only between two digits that are valid within the same lexical digit segment. Forms such as `1_000`, `0xFF_FF`, `1.234_567`, `1e1_000`, and `1.0e+1_024` are valid. Separators at a literal boundary, adjacent to a radix prefix, decimal point, exponent marker/sign, or float suffix, and consecutive separators are invalid; examples include `_1`, `1_`, `1__0`, `0x_FF`, `1_.0`, `1._0`, `1e_3`, `1e+_3`, and `1_f32`. Separators do not affect value. Owner decision: 2026-07-24.
- **D-041 — Decimal leading zeros: frozen.** Unprefixed decimal integer literals may contain any number of leading zeros and are always interpreted as decimal: `00755 == 755` and `00 == 0`. Leading zeros do not select octal and do not inherently produce a warning. Formatters may canonicalize them only under an explicit formatting policy that does not change program value. Owner decision: 2026-07-24.
- **D-042 — Numeric literal letter case: frozen.** Radix prefixes accept both cases (`0b`/`0B`, `0o`/`0O`, `0x`/`0X`); hexadecimal digits accept `a-f` and `A-F`; exponent markers accept `e` and `E`. Float-width suffixes have one canonical lexical spelling and are lowercase-only: `f32` and `f64`; forms such as `F32` and `F64` are lexical errors. This decision does not determine case sensitivity for ordinary identifiers or keywords. Owner decision: 2026-07-24.
- **D-043 — Invalid radix digits: frozen.** After a radix prefix begins a numeric literal, the lexer consumes the contiguous candidate literal segment as one token for validation. If it contains a digit or identifier character invalid for that radix, the whole token is an invalid numeric literal with a radix-specific diagnostic; it is not split at the longest valid prefix. Thus `0b102`, `0o89`, and `0xFG` each produce one primary bad-literal error rather than misleading secondary parse errors. Exact candidate-token boundaries and recovery after punctuation/whitespace remain lexer-spec details. Owner decision: 2026-07-24.
- **D-044 — Empty radix prefixes: frozen.** A radix prefix must be followed immediately by at least one digit valid for that radix. Empty forms (`0x`, `0b`, `0o`, in either accepted prefix case) and separator-first forms such as `0x_FF`, `0b_1010`, and `0o_755` are each one invalid numeric-literal token with a diagnostic that the radix prefix lacks an immediately valid digit. They are not split into decimal zero plus an identifier and are never interpreted as zero. Owner decision: 2026-07-24.
- **D-045 — Decimal-point digit omission: frozen.** Decimal floating literals may omit digits on either one side of the decimal point, so `.5` equals `0.5` and `1.` equals `1.0`; both are unsuffixed `Float64` under D-006. At least one side must contain decimal digits, so a lone `.` is punctuation/member-access syntax rather than a numeric literal. Existing separator constraints still prohibit forms such as `._5`, `1._0`, and `1_.`. Owner decision: 2026-07-24.
- **D-046 — Exponent-form decimal floats: frozen.** Decimal scientific notation forms a floating literal even without a decimal point. The exponent marker is `e` or `E`, followed by an optional single `+` or `-` and at least one decimal digit. Unsuffixed forms such as `1e3` and `2E-4` are `Float64`; lowercase `f32`/`f64` selects the explicit width. Digit separators remain valid only between exponent digits. The mantissa is decimal, and malformed/missing exponent digits are invalid-literal diagnostics. Owner decision: 2026-07-24.
- **D-047 — Hexadecimal floating literals: frozen.** The first specification supports C99-style hexadecimal floating literals with a `0x`/`0X` hexadecimal significand and a mandatory `p`/`P` binary-exponent marker whose exponent digits are decimal with an optional sign. Unsuffixed literals are `Float64`; lowercase `f32`/`f64` selects explicit width. Binary- and octal-prefixed literals never accept a radix point or floating exponent. Exact hexadecimal significand point requirements and separator boundaries remain separate lexical decisions. Owner decision: 2026-07-24.
- **D-048 — Hexadecimal float significands: frozen.** Hexadecimal floating significands may omit the radix point (`0x1p0`) or omit digits on either one side of a present point (`0x1.p0`, `0x.8p0`), but must contain at least one hexadecimal digit overall. A `p`/`P` exponent is always mandatory, so a form such as `0x1.` is invalid and `0x1e3` remains a hexadecimal `Integer`. Exponent digits are decimal with an optional single sign; unsuffixed and lowercase-width-suffixed typing follows D-047. Owner decision: 2026-07-24.
- **D-049 — Source float literal rounding: frozen.** Decimal and hexadecimal floating source literals are converted to their target `Float32` or `Float64` bit pattern with correctly rounded IEEE-754 `roundTiesToEven` semantics (nearest representable value, exact midpoint chooses an even significand). Compilation must not depend on the host process floating environment, current rounding mode, locale, or an inaccurately rounded host parser such as an unsuitable `strtod`. Equivalent source literals must produce the same bits across interpreter, JIT, target platform, and compiler host. Literal overflow and underflow outcomes remain separate decisions. Owner decision: 2026-07-24.
- **D-050 — Source float literal overflow and underflow: frozen.** Correctly rounded source literals use IEEE-754 gradual underflow: magnitude overflow produces signed infinity; sufficiently small values first round to subnormal values and eventually to signed zero. These remain valid literals. The compiler emits a default-enabled precision warning when a finite nonzero source literal rounds to infinity or to zero, but not merely for a representable finite/subnormal result. Tool policy may promote the warning to an error without changing the normative value or bit pattern. Owner decision: 2026-07-24.
- **D-051 — NaN and infinity source access: frozen.** Iris reserves no global `nan`/`inf` literal tokens or identifiers. Canonical special values are exposed through width-explicit type constants `Float32.nan`, `Float32.infinity`, `Float64.nan`, and `Float64.infinity`; negative infinity is produced with ordinary unary negation. NaN payload construction and exact bit patterns belong to future bit-construction APIs. Whether built-in type constants can be dynamically replaced remains a separate mutation decision. Owner decision: 2026-07-24.
- **D-052 — Special float values are class-object get-only properties: frozen in surface model.** `nan` and `infinity` are not constant slots; they are get-only properties on the `Float32` and `Float64` class objects. Expressions such as `Float32.nan` and `Float64.infinity` perform ordinary property-read/message semantics and return the canonical value of that width. No property writer exists, so source assignment such as `Float64.infinity = value` is invalid. Whether the built-in getter implementation itself may be replaced through dynamic method mutation remains a separate decision. Owner decision: 2026-07-24.
- **D-053 — Special-value getters remain dynamically mutable: frozen.** The built-in getter implementations for `Float32.nan`, `Float32.infinity`, `Float64.nan`, and `Float64.infinity` are not sealed. Users may replace or remove them through the ordinary dynamic class-object mutation mechanism and accept the resulting semantic consequences; after replacement, these expressions are no longer guaranteed to return canonical IEEE values. Optimizers may fold or specialize an access only while guarding/depending on the exact getter and relevant method/property-table versions, and mutation must invalidate or deoptimize dependent code under D-008. Whether users may add a setter to these initially get-only properties remains a separate decision. Owner decision: 2026-07-24.
- **D-054 — Dynamic setters on initially get-only properties: frozen.** Dynamic mutation may add a setter to an initially get-only built-in property, including the special-value properties on float class objects. Adding a setter is only the addition of an assignment-message implementation: it does not automatically allocate backing storage, replace the getter, or synchronize getter and setter behavior. User code defines and assumes responsibility for all state and side effects. Property/method shape versions must change and invalidate or deoptimize dependent inline caches and compiled code. Owner decision: 2026-07-24.
- **D-055 — Runtime float rounding mode: frozen.** Every primitive built-in `Float32` and `Float64` basic arithmetic step (`+`, `-`, `*`, `/`) is correctly rounded to its established result width using IEEE-754 `roundTiesToEven`. Iris exposes no mutable global or thread-local rounding mode that changes these operators, and results must not depend on the host floating environment. Directed or alternate rounding, if added, must use explicit APIs with separate contracts. Contraction and excess intermediate precision remain separate decisions. Owner decision: 2026-07-24.
- **D-056 — FMA contraction: frozen.** Source-level separate multiply and add operations round independently according to the expression tree. Implementations must not automatically contract `a * b + c` (or equivalent subtract forms) into a fused multiply-add when doing so could change observable bits, exceptions, or special-value behavior. Debug, release, interpreter, and JIT semantics are identical. Contraction is permitted only when proven bit-for-bit observationally equivalent. A future explicit `mul_add` method may expose true fused one-rounding semantics. Owner decision: 2026-07-24.
- **D-057 — Floating intermediate precision: frozen.** Every primitive `Float32` or `Float64` result is semantically rounded to its declared result width before it becomes an operand of a subsequent operation. Implementations may physically retain a wider register representation only when every later observation and operation is exactly equivalent to using the already-rounded target-width bits. Excess precision must never make results depend on storage, register lifetime, target architecture, interpreter/JIT choice, or optimization level. Owner decision: 2026-07-24.
- **D-058 — Explicit fused multiply-add: frozen.** The first standard numeric API provides the ordinary dynamically replaceable instance method `a.mul_add(b, c)`. It computes the exact product-plus-add expression and performs one final `roundTiesToEven` rounding at the established result width; the product is not rounded separately. It may therefore differ from `a * b + c`. Its two arguments make it ineligible for named infix syntax. Implementations may use hardware FMA or a correctly rounded software path, but optimized direct lowering must depend on the exact method/version and invalidate or deoptimize after dynamic replacement. Mixed-type width and exceptional-value contracts remain separate decisions. Owner decision: 2026-07-24.
- **D-059 — Built-in `mul_add` numeric types and width: frozen.** Built-in `Float32.mul_add` and `Float64.mul_add` accept `Integer`, `Float32`, and `Float64` for both arguments. The common result width is `Float64` if any of receiver, multiplier, or addend is `Float64`; otherwise it is the receiver's width. `Integer` operands participate as exact mathematical integers in the fused expression and are not first rounded to a float. The exact product-plus-add value is rounded once to the common result width under D-055. Unsupported user-defined numeric types follow ordinary method contracts/dispatch. Exceptional IEEE combinations remain separate decisions. Owner decision: 2026-07-24.
- **D-060 — `mul_add` infinity-times-zero: frozen.** If either fused multiplicand is positive or negative infinity and the other is numeric zero, built-in `mul_add` returns NaN at the D-059 common result width and does not raise an Iris exception. Numeric zero includes `Integer(0)` and either signed zero of either float width. The addend cannot make this invalid product valid. NaN bit/payload selection remains a separate decision. Owner decision: 2026-07-24.
- **D-061 — `mul_add` opposite-signed infinities: frozen.** If the exact fused product is positive infinity and the addend is negative infinity, or the product is negative infinity and the addend is positive infinity, built-in `mul_add` returns NaN at the D-059 common width and raises no Iris exception. If infinite product and infinite addend have the same sign, the result is that signed infinity unless another already-frozen NaN/invalid rule applies. NaN bit/payload selection remains separate. Owner decision: 2026-07-24.
- **D-062 — Ordinary NaN result bits: frozen.** When a built-in floating operation propagates an input NaN or creates a NaN through an invalid IEEE operation, Iris guarantees only a quiet NaN at the established result width. Ordinary arithmetic does not specify which input payload is propagated, the result payload, or the NaN sign bit, and those bits may differ across hardware while preserving numeric semantics. Code requiring exact NaN payload/sign construction or preservation must use explicit bit-level APIs rather than ordinary arithmetic. Owner decision: 2026-07-24.
- **D-063 — Exact float bit-conversion APIs: frozen.** The first standard numeric API provides `Float32#to_bits()` and `Float64#to_bits()` instance methods plus `Float32.from_bits(bits)` and `Float64.from_bits(bits)` class-object methods. These are exact IEEE interchange-format bit reinterpretations rather than numeric conversions and must round-trip every bit pattern, including signed zero, infinities, subnormals, quiet/signaling encodings on input, and NaN payload/sign bits. Ordinary arithmetic may still quiet or alter NaNs under D-062. The bit-container types and accepted numeric ranges remain separate decisions. Owner decision: 2026-07-24.
- **D-064 — Float bit-container values: frozen.** `Float32#to_bits()` returns a nonnegative `Integer` in `0..2^32-1`, and `Float64#to_bits()` returns one in `0..2^64-1`. The corresponding `from_bits` accepts exactly that width's range; negative and oversized values raise the ordinary catchable Iris `RangeError`. Inputs are never truncated, reduced modulo a power of two, rounded, or interpreted through host endianness. The first specification introduces no `UInt32`/`UInt64` solely for this API. Owner decision: 2026-07-24.
- **D-065 — Signaling-NaN bit preservation: frozen.** `from_bits(bits).to_bits() == bits` holds for every valid 32- or 64-bit interchange pattern, including signaling-NaN encodings. Construction, storage, argument passing, return, copying, and `to_bits` must not automatically quiet or canonicalize an sNaN. When such a value participates in ordinary floating arithmetic, D-062 applies and the result is only guaranteed to be a quiet NaN. Non-arithmetic classification and comparison handling remain separate decisions. Owner decision: 2026-07-24.
- **D-066 — Non-arithmetic float classification: frozen.** `is_nan`, `is_signaling_nan`, `is_infinite`, `is_finite`, `is_normal`, `is_subnormal`, `is_zero`, and `sign_bit` are pure bit-classification methods. They perform no ordinary floating arithmetic, never quiet an sNaN, preserve payload and sign, raise no floating exception, and leave `to_bits()` unchanged. A given interchange bit pattern must receive the same classification across interpreter, JIT, and platform. Owner decision: 2026-07-24.
- **D-067 — Signaling-NaN comparisons: frozen.** A signaling NaN participates in ordinary comparisons with the same non-trapping results as any NaN: `==` is `false`, `!=` is `true`, and `<`, `<=`, `>`, and `>=` are all `false`. Comparison raises no Iris floating exception and does not mutate either operand's stored bit pattern. Any internal quieting used by hardware is not observable through the original values. Owner decision: 2026-07-24.
- **D-068 — Floating values are immutable: frozen.** `Float32` and `Float64` instances are immutable value objects: their stored interchange bit pattern cannot change after creation. Arithmetic, conversions, and `from_bits` produce values rather than mutating an existing instance; `to_bits` and classification are pure reads. Dynamic mutation may replace class-level methods and property protocols but cannot alter the numeric bits held by an already-existing float value. This permits sharing, unboxing, constant reuse, and register representation while method/version guards remain required for dynamically replaceable behavior. Owner decision: 2026-07-24.
- **D-069 — Integer values are immutable: frozen.** Every `Integer` instance is an immutable value object independent of hidden SmallInt/BigInt representation. Arithmetic, exponentiation, bitwise operations, shifts, and representation promotion produce values and cannot mutate an existing integer's mathematical value. Dynamic class methods remain replaceable. Implementations may reuse or mutate uniquely owned internal BigInt storage only when no Iris observation can distinguish it from creating a new immutable value; internal representation must never change alias-visible behavior. Owner decision: 2026-07-24.
- **D-070 — Built-in numeric values have no observable object identity: frozen.** `Integer`, `Float32`, and `Float64` expose value and bit-value semantics but no stable object identity. A future identity protocol must reject these values rather than return implementation-dependent results. Implementations may use immediates, interning, constant merging, reboxing, shared BigInt storage, or different interpreter/JIT representations without Iris observation. Float bit distinctions such as signed zero and NaN payload remain observable through explicit bit APIs but are not object identity. Owner decision: 2026-07-24.
- **D-071 — Hash consistency for equal built-in numbers: frozen.** Every pair of built-in numeric values for which ordinary `==` is `true` must produce the same hash/key hash, including equality across `Integer`, `Float32`, and `Float64` and equality of positive and negative zero. Hashing therefore cannot simply include the concrete numeric type or raw float bits. Unequal values may collide. The exact stable/randomized hash algorithm and NaN key behavior remain separate decisions. Owner decision: 2026-07-24.
- **D-072 — NaN hash keys: frozen.** No quiet or signaling NaN of either float width is a valid Hash key. Hash construction, insertion, or key update with a NaN raises the ordinary catchable Iris `InvalidKeyError`; containers do not introduce a NaN-specific equality relation. Code that needs payload-sensitive mapping must explicitly use `to_bits()` (and encode width separately when needed) as a non-NaN key. Ordinary NaN equality remains unchanged. Owner decision: 2026-07-24.
- **D-073 — Stable public hash plus randomized table mixing: frozen.** Built-in numeric `hash` returns a specification-defined value stable across processes, platforms, interpreter/JIT modes, and conforming implementations/versions unless a future spec revision explicitly versions the algorithm. Hash containers do not use that public value directly as a bucket index: each runtime/container mixes it with a secret randomized seed to resist collision attacks. This internal mixing is not observable through public `hash` and must preserve D-071 equality consistency. Result width and algorithm remain separate decisions. Owner decision: 2026-07-24.
- **D-074 — Public hash result domain: frozen.** The public stable `hash` protocol returns an ordinary nonnegative `Integer` in the fixed range `0..2^64-1`. It introduces no `UInt64`, does not depend on pointer width or host `size_t`, and yields the same 64-bit result for the same specification value across process, platform, interpreter, and JIT. Hash containers may secretly remix and reduce this value for their own table geometry without exposing that internal result. Exact algorithm and evolution policy remain separate decisions. Owner decision: 2026-07-24.
- **D-075 — Public hash compatibility versioning: frozen.** The exact public `hash` mapping is part of a language-specification major-version contract: every conforming implementation of the same major version returns the same hash for every specification value, and minor/patch revisions cannot change it. A later major version may adopt a new algorithm only while exposing explicit versioned legacy entry points (for example `hash_v1`) sufficient to read, migrate, or reproduce persisted data. Unversioned `hash` follows the active major specification. Owner decision: 2026-07-24.
- **D-076 — First-version stable numeric hash structure: frozen.** The first public numeric hash maps every built-in numeric value to a unique canonical mathematical-value encoding before hashing, so values equal under D-017 share the same bytes regardless of `Integer`, `Float32`, or `Float64` representation and signed zeros share one encoding. Exact integral floats reuse the integer-value encoding; other finite floats use a canonical exact binary-rational encoding. NaN remains outside the Hash-key domain under D-072, while public hashing behavior for direct NaN method calls remains to be specified. The canonical bytes are hashed through a specification-fixed BLAKE3 derivation and reduced to the D-074 64-bit result. Dynamic user method replacement cannot alter this built-in normative mapping while the built-in hash method remains selected; replacing that method invokes the ordinary dynamic-mutation consequences. Domain separation, byte grammar, and 64-bit extraction remain separate decisions. Owner decision: 2026-07-24.
- **D-077 — BLAKE3 digest extraction for public numeric hash: frozen.** Compute the specification's domain-separated standard 32-byte BLAKE3 digest over the canonical numeric encoding, take digest bytes `0..8`, interpret those eight bytes as an unsigned little-endian integer independent of host byte order, and return that value as the nonnegative Iris `Integer` public hash. No XOR folding or alternate digest segment is used. The exact domain identifier and canonical encoding grammar remain separate decisions. Owner decision: 2026-07-24.
- **D-078 — Numeric-hash BLAKE3 domain separation: frozen.** First-version public numeric hashing uses BLAKE3 derive-key mode with the exact ASCII context string `Iris Language v1 stable numeric hash`. The canonical numeric encoding is the derive-key input material; the context is not manually concatenated to it. Context bytes, capitalization, spaces, and version marker are normative. Digest extraction then follows D-077. Owner decision: 2026-07-24.
- **D-079 — Top-level canonical numeric-hash tags: frozen.** Canonical numeric hash encodings begin with one byte: `0x00` for every finite mathematical value, `0x01` for positive infinity, and `0x02` for negative infinity. Concrete numeric type and float width are omitted, so equal `Integer`, `Float32`, and `Float64` values share bytes; integer zero and both signed float zeros share the finite-zero encoding, and infinities share encoding across widths. NaN has no Hash-key canonical encoding under D-072. Direct public `hash` behavior on NaN remains separate. Owner decision: 2026-07-24.
- **D-080 — Direct NaN public hash: frozen.** Calling the built-in public `hash` method on any quiet or signaling NaN of either width raises the ordinary catchable Iris `InvalidKeyError`, matching NaN's exclusion from Hash keys. It returns no canonical or payload-dependent numeric hash. Code that intentionally hashes a NaN bit pattern must explicitly call `to_bits().hash` and encode width separately when required. Owner decision: 2026-07-24.
- **D-081 — Canonical finite mathematical normal form: frozen.** Every nonzero finite built-in numeric value has the unique exact form `sign × odd_significand × 2^exponent`, where `sign` is positive or negative, `odd_significand` is a positive odd arbitrary-precision integer, and `exponent` is a signed arbitrary-precision integer. All factors of two are removed from the significand and added to the exponent. Zero has a separate encoding. This normal form is independent of concrete numeric type/width and therefore identical for equal `Integer`, `Float32`, and `Float64` values. Owner decision: 2026-07-24.
- **D-082 — Finite canonical sub-tags: frozen.** Immediately after top-level finite tag `0x00`, one byte identifies the normalized finite case: `0x00` for zero, `0x01` for positive nonzero, and `0x02` for negative nonzero. The zero encoding ends after these two bytes, so `Integer(0)` and both widths/signs of floating zero encode exactly as `[0x00, 0x00]`. Positive/negative encodings continue with the normalized odd significand and exponent. Owner decision: 2026-07-24.
- **D-083 — Canonical odd-significand bytes: frozen.** A normalized positive odd significand is encoded as `ULEB128(byte_length) || big_endian_magnitude`. `byte_length` uses the shortest canonical ULEB128 and is at least one. Magnitude uses the shortest unsigned big-endian byte sequence with no leading zero; decoded magnitude must be positive and odd. Zero, even magnitude, redundant ULEB128, and leading-zero magnitude are invalid canonical encodings. The length explicitly frames the following exponent field. Owner decision: 2026-07-24.
- **D-084 — Canonical exponent bytes: frozen.** The arbitrary-precision signed exponent is mapped to a nonnegative arbitrary-precision integer with ZigZag ordering (`0→0`, `-1→1`, `1→2`, `-2→3`, ...), then encoded as the shortest canonical ULEB128. Redundant ULEB128 encodings are invalid. No fixed-width two's-complement limit applies. The exact arbitrary-precision ZigZag formula remains to be stated separately to prevent host-width implementation errors. Owner decision: 2026-07-24.
- **D-085 — Arbitrary-precision ZigZag formula: frozen.** For exponent `e`, ZigZag encoding is the mathematical piecewise mapping `2*e` when `e >= 0`, and `-2*e - 1` when `e < 0`. Decoding nonnegative `u` yields `u/2` when `u` is even and `-(u+1)/2` when odd. This definition applies to arbitrary-precision `Integer`; host-width shift/XOR formulas may be used only when proven exactly equivalent without overflow or width dependence. The mapped value is then encoded by D-084's shortest ULEB128. Owner decision: 2026-07-24.
- **D-086 — Infinity canonical encoding length: frozen.** Positive infinity is encoded exactly as the single byte `[0x01]`, and negative infinity exactly as `[0x02]`; each encoding ends immediately after its top-level tag. No width, sign, payload, length, or trailing field is present. Consequently equal infinities of `Float32` and `Float64` hash identically. Any trailing byte would make the encoding noncanonical. Owner decision: 2026-07-24.
- **D-087 — Canonical numeric-hash bytes are not public API: frozen.** The canonical byte encoding used to define built-in numeric `hash` is specification-internal and is not exposed through an Iris method such as `canonical_numeric_bytes`. It is not a general serialization, persistence, or network format. Implementations and conformance tools may inspect it internally, and non-normative debugging tools may display it, but user programs observe only the final public hash. Float bit access remains provided by `to_bits`/`from_bits`. The internal encoding remains major-version constrained because it determines public hash results. Owner decision: 2026-07-24.
- **D-088 — Exact cross-type numeric ordering: frozen.** Ordinary ordered comparisons among finite `Integer`, `Float32`, and `Float64` values use exact mathematical values and remain symmetric across operand order. Implementations must not round arbitrary-precision integers to a float before comparison. Equal values follow D-017/D-016; infinities compare by their mathematical extended-real positions; any NaN operand follows D-018 and makes all ordering operators false. Dynamic method replaceability remains a separate decision from the built-in method contract. Owner decision: 2026-07-24.
- **D-089 — Numeric comparison methods are dynamically replaceable: frozen.** The built-in `Integer`, `Float32`, and `Float64` implementations of `==`, `!=`, `<`, `<=`, `>`, and `>=` are ordinary dynamically replaceable methods. The frozen numeric rules specify their unmodified standard behavior only. Comparison fast paths, inline caches, and JIT code must depend on the exact methods and relevant lookup versions and invalidate/fallback/deopt after mutation. Users may thereby violate symmetry, transitivity, ordering, or equality/hash consistency and assume responsibility for resulting Hash, set, and sorting behavior. Default derivation relationships among comparison operators remain a separate decision. Owner decision: 2026-07-24.
- **D-090 — Default comparison operators derive from `<=>`: frozen.** `==`, `!=`, `<`, `<=`, `>`, and `>=` each remain an ordinary one-argument method slot. Their unmodified default implementations derive Boolean results from the current visible `<=>` response, subject to D-097's identity-first rule for ordinary identity-bearing objects. For `<=> == -1/0/1`: `==` tests zero, `!=` tests nonzero, `<` tests `-1`, `<=` tests `-1 or 0`, `>` tests `1`, and `>=` tests `0 or 1`. A standard `<=>` result of `nil` means unordered and maps to `== false`, `!= true`, and all four ordered comparisons `false`. This is method-level default delegation, not parser desugaring, so normal dynamic dispatch and evaluation order apply. Owner decision revised and confirmed: 2026-07-24.
- **D-091 — Comparison slots can override `<=>` derivation independently: frozen.** Users may dynamically replace any of `==`, `!=`, `<`, `<=`, `>`, or `>=`; once a slot is replaced, calls to that operator execute the replacement and need not consult `<=>`. Replacing `<=>` affects every still-unmodified/default-delegating comparison slot, but does not override a user-replaced slot. Replacing one derived comparison slot does not alter `<=>` or the other slots. Inline caches and JIT specializations must depend on both the selected operator method and every delegated `<=>` method/version actually used; either mutation must invalidate, fallback, or deoptimize affected code. Users assume responsibility for any resulting equality, ordering, or hash inconsistency. Owner decision revised and confirmed: 2026-07-24.
- **D-092 — Numeric three-way comparison operator: frozen.** `<=>` is an independent, dynamically replaceable one-argument operator method. Its unmodified built-in numeric implementation performs exact cross-type mathematical comparison and returns `Integer(-1)`, `Integer(0)`, or `Integer(1)` for less/equal/greater, without first rounding arbitrary-precision `Integer`; if either operand is NaN it returns `nil` for unordered. The six standard comparison methods derive from the current visible `<=>` only while their own default implementations remain installed, under D-090/D-091. Owner decision revised and confirmed: 2026-07-24.
- **D-093 — Default comparison validates the `<=>` result contract: frozen.** A default-delegating `==`, `!=`, `<`, `<=`, `>`, or `>=` accepts from the invoked `<=>` only exact `Integer(-1)`, `Integer(0)`, `Integer(1)`, or `nil`. Any other integer, any other type, or a contract-violating dynamic value raises the ordinary catchable Iris `ComparisonContractError`; default comparison never coerces by sign or truthiness and never silently returns `false`. A user-replaced comparison slot may define its own behavior because it no longer uses the default delegation. Owner decision: 2026-07-24.
- **D-094 — Static return type of `<=>`: frozen.** In the first gradual type system, `<=>` is annotated to return `Integer?`. `nil` represents unordered; non-nil protocol-valid results are restricted dynamically to exact `-1`, `0`, or `1`. A non-`Integer`/non-`nil` result violates the ordinary return type contract and raises `TypeError`; another `Integer` satisfies the broad static type but causes a default-delegating comparison to raise `ComparisonContractError` under D-093. This decision introduces neither literal unions nor a nominal `Comparison` type. Owner decision: 2026-07-24.
- **D-095 — Built-in numeric `<=>` parameter and heterogeneous result: frozen.** The built-in numeric `<=>` methods accept `other: Object` and return `Integer?`. They perform the frozen exact comparison for `Integer`, `Float32`, and `Float64`; NaN or a nonnumeric object yields `nil` rather than `TypeError`. Therefore still-default-derived comparison methods produce `== false`, `!= true`, and all ordered comparisons `false` for numeric-vs-nonnumeric operands. User replacements may narrow or change their own contracts subject to the gradual type and override rules. Owner decision: 2026-07-24.
- **D-096 — Root `Object` comparison surface: frozen.** Root `Object` provides `<=>(other: Object) -> Integer?`, whose default implementation returns `nil` for every operand. Consequently every object accepts the comparison message, and subclasses obtain value ordering by overriding `<=>`; no global address/object-ID order is exposed. How root default `==` treats two references to the same ordinary object remains a separate identity/equality decision and may override the generic `<=>` derivation at `Object`. Owner decision: 2026-07-24.
- **D-097 — Identity-first default equality for ordinary objects: frozen.** For identity-bearing objects whose `==` slot still uses the root/default implementation, equality first tests whether both references denote the same object; if so it returns `true` without consulting `<=>`. Otherwise it invokes the current visible `<=>` and returns `true` only for exact `Integer(0)`, with `nil` mapping to `false` and invalid results following D-093. Default `!=` is complementary while its own default slot remains installed. A subclass/user may replace `==` or `!=` independently. Built-in numeric value objects have no observable identity under D-070 and use their numeric `<=>` value protocol only. Owner decision: 2026-07-24.
- **D-098 — Explicit identity primitive and `?` method names: frozen.** Iris provides the non-overloadable primitive `same?` for explicit object-identity comparison, usable as `a same? b` and `a.same?(b)`. It evaluates the left operand and then the right operand once each and returns `Bool`; it bypasses method lookup, `<=>`, `==`, proxies, and user replacement. Only identity-bearing operands are accepted; built-in numeric value objects raise the ordinary catchable `IdentityError`. To support this surface consistently, an ordinary method identifier may end in one trailing `?`, which is part of its name; detailed identifier grammar and whether other suffix punctuation is allowed remain separate decisions. Special singleton/value categories such as `nil`, booleans, and class objects remain to be classified for identity. Owner decision: 2026-07-24.
- **D-099 — Identity-bearing singleton and meta objects: frozen.** `nil`, `true`, and `false` are unique identity-bearing singleton objects. Class, Module, Contract, Method, Closure/Block, and other runtime definition/meta entities have stable observable identity and may participate in `same?`. `Integer`, `Float32`, and `Float64` remain identity-less immutable values and cause `IdentityError` when used as either operand. Future immutable value types must explicitly declare whether they are identity-less; identity is not inferred merely from implementation allocation. Owner decision revised and confirmed: 2026-07-24.
- **D-100 — Class reopen preserves identity: frozen.** Reopening an existing class mutates the same identity-bearing Class object rather than creating a replacement. References captured before and after reopening satisfy `same?`; existing instances remain instances of that Class object. Reopen updates relevant method/property/shape/contract versions and invalidates or deoptimizes dependent caches/code. Rebinding a name to a newly created Class object is a distinct operation with distinct identity and is not class reopen. Exact rebinding permissions remain separate. Owner decision: 2026-07-24.
- **D-101 — Method replacement creates a new Method object: frozen.** Replacing a method slot creates a new identity-bearing Method object and installs it in the slot, incrementing relevant versions. Previously captured Method objects retain their identity and old body and remain explicitly invocable through reflection; already-running old frames complete the old body. Future ordinary lookup uses the new Method. Removing a slot likewise does not invalidate an old Method object that remains referenced. Caches/JIT depending on the old slot or Method identity must invalidate, fallback, or deoptimize. The lookup context used by `super` inside a retained old Method remains a separate decision. Owner decision: 2026-07-24.
- **D-102 — Retained Method `super` uses the current MRO: frozen.** Every Method object retains the identity of its lexical owner Class/Module. When an old retained Method is explicitly invoked and executes `super`, lookup uses the receiver's current, versioned MRO at invocation time and continues after that lexical owner; the Method does not preserve a historical hierarchy/MRO snapshot. Hierarchy mutation therefore affects future reflective invocations of old bodies, while already-resolved active calls follow normal frame semantics. Behavior when the owner is absent from the receiver's current MRO remains separate. Owner decision: 2026-07-24.
- **D-103 — Missing lexical owner during retained-Method `super`: frozen.** When a reflectively invoked retained Method executes `super`, its lexical owner must be locatable in the receiver's current MRO. If absent, execution raises the ordinary catchable Iris `InvalidSuperError`; lookup does not restart from the receiver class, guess from a same-named method, use a historical MRO, follow the owner's unrelated hierarchy, or return `nil`. Diagnostics expose the Method identity/name, lexical owner, receiver class, current MRO/version, and `super` source location. Whether owner membership is required at Method invocation entry even when the body never executes `super` remains separate. Owner decision: 2026-07-24.
- **D-104 — Reflective Method receiver binding: frozen.** Explicit reflective invocation validates at entry that the receiver's current MRO contains the Method's lexical owner: a Class owner requires an instance whose MRO includes that Class; a Module owner requires the Module in the receiver MRO. Incompatibility immediately raises the ordinary catchable Iris `MethodBindingError`, even if a particular body path would not access state or execute `super`. This makes validity independent of body contents. D-103 still governs a later `super` if reentrant/concurrent hierarchy mutation removes the owner after entry validation. Bound-method capture and revalidation remain separate. Owner decision: 2026-07-24.
- **D-105 — BoundMethod capture and revalidation: frozen.** Reading/binding an instance method creates a BoundMethod that captures the invocation receiver and the exact Method object's identity resolved at binding time, but no historical MRO snapshot. For identity-bearing receivers it captures receiver identity; for identity-less immutable values it captures the value representation needed to invoke with that value as `self` without creating observable receiver identity. Later slot replacement does not redirect the BoundMethod. Each invocation revalidates that the receiver's current Class/MRO contains the Method's lexical owner, raising `MethodBindingError` if absent; `super` uses invocation-time current MRO under D-102. BoundMethod itself is identity-bearing. Owner decision revised and confirmed: 2026-07-24.
- **D-106 — Repeated BoundMethod reads create distinct identities: frozen.** Each evaluation that reads/binds `obj.method` creates a new identity-bearing BoundMethod, even when receiver and resolved Method are unchanged. Therefore `obj.method same? obj.method` is `false` because the two operands are separately evaluated bindings, while a saved BoundMethod reference is `same?` itself. Implementations may elide allocation only when identity observations remain exactly equivalent; no interning or weak-cache behavior is part of the language contract. Equality by captured contents remains separate. Owner decision: 2026-07-24.
- **D-107 — BoundMethod default equality is identity-only: frozen.** BoundMethod does not override root `<=>` or define value equality by captured receiver/Method. Its default `==` is `true` only for the same BoundMethod identity under D-097; separately created bindings compare unequal even when they capture the same receiver identity and Method identity. Reflection may expose those components for explicit comparison. Users may dynamically replace BoundMethod comparison/hash behavior and assume responsibility for contracts. Owner decision: 2026-07-24.
- **D-108 — Closure/Block identity and equality: frozen.** Each evaluation of a closure/block expression creates a new identity-bearing Closure/Block object with its own captured environment, even when code location and captured values are equal. Default equality is identity-only through root Object behavior: a saved closure equals/is `same?` itself, while separately evaluated closures compare unequal. Iris does not structurally compare executable code or captured environments. Implementations may elide allocation only when identity and capture observations remain equivalent. Owner decision: 2026-07-24.
- **D-109 — Method default equality is identity-only: frozen.** Method objects use root identity-first equality and do not define structural/source equality. Only the same Method identity compares equal by default; distinct Method objects remain unequal even when owner, name, signature, visibility, types, and body are equivalent. Method replacement therefore yields old/new Methods that are both `!=` and not `same?`. Reflection may compare individual metadata explicitly. Users may dynamically replace Method comparison/hash behavior and assume responsibility for contracts. Owner decision: 2026-07-24.
- **D-110 — Definition-object default equality is identity-only: frozen.** Class, Module, and Contract runtime objects compare equal by default only when they are the same identity. Equal qualified names, structure, source location, signatures, or members do not establish equality across distinct objects/load contexts/rebindings. Class reopen remains equal before/after because D-100 preserves the same identity. Users may dynamically replace comparison/hash behavior and assume responsibility for contracts. Owner decision revised and confirmed: 2026-07-24.
- **D-111 — Default identity-object hashing: frozen.** Ordinary instances and identity-bearing runtime/meta objects may be Hash keys and use a runtime-stable identity hash returned as `Integer` in `0..2^64-1`. The same object retains that hash throughout its lifetime and across movement by GC; distinct identities may collide. The value is not stable across processes, runtimes, or restarts and must not expose a raw memory address. Implementations may assign it lazily/randomly, and Hash tables may secretly remix it further. This identity-hash contract is distinct from D-073's cross-platform stable built-in numeric hash. Owner decision: 2026-07-24.
- **D-112 — Stable hashes for language singletons: frozen.** Although `nil`, `true`, and `false` are identity-bearing singleton objects for `same?`, their built-in public `hash` overrides generic identity hashing and is specification-stable across process, platform, runtime, and conforming implementation within a language major version. Each is a valid Hash key and returns a `0..2^64-1` Integer; table-internal randomized mixing still applies. Exact derivation/domain and values remain separate decisions. Owner decision: 2026-07-24.
- **D-113 — Stable singleton-hash derivation: frozen.** `nil`, `false`, and `true` hashes use BLAKE3 derive-key mode with the exact ASCII context `Iris Language v1 stable singleton hash` and one-byte inputs `[0x00]`, `[0x01]`, and `[0x02]` respectively. The standard 32-byte digest is reduced by D-077's first-eight-bytes little-endian rule. This domain is separate from numeric hashing. Formal conformance vectors must publish the resulting 64-bit values. Owner decision: 2026-07-24.
- **D-114 — Bool ordering: frozen.** Built-in `Bool#<=>(other: Object) -> Integer?` defines a total order within Bool: equal singleton values return `0`, `false <=> true` returns `-1`, and `true <=> false` returns `1`; a non-Bool operand returns `nil`. Therefore default derived relations make `false < true`. Bool remains distinct from numeric types: it is neither equal nor ordered with `Integer(0/1)` and retains its separate stable singleton hashes. Methods remain dynamically replaceable under the general comparison rules. Owner decision: 2026-07-24.
- **D-115 — Nil comparison: frozen.** Built-in `nil#<=>(other: Object) -> Integer?` returns `Integer(0)` only when `other` is the same `nil` singleton and returns `nil` for every non-nil value. Thus nil is equal/order-equivalent only to itself and is neither a global minimum nor maximum. Default derived equality/ordering follows D-090, while identity-first equality also recognizes the singleton. Methods remain dynamically replaceable. Owner decision: 2026-07-24.
- **D-116 — Hash uses the current dynamic equality/hash protocol: frozen.** Hash key insertion, lookup, update, and deletion use the key's current dynamically dispatched `hash` and `==` methods uniformly for value and identity-bearing objects; identity keys do not secretly switch to `same?`. Users replacing either method must preserve equal-implies-same-hash and related container invariants or accept broken lookup/duplicate behavior and rebuild affected containers. Hash does not freeze historical Method objects merely because a key was inserted. Automatic version detection/rehashing remains separate. Owner decision: 2026-07-24.
- **D-117 — Hash rehash is explicit after protocol mutation: frozen.** Existing Hash containers do not automatically detect `==`/`hash` method-version changes, track every key-class dependency, or rebuild during global mutation. The modifier/user must call `table.rehash()` or recreate the container. Rehash recomputes each current key's current dynamic hash/equality and reapplies runtime-secret table mixing. Until then, lookup behavior may be inconsistent and is the modifier's responsibility. Conflict resolution when formerly distinct keys become equal remains separate. Owner decision: 2026-07-24.
- **D-118 — Default `Hash#rehash` is atomic and conflict-intolerant: frozen.** `rehash()` builds and validates a temporary replacement using current key `hash`/`==`. If two previously distinct entries now belong to one equality class, it raises the ordinary catchable Iris `KeyConflictError`, publishes no partial result, and leaves the original Hash contents, buckets, key objects, values, and iteration state unchanged. It never silently chooses first/last or aggregates values. An explicit conflict-merge API remains separate. Owner decision: 2026-07-24.
- **D-119 — Block-driven atomic Hash rehash merge: frozen.** Supplying a trailing block to `rehash` resolves each equality-class collision. The block receives `(kept_key, kept_value, incoming_key, incoming_value)` and must return a two-element `(key, value)` result for the replacement candidate. It may preserve either key identity, create a new equivalent key, and merge values. The returned key must be equal to the collision class and obey the current hash/equality contract; shape/contract errors, new inconsistencies, or block exceptions abort atomically and leave the original Hash entirely unchanged. Successful rebuild is published once. Ordering of kept/incoming remains tied to the future Hash iteration/order decision. Owner decision: 2026-07-24.
- **D-120 — Hash iteration order is unspecified: frozen.** Hash exposes no insertion-order, stable-hash-order, sorted-order, or cross-run iteration guarantee. Entry traversal may vary with implementation, capacity, mutation history, runtime-secret bucket mixing, and process execution. Updating, deleting, reinserting, or rehashing may change observed order. Programs requiring deterministic order must sort/copy through an explicitly ordered structure. The collision order supplied to block-driven `rehash` remains a separate decision rather than inheriting a nonexistent public insertion order. Owner decision: 2026-07-24.
- **D-121 — Block-driven rehash merge order is unspecified: frozen.** `rehash` provides no deterministic order for collision resolution or for assigning `kept` versus `incoming`; it follows implementation/runtime traversal and rebuild order, which may vary with seed, buckets, capacity, mutation history, or version. Merge blocks that are not commutative/associative may therefore produce different valid outcomes, and the runtime does not attempt to prove those properties. Deterministic merging requires the user to extract entries, explicitly total-order/sort them, merge, and construct a new Hash. Owner decision: 2026-07-24.
- **D-122 — Hash traversal is fail-fast for structural mutation: frozen.** While an iterator/traversal is active, adding/removing a key, clearing, rehashing, or any mutation that changes entry structure increments a structural version; the iterator raises ordinary catchable `ConcurrentModificationError` on its next advance rather than continuing with duplicates/omissions. Updating the value associated with an already-existing key is non-structural and allowed. An entry not yet yielded reads its latest value at yield time. Mutation does not retroactively alter a value already delivered to user code; exact yielded-value capture remains to be confirmed separately. Owner decision: 2026-07-24.
- **D-123 — Yielded Hash entries capture ordinary arguments: frozen.** When traversal yields `(key, value)`, both are bound using ordinary argument semantics at that moment. Replacing the Hash slot's value afterward does not rewrite the already-bound local `value`; a later Hash lookup sees the replacement, and an entry not yet yielded observes its latest value when yielded. If the captured value is itself a mutable identity-bearing object, ordinary shared-reference mutations remain observable; that is distinct from replacing the slot. Owner decision: 2026-07-24.
- **D-124 — Hash iterator `remove_current`: frozen.** Hash iterators provide `remove_current()` to remove exactly the entry most recently yielded by that iterator without causing that same iterator to fail-fast. It may be called at most once after each successful yield and before the next advance; calls before the first yield, twice for one yield, or after completion raise an iterator-state error. The iterator updates its own expected structural version. Every other active iterator observes the structural change and raises `ConcurrentModificationError` on next advance. It cannot remove arbitrary or not-yet-yielded entries. How traversal blocks access the iterator remains separate. Owner decision: 2026-07-24.
- **D-125 — Hash block traversal variants: frozen.** `Hash#each` yields exactly `(key, value)`. `Hash#each_with_iterator` yields exactly `(key, value, iterator)`, and that explicit iterator is the only block-traversal surface for `remove_current()`. No implicit/current iterator context exists. Ordinary structural mutation through the Hash during either traversal still causes fail-fast on the next advance, except the owning iterator's valid `remove_current`. Nested traversals receive distinct iterator objects. Owner decision: 2026-07-24.
- **D-126 — Iterator state errors: frozen.** Invalid sequencing of iterator-specific stateful operations raises the ordinary catchable Iris `IteratorStateError`. For Hash `remove_current`, this includes invocation before a successful yield, more than once for one yielded entry, or after completion. This error is distinct from `ConcurrentModificationError`, which reports external structural-version mismatch, and from key/range errors. Return-false/nil is not used to hide invalid state. Owner decision: 2026-07-24.
- **D-127 — Iterator completion uses an `Iteration` result, not exceptions: frozen.** Explicit `iterator.next()` returns the built-in nominal `Iteration` result type. A produced element is represented by `Iteration.yield(value)`, which can carry any Iris value including `nil`; normal exhaustion returns the unique singleton `Iteration.done`. Repeated `next()` after exhaustion continues returning that same done singleton. `for`, `each`, and other traversal facilities inspect the result and terminate on `done`; they do not catch `StopIteration`, and normal completion never performs Iris exception unwinding. Actual iterator faults continue to raise ordinary exceptions, including `IteratorStateError` and `ConcurrentModificationError`. The semantic result object does not require heap allocation: interpreters/JITs may lower it to a tag plus value, registers, or direct control flow when observations remain equivalent. Owner decision revised and confirmed: 2026-07-24.
- **D-128 — `Iteration.yield` value semantics: frozen.** `Iteration.yield(value)` is an immutable built-in value object with no observable identity; applying `same?` raises `IdentityError`. Its default equality compares the variant and delegates payload comparison through the payload's current dynamic `==`: two yield results are equal only when their payloads compare equal. `Iteration.done` remains a unique identity-bearing singleton and is never equal to a yield result. Implementations may represent yield results without allocation. Hash behavior and public inspection APIs remain separate decisions. Owner decision: 2026-07-24.
- **D-129 — `Iteration` inspection properties: frozen.** `Iteration` exposes get-only properties `yield?`, `done?`, and `value`. For `Iteration.yield(payload)`, `yield?` is `true`, `done?` is `false`, and `value` returns the payload including legitimate `nil`. For singleton `Iteration.done`, `yield?` is `false`, `done?` is `true`, and reading `value` raises `IteratorStateError` rather than returning a sentinel. The internal tag is not otherwise exposed. Under maximum dynamicity these getters may later be replaced; built-in traversal may bypass them only with valid method/property-version guards. Owner decision: 2026-07-24.
- **D-130 — Conditional Hash support for `Iteration`: frozen.** `Iteration.done` is a valid stable-hash singleton key. `Iteration.yield(payload)` is a valid key exactly when invoking the payload's current public `hash` succeeds; its built-in hash derives from the yield variant plus that public payload hash and must give equal wrapper hashes whenever wrapper equality is true. If payload hashing raises `InvalidKeyError` or another contract failure (including NaN), wrapper hashing propagates the failure and insertion is rejected. It never falls back to wrapper identity because yield results are identity-less. Exact derivation/domain remains separate. Owner decision: 2026-07-24.
- **D-131 — Stable `Iteration` hash derivation: frozen.** Use BLAKE3 derive-key mode with exact ASCII context `Iris Language v1 stable iteration hash`. `Iteration.done` hashes input `[0x00]`; `Iteration.yield(payload)` hashes `[0x01] || payload_public_hash_u64_le`, where the payload's current public hash is encoded as exactly eight little-endian bytes. Digest reduction follows D-077. Payload hash failure propagates. The domain is independent from numeric and language-singleton domains and remains major-version stable. Owner decision: 2026-07-24.
- **D-132 — `Iteration` three-way comparison: frozen.** Built-in `Iteration#<=>(other: Object) -> Integer?` returns `0` for `done <=> done`; returns `nil` between `done` and any yield, between yield and done, or with a non-Iteration; and for `yield(a) <=> yield(b)` invokes the current dynamic `a <=> b` and returns that result. Default `==`, `!=`, and ordering then derive under D-090/D-093, so payload equality/order/unordered behavior is preserved. Users may dynamically replace Iteration comparison slots. Validation/error propagation for an invalid payload `<=>` result remains separate. Owner decision: 2026-07-24.
- **D-133 — `Iteration#<=>` validates delegated results immediately: frozen.** After `yield(a) <=> yield(b)` invokes the payload's current `<=>`, the Iteration method itself accepts only exact `Integer(-1)`, `Integer(0)`, `Integer(1)`, or `nil`. Any other integer or type immediately raises `ComparisonContractError` with wrapper, payload types, delegated Method, actual result/type, and expected protocol context. It does not normalize by sign, convert to `nil`, or defer validation to an outer comparison operator. Owner decision: 2026-07-24.
- **D-134 — Iterator identity and equality: frozen.** Explicit Iterator objects are mutable identity-bearing cursor/state-machine objects. Every iterator creation produces a new identity, including repeated `container.iterator()` calls. Default equality is identity-only; source container, current position, expected version, and current entry do not establish value equality. `same?` is valid, and two distinct iterators remain unequal even at equivalent positions. Iterator key eligibility remains separate. Owner decision: 2026-07-24.
- **D-135 — Iterator Hash-key eligibility: frozen.** Iterator objects may be Hash keys through the ordinary runtime-stable identity hash. Advancing, exhaustion, `remove_current`, or invalidation does not change identity or hash; source container and cursor state are excluded. The value is not cross-runtime stable. Dynamic replacement of Iterator `==`/`hash` invokes the ordinary user-responsibility and explicit-rehash rules. Owner decision: 2026-07-24.
- **D-136 — Iterator strongly retains its source: frozen.** An Iterator holds a strong reference to its source container so the container and iteration state remain alive and usable even when no other Iris reference exists. Behavior never depends on GC timing and no `CollectedSourceError` exists for ordinary iterators. This may extend the lifetime of the container and reachable elements. Whether the strong reference is released immediately on exhaustion/close or only with iterator collection remains separate. Owner decision: 2026-07-24.
- **D-137 — Exhausted Iterator releases its source: frozen.** On the first advance that determines exhaustion and returns singleton `Iteration.done`, the Iterator enters permanent done state and immediately clears its strong source-container reference, current-entry reference, and unneeded traversal state. Later `next()` returns the same done singleton without touching the source; `remove_current()` raises `IteratorStateError`. Iterator identity/hash remain unchanged. Retaining an exhausted Iterator therefore does not retain the source object graph. Early close remains separate. Owner decision: 2026-07-24.
- **D-138 — Iterator early close: frozen.** Iterator provides idempotent `close()`. Calling it before exhaustion immediately releases source/current-entry/traversal references and enters the same permanent done state as natural exhaustion. Subsequent `next()` returns singleton `Iteration.done`; `remove_current()` raises `IteratorStateError`; repeated `close()` succeeds with no additional effect. Identity/hash remain unchanged. Traversal constructs' obligation to close on nonlocal exit remains separate. Owner decision: 2026-07-24.
- **D-139 — Traversal always closes iterators: frozen.** Language/standard traversal constructs guarantee iterator cleanup on every exit path. Natural exhaustion already releases under D-137; `break`, return/nonlocal block exit, body exception, iterator exception, cancellation, or outer unwinding invoke idempotent `close()` with finally/defer-equivalent semantics before propagating the original control flow. This applies even when `each` does not expose the iterator. The protocol is suitable for future resource-backed iterators. Conflict handling when close itself fails remains separate. Owner decision: 2026-07-24.
- **D-140 — Cleanup-failure exception precedence: frozen.** If traversal already has a primary `ExceptionContext` E and iterator `close()` raises C, E remains primary and C's `ExceptionContext` is appended to `E.suppressed`; neither is lost. If the pending exit was normal completion, `break`, return, or another non-exception control transfer, a close failure becomes the primary propagated context and prevents that control transfer from completing. Ordering is governed by D-141. Owner decision revised and confirmed: 2026-07-24.
- **D-141 — Suppressed cleanup failures preserve occurrence order: frozen.** Cleanup remains LIFO and continues after failures. If a primary `ExceptionContext` exists, each cleanup failure's `ExceptionContext` is appended to its `suppressed` list in exact occurrence order; if none exists, the first cleanup failure context becomes primary and later failures append to it. Entries are never sorted, deduplicated, or discarded and retain identity, stack, cause, and nested suppressed state. Owner decision revised and confirmed: 2026-07-24.
- **D-142 — Runtime-owned immutable `ExceptionContext.suppressed`: frozen.** Every `ExceptionContext` exposes a get-only immutable ordered collection/view of suppressed `ExceptionContext` entries. Only runtime unwinding/cleanup machinery appends; user code cannot insert, delete, replace, reorder, or fabricate entries, but may iterate/copy. Raised values themselves do not inherit or store this channel. The public getter may be dynamically replaced under D-143. Owner decision revised and confirmed: 2026-07-24.
- **D-143 — Dynamic public suppressed getter with protected runtime chain: frozen.** The public `ExceptionContext.suppressed` getter may be dynamically replaced or removed, affecting ordinary Iris property reads only. The actual runtime chain remains an unforgeable internal channel used by unwinding, debugger, uncaught formatter, host/native bridge, and reporting tools; it cannot be altered through the getter. JIT property access remains version-guarded. Owner decision revised and confirmed: 2026-07-24.
- **D-144 — Exception cause chaining: frozen.** Throwing a new exception `N` while handling active exception `E` automatically records `E` as `N`'s cause. Throw syntax provides an explicit `from C` form to replace the automatic cause and `from nil` to suppress it. Cause is a single chain distinct from the ordered suppressed-cleanup list; cleanup failures continue to follow D-140/D-141 rather than becoming cause. Public/runtime ownership of the cause property and final exception keyword remain separate decisions. Owner decision: 2026-07-24.
- **D-145 — Throw keyword is `raise`: frozen.** Revived Iris uses `raise error`, `raise error from cause`, and `raise error from nil` as the sole formal throw syntax. Legacy `groan` is intentionally removed and recorded in the migration/divergence ledger; no permanent synonym is provided. Cause semantics follow D-144. Owner decision: 2026-07-24.
- **D-146 — Exception-handling vocabulary: frozen.** Revived Iris uses `try`, `catch`, and `finally` as the sole formal exception-handling keywords. Legacy `order`, `serve`, and `ignore` are intentionally removed and recorded in the migration/divergence ledger; no permanent aliases are provided. Detailed catch matching, ordering, binding, and finally control-flow rules remain separate decisions. Owner decision: 2026-07-24.
- **D-147 — First-version catch match domain: frozen.** A typed catch may name a nominal Class or explicit Contract. Class matching accepts that Class/subclasses; Contract matching accepts Classes with explicit nominal conformance, never structural auto-conformance. V1 catch has no arbitrary patterns, destructuring, or guards. Owner decision revised and confirmed: 2026-07-24.
- **D-148 — Catch selection is source-order first-match: frozen.** Catch clauses are tested in written order and only the first matching Class/Contract clause executes. Iris computes no cross-hierarchy “most specific” match and never executes multiple catches. Statically unreachable later clauses are compile errors. Dynamic matching uses current runtime Class/Contract state. Owner decision revised and confirmed: 2026-07-24.
- **D-149 — Current Contract state affects future catch matching: frozen.** Each exception dispatch uses current Class hierarchy and explicit Contract conformance when selection begins. Catch/JIT caches depend on hierarchy/contract versions and target identity; compatible runtime implementation revisions invalidate/deopt as needed. Once entered, later mutation does not retroactively reselect. Declared conformance itself remains immutable under D-173. Owner decision revised and confirmed: 2026-07-24.
- **D-150 — Catch-all syntax: frozen.** An untyped `catch error { ... }` catches every raised object and binds it; `catch { ... }` is the equivalent catch-all without a binding. A catch-all must be the final catch clause, and any following catch is a compile-time unreachable-clause error. It does not replace or suppress `finally`; normal propagation depends on the catch body's behavior. Owner decision: 2026-07-24.
- **D-151 — Catch binding is lexical and immutable: frozen.** A named catch creates a new immutable binding visible only within that catch body, shadowing but not modifying an outer same-named binding. It may be captured by Closures. The caught object may remain mutable. Typed catches narrow to the named Class/Contract; catch-all binding is Object under D-152. Owner decision revised and confirmed: 2026-07-24.
- **D-152 — Any Iris object may be raised: frozen.** `raise` accepts every Iris value/object without requiring Exception inheritance or a throwable Contract. Catch receives the original value unchanged; catch-all binding is Object. Cause, suppressed failures, and stack live in the per-propagation `ExceptionContext`, not on the raised value. Typed Class/Contract catches match the original object. Re-raise/context lifetime follow D-153 through D-163. Owner decision revised and confirmed: 2026-07-24.
- **D-153 — Explicit raise creates fresh propagation metadata: frozen.** Every explicit `raise object` creates a new propagation record containing its own stack, cause, suppressed list, source location, and state, even when the same object/value was raised before or is a singleton/immutable value. Metadata never permanently accumulates on the object. Catch still receives the original value. Only a bare re-raise may continue the active record; syntax and scope remain separate. Owner decision: 2026-07-24.
- **D-154 — Bare re-raise scope: frozen.** Parameterless `raise` continues the currently handled propagation record and is valid throughout the synchronous dynamic extent of a catch, including helper calls made before that catch exits. Once the catch dynamic extent ends, the active record is unavailable; a stored closure invoked later or any unrelated call to bare `raise` raises ordinary catchable `NoActiveExceptionError`. Bare re-raise does not create a fresh record. Stack-trace presentation remains separate. Owner decision: 2026-07-24.
- **D-155 — Bare re-raise stack history: frozen.** A propagation record preserves the complete original raise stack and an ordered `re_raise_sites` sequence. Each bare `raise` appends one site with source location and current callable/context metadata, without replacing the root stack or duplicating the full current stack. Multiple sites retain occurrence order. Uncaught diagnostics present the original stack followed by re-raise sites, separately from cause and suppressed chains. Owner decision: 2026-07-24.
- **D-156 — Explicit cause accepts propagation handles only: frozen.** `raise value from cause` requires `cause` to be an identity-bearing handle to an existing propagation event, or literal/value `nil` to suppress chaining. A plain arbitrary raised object is not sufficient because it does not identify which of potentially many propagation records/stacks is intended. Automatic chaining uses the current active propagation handle. Passing any other value raises/produces a type-contract error according to static knowledge. The public handle type and catch access syntax remain separate. Owner decision: 2026-07-24.
- **D-157 — Public `ExceptionContext` and catch dual binding: frozen.** Each propagation event has a distinct identity-bearing, runtime-owned, read-only `ExceptionContext`, separate from the original raised object. Typed catch may bind only the object (`catch error: Type`) or both object and context (`catch error: Type, context`); catch-all analogously supports `catch error, context`. Re-raising the same object creates a distinct context. Explicit `from` accepts this context under D-156. Context-only catch syntax remains separate. Owner decision: 2026-07-24.
- **D-158 — Global `_` discard binding and context-only catch: frozen.** `_` is a language-wide discard binding/pattern: it accepts a value without creating a readable binding, may appear repeatedly in one binding/destructuring/parameter list, cannot be captured, and is a compile error when read as an expression. Catch may therefore ignore the raised object while binding context as `catch _, context`, or in typed form `catch _: Type, context`. This discard semantics applies consistently to future block parameters and destructuring. Owner decision: 2026-07-24.
- **D-159 — Public `ExceptionContext` properties: frozen.** `ExceptionContext` exposes get-only `value: Object`, `cause: ExceptionContext?`, `suppressed`, `original_stack`, `re_raise_sites`, and `raise_location`. They expose the original raised value, cause context, immutable ordered cleanup-failure collection, immutable original stack, immutable ordered bare-re-raise sites, and initial raise source location. Public getters remain dynamically replaceable, while runtime diagnostics/unwinding/native bridges read protected internal records. Exact element type of `suppressed` remains separate. Owner decision: 2026-07-24.
- **D-160 — Suppressed entries are `ExceptionContext`: frozen.** `ExceptionContext.suppressed` is an immutable ordered collection/view of `ExceptionContext` objects, one per suppressed cleanup-failure propagation event. Each entry preserves its own raised `value`, original stack, cause, re-raise sites, and nested suppressed contexts. Bare raised objects or formatted strings are not substituted. The public collection type may later be named as an immutable Array/View abstraction. Owner decision: 2026-07-24.
- **D-161 — Exception-context graphs are acyclic: frozen.** Runtime-owned `cause` and `suppressed` edges may not create a cycle, including mixed paths across both edge kinds. Before automatic cause linkage, explicit `from context`, or suppressed append, the runtime performs an identity-based cycle check. A cycle attempt raises ordinary catchable `ExceptionChainError` and leaves the existing graph unchanged. System formatters, debuggers, and native bridges still use visited-set defenses against corrupted plugin/native/runtime data. User-visible properties cannot directly mutate the graph. Owner decision: 2026-07-24.
- **D-162 — ExceptionContext equality and hashing are identity-based: frozen.** `ExceptionContext` uses root identity-only equality and is a valid Hash key through runtime-stable identity hash. Distinct propagation events are unequal even when raised value, stack, cause, and suppressed structure are equivalent. Identity/hash remain stable throughout context lifetime and are not cross-runtime stable. This supports user-visible visited sets and graph analysis. Dynamic method replacement remains subject to ordinary comparison/hash responsibility. Owner decision: 2026-07-24.
- **D-163 — Retained ExceptionContext lifetime and cause reuse: frozen.** A context retained beyond catch remains fully readable, identity/hash-stable, and valid as an explicit future `from` cause. It strongly retains its reachable propagation graph and raised values. Ending catch removes only the active dynamic record used by bare `raise`; a saved context cannot later enable bare re-raise but can be linked explicitly after acyclicity validation. Owner decision: 2026-07-24.
- **D-164 — `finally` may override with non-exception control flow: frozen.** `return`, `break`, and `continue` are legal in `finally` and override any pending normal transfer or exception. If they discard pending exception context `E`, ordinary callers observe only the new control transfer, while runtime records `E` in a protected internal `discarded_contexts` diagnostic channel visible to debuggers/trace/reporting hooks. The exception no longer propagates normally. A new exception raised by finally is preserved through cause/suppressed rules rather than discarded; exact relationship remains separate. Owner decision: 2026-07-24.
- **D-165 — Exception raised by `finally` becomes primary with cause: frozen.** If pending exception context `E` exists and `finally` explicitly raises new value/context `N`, `N` becomes the new primary propagation and `E` is automatically linked as `N.cause`, unless explicit `from another_context` replaces it or `from nil` suppresses it. `E` is not placed in discarded or suppressed for this case. Cleanup failures continue to use suppressed rules. Acyclicity validation applies. Bare raise in finally remains separate. Owner decision: 2026-07-24.
- **D-166 — Bare raise in `finally`: frozen.** Parameterless `raise` in `finally` continues the same pending propagation record, appends a re-raise site, and propagates outward when an exception is still pending. If try completed normally or a catch fully handled the exception so no pending record remains, bare raise instead raises a fresh `NoActiveExceptionError`; it never resurrects a merely recent handled context and never silently succeeds. Owner decision: 2026-07-24.
- **D-167 — Catch executes before finally: frozen.** Control order is try, then the selected first-match catch if any, then finally, then outward commitment of the resulting normal transfer/return/loop transfer/exception. An unmatched exception remains pending through finally. A catch re-raise or replacement exception becomes pending before finally. Finally always runs and may override under D-164/D-165. Owner decision: 2026-07-24.
- **D-168 — Try/catch/finally is value-producing: frozen.** The construct is an expression. On normal try completion its last expression is the provisional result; when a catch handles an exception normally, that catch body's last expression is the provisional result. An empty/no-value body yields `nil`. A normally completing finally does not replace the provisional result, while finally return/break/continue/raise may override control flow under existing rules. Static result typing must merge normal-producing branches without treating finally's ordinary value as a branch result. Owner decision: 2026-07-24.
- **D-169 — Normally completing finally value is discarded: frozen.** A finally body executes fully and evaluates its last expression for all side effects, but its ordinary value is discarded and never replaces the provisional try/catch expression result. Only nonlocal control transfer or raise from finally can override. Optimizers may remove finally expressions only under ordinary proof of no observable effect. Owner decision: 2026-07-24.
- **D-170 — Normal catch completion handles the exception: frozen.** When a selected catch reaches normal completion, the caught propagation is considered handled and its last-expression value becomes the provisional try result. The original exception does not continue automatically. Continuing the same record requires bare `raise`; replacing/wrapping it requires explicit `raise value` with automatic/explicit cause semantics. No truthiness or catch kind changes this rule. Owner decision: 2026-07-24.
- **D-171 — Explicitly raising the caught value creates a new context: frozen.** Bare `raise` alone continues the active propagation record. Any value-bearing `raise value`, even when value is the exact caught binding/object, creates a fresh ExceptionContext with a new original stack; the old active context is automatically linked as cause unless explicit `from` overrides/suppresses it. No identity, equality, alias, or binding-origin special case converts explicit raise into re-raise. Owner decision: 2026-07-24.
- **D-172 — Typed catch narrowing relies on immutable static Contracts: frozen.** Matching performs checked narrowing once and gives the immutable catch binding that static Class/Contract type. A Class revision cannot remove or weaken declared Contract conformance, member names/signatures, typed properties, or other supporting static facts. Dynamic implementation replacement may invalidate caches but must validate before atomic commit; incompatibility raises `TypeContractError` and preserves prior implementation. Owner decision revised and confirmed: 2026-07-24.
- **D-173 — Declared Contract conformance is immutable: frozen.** For a given nominal Class declaration, the declared Contract set and every contract-visible method/property name and signature form a static spine. Metaprogramming cannot add, remove, rename, weaken, or incompatibly replace those facts in place. Dynamic methods, accessors, modules, and bodies may change only when the candidate state still satisfies the complete static spine; validation happens before atomic publication. A different static contract requires a distinct class revision/declaration created through the explicit class-evolution system rather than monkey-patching the active contract. Owner decision revised and confirmed: 2026-07-24.
- **D-174 — Declared superclass is a static nominal bound: frozen.** The declared superclass is an immutable nominal subtype fact and minimum static contract for every runtime evolution. - **D-176 — Static spine constrains the dynamic metaprogramming surface: frozen.** Iris Class design is explicitly two-layered. The static spine contains nominal identity, declared superclass bound, declared Contracts, contract-visible member names/signatures, typed properties, and native layout obligations; compiled code and typed bindings may rely on these facts permanently for that class revision. The dynamic surface contains compatible Method bodies, non-contract members, getter/setter implementations, Module composition, class-object state, and user metadata. Source/link ordering relative to the origin declaration remains separate. Owner decision revised and confirmed: 2026-07-24.

Types are reified, support narrowing, and do not add conditional/mapped types, structural auto-conformance, overload, or arbitrary compile-time computation. Union exposes only common safe members; intersection combines compatible guarantees. Owner decision revised and confirmed: 2026-07-24.
- **D-185 — Nilability is union sugar: frozen.** `T?` is exactly the same type as `T | Nil`, not a distinct constructor. Type identity, reflection, hashing, assignability, runtime guards, generic arguments, narrowing, and JIT semantics are identical. Duplicate Nil/members collapse. Formatting prefers `T?` when the normalized union is exactly one non-Nil type plus Nil; more complex optional-union display remains separate. Owner decision: 2026-07-24.

Members are canonicalized in stable Type-identity order and the normalized composite Type object is runtime-interned, so reordered/grouped equivalents are the same Type identity. Nominal subtype absorption applies: if `Dog <: Animal`, `Dog | Animal` normalizes to `Animal`, while `Dog & Animal` normalizes to `Dog`. Duplicate members collapse. Distribution and impossible-type handling remain separate decisions. Owner decision: 2026-07-24.
- **D-187 — Distribution is logical-only, not canonical expansion: frozen.** Canonical Type identity never expands intersections over unions or unions over intersections into DNF/CNF. Assignability, overlap, and narrowing algorithms may reason with distributive equivalence on demand without materializing/interning exponential expanded Type graphs. Representation and diagnostics remain compact and independent of thresholds/optimization. Base flatten/order/dedup/subtype absorption still applies. Owner decision: 2026-07-24.
- **D-188 — Impossible intersections normalize to `Never`: frozen.** Iris has an intrinsic bottom type `Never`. When nominal/final/constraint reasoning proves an intersection has no possible value, it normalizes to the interned `Never` Type. `Never` has no normally constructible runtime values and is a subtype of every type. It may annotate functions/expressions that cannot complete normally (raise, nonterminating paths) and drives unreachable-flow analysis. Whether source permits arbitrary Never variables and its algebraic simplifications remain separate. Owner decision: 2026-07-24.
- **D-189 — `Never` bottom algebra: frozen.** `T | Never` normalizes to `T`; `T & Never` to `Never`; duplicate Never collapses; `Never?` is `Never | Nil` and normalizes to `Nil`. The empty union identity is `Never`. Raise/nonterminating/unreachable paths may contribute Never without widening branch results. The empty-intersection/top identity remains separate. Owner decision: 2026-07-24.
- **D-190 — `Object` is the top type: frozen.** Because every Iris value is an object, `Object` is the nominal top type and the identity of an empty intersection. Every type, including value/meta/runtime types, is a subtype of Object unless nilability semantics explicitly distinguish Nil membership. `Object` exposes only its declared static contract. `Dynamic` is not the top type and does not serve as an algebraic identity; it represents disabled static member checking subject to its optional nominal bound. Iris introduces no separate `Any` top. Whether Nil is included in non-optional Object remains separate. Owner decision: 2026-07-24.
- **D-191 — `Nil` is an Object and `Object?` collapses: frozen.** `Nil <: Object`; nil is a real object with Class, identity, methods, hash, and raise eligibility. `Object` therefore contains every runtime value and is the true top type. Concrete types such as `String`/`User` do not implicitly include Nil, but `T?` adds it unless already present. Normalization includes `Object | Nil -> Object`, `Object? -> Object`, and `Nil & Object -> Nil`. The nilability principle is membership-based rather than a universal non-null-reference rule. Owner decision: 2026-07-24.
- **D-192 — Unconstrained generic parameters are `Object`-bounded: frozen.** A type parameter with no explicit `where` constraint has implicit upper bound `Object`, not Dynamic and not an implicit non-null bound. `Nil` is therefore a valid type argument, and generic bodies must assume values of unconstrained `T` may be nil while using only Object's static contract. Excluding Nil requires an explicit constraint mechanism. Owner decision: 2026-07-24.
- **D-193 — Built-in `NonNil` marker constraint: frozen.** Iris provides intrinsic marker Protocol/type `NonNil`, satisfied by every type/value except `Nil`; Nil can never acquire it through metaprogramming. It is usable in ordinary type algebra and generic constraints, e.g. `where T: NonNil & Hashable`. `Object & NonNil` denotes all non-nil values, and `Nil & NonNil` normalizes to `Never`. Detailed normalization with unions/type variables remains separate. Owner decision: 2026-07-24.
- **D-194 — `NonNil` normalization: frozen.** Intersecting a union with `NonNil` removes its Nil member semantically: `(A | Nil) & NonNil` becomes `A & NonNil`, then subtype absorption reduces to `A` when A is known non-nil. `Object & NonNil` remains the canonical non-nil top. For an unconstrained/unknown type variable `T`, `T & NonNil` remains explicit and is not simplified to T. This rule drives nil-check flow narrowing without introducing general type subtraction. Owner decision: 2026-07-24.

For each argument position, callers are restricted to the intersection of accepted input domains; the result type is the normalized union of branch return types. If arity, parameter modes, visibility, effects/contracts, or types cannot produce one safe call contract, the member is unavailable until flow narrowing. Runtime method selection remains based on the actual receiver. Optional/variadic arity combination remains separate. Owner decision: 2026-07-24.

Static checking then computes safe parameter domains for the actual positions supplied. The common API need not be representable as one simplified declaration. Variadic acceptance never overrides another branch's finite restriction. Other parameter modes follow the same all-branches-safe principle. Owner decision: 2026-07-24.

If incompatibility is statically certain, the intersection normalizes to `Never` when the type itself is impossible or the declaration/constraint is rejected as unsatisfiable. If openness prevents proof, runtime conformance guards validate candidate classes/revisions. Exact function-signature variance rules remain separate. Owner decision: 2026-07-24.
- **D-198 — Method-contract variance: frozen.** A Method implementation satisfies a typed Contract/intersection/base promise using standard function subtyping: parameters contravariant and return covariant, recursively through callable positions. Owner decision revised and confirmed: 2026-07-24.
- **D-199 — Generic instantiations are strictly invariant: frozen.** V1 has no declaration-site variance, use-site projection, or `Actual as Exposed` generic syntax. `G<A>` and `G<B>` have no subtype/assignment relation merely because `A <: B`, for generic Classes and Contracts alike. `as` cannot cross invariant arguments. Collection conversion is explicit user code; Iris does not implicitly share, copy, or convert elements. Owner decision revised and confirmed: 2026-07-24.

- **D-245 — One active package revision per package API major: frozen.** A runtime activates at most one package implementation revision for each `(package_id, api_major)`. Dependency resolution/linking selects one minor/patch satisfying all constraints before initialization; failure to unify aborts linking/startup. Same-major versions do not coexist with shared identity, override by load order, or gain implicit load-context identities. Coexisting incompatible implementations require different API majors and nominal identities. Hot upgrade remains separate. Owner decision: 2026-07-24.
- **D-246 — Same-major package hot upgrade is explicit and transactional: frozen.** `Package.upgrade(...)` may replace the one active minor/patch implementation with a compatible newer revision of the same `(package_id, api_major)`. The runtime builds candidates for all affected Modules, generic definitions/closed constructions, Classes, methods, properties, native ABI obligations, and extension effects; validates static identities/contracts and initialization as one transaction; then atomically switches all active revisions and invalidates/deoptimizes dependencies. Any failure leaves the old package fully active. Existing instances retain their logical Class identities and begin using the newly active revisions for subsequent sends after commit; already-entered frames and retained Method/BoundMethod objects continue their captured Method identities. Iris does not automatically reinitialize/migrate existing instance state. Old-revision reclamation remains separate. Owner decision revised and confirmed: 2026-07-24.
- **D-247 — Old package revisions unload after captured references and execution cease: frozen.** A superseded package revision remains loaded while reachable from retained Methods/BoundMethods, Closures/code, active interpreter/JIT/construction frames, native handles/pins, revision reflection objects, JIT dependencies, debugger/profiler pins, or other artifacts explicitly tied to old code/metadata. - **D-248 — Hot upgrade preserves compatible state and supports explicit migration: frozen.** A same-major package upgrade reuses existing module/class/shared/per-closed storage whose static contracts remain compatible and does not rerun their ordinary initializers. Newly introduced storage runs its new initializer in the candidate transaction. A package may define an explicit `upgrade(from_version, state/context)` migration hook to transform/validate candidate state. All runtime-owned candidate changes publish atomically with the package revision; hook/validation failure leaves the old package and state active. External side-effect responsibility remains separate. Owner decision: 2026-07-24.
- **D-249 — Upgrade migration owns external side-effect compensation: frozen.** Runtime rollback covers only candidate package/module/Class/state/interning/MRO/contract/JIT/native-binding publication. Filesystem, database, network, external-process, native-internal, and other external effects are not automatically reversed. Migration hooks must use cleanup/compensation and should be idempotent/retry-safe. Failure propagates a normal ExceptionContext, leaves the old package active, and discards the candidate; uncompensated external effects remain the migration author's responsibility. Owner decision: 2026-07-24.
- **D-250 — Package hot-upgrade commit uses a global runtime safepoint: frozen.** After candidate validation/migration, commit brings runtime threads to safepoints, atomically publishes all package/module/Class active revisions and state plus dispatch/JIT dependency invalidation, then resumes execution. Threads never observe a partial package mix. Method frames entered before commit continue their captured old bodies/revisions; sends/lookups after resume use the newly active revisions. Commit does not wait for all old frames to finish; old revision reclamation follows D-247. Owner decision: 2026-07-24.
- **D-251 — Structural open commits use a global runtime safepoint: frozen.** Class/Module structural changes (member/property shape, Method add/remove/replace, Module composition, runtime-superclass/MRO revision, contract implementation, generic revision propagation, native structural metadata) validate off-line then commit atomically at a global safepoint with cache/JIT invalidation/deoptimization. Old entered frames continue old bodies; post-resume sends use new active revisions. Updating the value of an already-existing class/shared property is ordinary state mutation and does not itself require a structural safepoint, subject to future concurrency rules. - **D-252 — Open/revision transactions are synchronous and thread-confined: frozen.** Origin/open transaction bodies execute to completion on one thread and may not `await`, scheduler-yield with resumable transaction state, transfer/resume on another thread, share candidate mutation with child threads, or let candidate/transaction capability escape. They may call ordinary synchronous user/native code and perform IO, but rollback covers only runtime candidate state and external effects remain user responsibility. Violation is a compile error when statically known or `MetaTransactionError` dynamically. Nested transaction behavior remains separate. Owner decision: 2026-07-24.
- **D-253 — Nested opens form one atomic transaction group: frozen.** Same-thread nested `open` calls join the outermost transaction group; inner opens never commit independently. All target candidates and cross-target MRO/contracts validate together and publish at one global safepoint, or all roll back. Reopening a target already in the group reuses its one candidate. The group remains synchronous, thread-confined, non-suspending, and non-escaping. Concurrent transaction conflicts remain separate. Owner decision: 2026-07-24.
- **D-254 — Concurrent open groups use optimistic revision conflicts: frozen.** Candidate construction does not hold long-lived exclusive Class/Module locks. Each target records its base active revision. At commit, the group compares every base; the first valid committer may publish, while any group with an overlapping changed target raises ordinary catchable `MetaTransactionConflictError` and rolls back all candidates. Runtime never auto-merges, rebases, retries, or re-executes the block, avoiding duplicated external effects. User-directed retry remains separate. Owner decision: 2026-07-24.
- **D-255 — No automatic meta-transaction retry in v1: frozen.** Iris/runtime provides no `open_retry`, automatic rebase/merge, or hidden block re-execution after `MetaTransactionConflictError`. User code may explicitly catch conflicts and choose compensation, backoff, retry count, and rerun, accepting responsibility for duplicated external effects and idempotency. Owner decision: 2026-07-24.
- **D-256 — Ordinary instance sends inside open use the published active revision: frozen.** Transaction context does not redirect instance dispatch to an unpublished candidate. Existing instances continue through their logical Class's currently published active revision for ordinary sends inside and outside the open block; candidate members are visible only through transaction-aware Class/Module meta/reflection reads. After atomic commit, subsequent sends from all existing instances use the new active revision. This preserves isolation and prevents helper call chains from seeing uncommitted dispatch. Owner decision revised and confirmed: 2026-07-24.
- **D-257 — No candidate-instance preview in v1: frozen.** Open transactions expose candidate metadata/contracts/MRO/module/layout descriptors through meta/reflection only. They provide no wrapper or operation that dispatches candidate Methods/MRO against an existing instance, no automatic clone/migration, and no purity-based exception. Ordinary instances remain on published revisions. Candidate test-instance semantics are deferred. Owner decision: 2026-07-24.
- **D-258 — Instances bind the stable logical Class, not a permanent revision: frozen.** Every instance references stable logical Class. Ordinary sends, qualified Contract implementation lookup, MRO, and ancestry tests use current active revision. Open/upgrade affects existing/future instances after commit; entered frames and retained Methods continue captured identities. Instance state is not automatically migrated. Owner decision revised and confirmed: 2026-07-24.
- **D-259 — Construction snapshots a revision only for allocation/initialization: frozen.** `A.new(...)` captures A's active revision at construction start so allocation and initialization never mix revisions mid-construction. If a new revision commits before completion, construction continues using the captured code/layout without retry. On success, the instance references logical Class A; subsequent ordinary sends use A's current active revision. Constructor side effects are never automatically repeated or compensated. Owner decision revised and confirmed: 2026-07-24.
- **D-260 — No automatic construction/revision reconciliation in v1: frozen.** Iris provides no `new_current`, `new_checked`, constructor retry, revision lock, automatic post-construction reinitialization, or instance state migration. Applications coordinate construction versus structural metaprogramming when required. If the current active behavior expects state absent from an existing/newly completed instance, responsibility belongs to the metaprogrammer under D-263. Owner decision revised and confirmed: 2026-07-24.
- **D-261 — Class revisions are transparent to nominal type identity: frozen.** Every instance and revision of logical Class A has nominal Type A. `is A`, typed boundaries, generics, Contract/static-spine promises, and Type metadata treat revisions identically. Revision identity is explicit reflection only; runtime ancestry follows D-262. Owner decision revised and confirmed: 2026-07-24.
- **D-262 — Runtime ancestry tests use the logical Class's current active revision: frozen.** `is` and runtime checked ancestry tests inspect the active revision current at the test. After a superclass/MRO evolution commit, existing and future instances observe the new runtime ancestry for subsequent tests/sends. The immutable declared superclass bound remains the permanent compile-time ancestry promise; stricter runtime ancestors require a current `is` check/narrowing. Already-running frames are unaffected until later operations. Owner decision revised and confirmed: 2026-07-24.
- **D-263 — Structural metaprogramming responsibility boundary: frozen.** Iris guarantees static-spine Contracts, superclass bounds, MRO acyclicity, atomicity, memory/GC/native-layout safety, and invalidation. It does not rerun constructors/migrate fields/resources/scan instances/restore business invariants. Existing instances follow new behavior with old state; users own reinitialization. Memory/GC/ABI-unsafe candidates are always rejected. Owner decision revised and confirmed: 2026-07-24.
- **D-264 — Optional explicit instance revision-migration convention: frozen.** V1 defines a conventional instance Method `migrate_revision(from, to)` that applications may implement and explicitly invoke on objects they themselves track after structural evolution. Runtime/open commit never enumerates live instances, never invokes this Method automatically, and provides no Class-wide live-instance enumeration. Applications choose object sets, timing, synchronization, retries, and compensation. Exact parameter types/selector protection remain separate. Owner decision: 2026-07-24.
- **D-265 — `migrate_revision` is an ordinary dynamic message: frozen.** The convention is an ordinary unqualified replaceable Method, no privileged path or special Contract, and never implicit. Applications own results. Parameters follow D-266. Owner decision revised and confirmed: 2026-07-24.
- **D-266 — Migration arguments are read-only `ClassRevision` objects: frozen.** Conventional signature is `migrate_revision(from: ClassRevision, to: ClassRevision) -> Nil`. `ClassRevision` is identity-bearing, runtime-owned/read-only, reflectable, `same?`-comparable, and usable as an identity Hash key. It exposes owner Class, revision number, static-spine reference, runtime superclass/MRO/modules, member/property metadata, layout/shape descriptor, and source/package revision metadata. Users cannot mutate/reactivate it. Holding one pins its metadata/code. Success returns Nil; failure raises ordinary exceptions. Revision numbering remains separate. Owner decision: 2026-07-24.
- **D-267 — ClassRevision numbers are per-Class monotonic: frozen.** Each stable logical Class numbers revisions independently: origin revision is `1`; each successful structural publication affecting that Class receives the next integer; failed/rolled-back candidates consume no number. Numbers from different Classes have no ordering/equality meaning by themselves; use owner plus number or `same?`. Numbers are diagnostic/history metadata, not cross-runtime stable Type identity. Multi-Class group commit correlation remains separate. Owner decision: 2026-07-24.
- **D-268 — Structural commits have runtime-wide monotonic `commit_id`: frozen.** Each successfully published structural transaction group receives one runtime-wide strictly increasing `commit_id`, shared by all Class/Module revisions in that group. Failed/rolled-back groups receive/consume none. Per-Class `revision_number` remains independent. `commit_id` is runtime-local diagnostic/audit ordering metadata, not cross-process stable and not part of nominal Type identity. Revision metadata may additionally record package/source/initiator information. Owner decision: 2026-07-24.
- **D-269 — Superseded revisions are reclaimable with lightweight audit history: frozen.** Active revisions and old revisions pinned by Method/frame/native/tool/user `ClassRevision` references retain full executable metadata/code. Once unreferenced and inactive, heavy revision state may be reclaimed/unloaded. Reflection history retains a lightweight non-executable audit record containing owner, revision number, commit ID, package/source/initiator, timestamps/context, and change summary sufficient for diagnostics but not Method execution. Retention/storage policy may bound persisted audit records without pinning executable revisions. Rollback/reactivation from records remains separate. Owner decision: 2026-07-24.
- **D-270 — Rollback creates a new validated revision: frozen.** Historical revisions/audit records are never directly reactivated. `Class.rollback(target)` is a new structural transaction that reconstructs desired state from current active state plus available historical artifacts, validates current static spine/contracts/MRO/native constraints, and publishes with new per-Class revision number and runtime commit ID. History remains linear. External data/resources/instance state are not restored automatically. Lightweight audit records need not retain executable code; artifact requirements remain separate. Owner decision: 2026-07-24.
- **D-271 — Audit rollback requires exact artifact retrieval: frozen.** Lightweight audit records retain an immutable artifact locator plus cryptographic digest. Rollback resolves the exact source/bytecode/native artifact through the active package store or an explicit user resolver and verifies the digest before reconstruction. Missing, inaccessible, or mismatched artifacts raise ordinary catchable `RevisionArtifactUnavailableError` and publish nothing; runtime never substitutes current/nearest source or approximate semantics. Digest algorithm/scope remain separate. Owner decision: 2026-07-24.
- **D-272 — Revision artifacts use full BLAKE3-256 canonical manifests: frozen.** Integrity digest is the complete 32-byte BLAKE3 hash of a canonical manifest covering relevant Iris source blobs, bytecode/IR, native binaries, dependency package IDs/API majors/exact revisions, Iris language/compiler/runtime ABI versions, and every semantics-affecting build option/path-to-content mapping. Locator is excluded so mirrors may change. Any mismatch aborts exact recovery. Canonical manifest serialization/path normalization remain package-format details. Owner decision: 2026-07-24.
- **D-273 — Same-major rollback cannot downgrade the current static spine: frozen.** Rollback may use an older minor/patch implementation artifact of the same package API major, but reconstructs a candidate against the currently active static spine/contracts. Old bodies/state logic may be restored only if they satisfy every current member, Contract, generic, superclass-bound, visibility, and native obligation. Missing later contracts cause rollback failure; runtime does not remove current API or synthesize failing stubs. Owner decision revised and confirmed: 2026-07-24.
- **D-274 — Same-major releases may add only backward-compatible ordinary static API: frozen.** Minor/patch revisions may add ordinary typed methods/properties that do not invalidate existing callers or implementers. They may not change/remove existing signatures, constraints, visibility obligations, superclass bounds, generic arity/invariance, add required members to existing Contracts, or add new mandatory obligations to existing implementers. Such changes require a new package API major/nominal identity. Owner decision revised and confirmed: 2026-07-24.
- **D-275 — Contracts have no default Method implementations: frozen.** Contracts are pure static promises: member names/signatures/generic constraints/visibility and qualified slot identities only. They contribute no Method bodies to MRO, `super`, or dispatch. Behavior reuse belongs to Modules with explicit mixin/include and Self constraints. Existing Contract required members cannot gain compatibility-evolution defaults in minor releases; adding required members remains API-major breaking. Owner decision revised and confirmed: 2026-07-24.
- **D-276 — Contracts support multiple inheritance/composition: frozen.** A Contract may inherit multiple named Contracts, forming the union of their static requirements without creating any implementation MRO or `super` path. Compatible same-name requirements merge into one obligation under method-compatibility rules; incompatible requirements make the declaration a compile-time error. Parent order never chooses a winner, and Contract inheritance cycles are compile errors. Exact keyword syntax remains separate. Owner decision: 2026-07-24.
- **D-277 — Contract inheritance uses `extends`: frozen.** Syntax is `contract Child extends ParentA, ParentB { ... }`. `extends` uniformly denotes nominal subtype: Classes permit one superclass, Contracts permit one or more parent Contracts. Contract parent order has no winner/MRO meaning. `include` remains runtime Module composition only. Owner decision: 2026-07-24.
- **D-278 — Class Contract conformance uses header keyword `for`: frozen.** Syntax is `class Sprite extends Node for Drawable, Serializable { ... }`. In a Class header, `for` declares immutable nominal Contract conformance in the static spine; individual implementing members use `impl`. In statement grammar, `for` remains the iteration keyword, with declaration context making the uses unambiguous. `satisfies` and legacy `implements` are not formal keywords. Owner decision revised and confirmed: 2026-07-24.
- **D-279 — Only Classes declare Contract conformance with `for`: frozen.** Modules cannot use header `for` to claim instance Contract conformance, and Module composition never automatically transfers nominal conformance to the host. A Module may provide `impl`-marked compatible bodies and constrain `Self` by a Contract; the final Class static spine must explicitly list the Contract with `for`. Dynamic Module removal is rejected if it leaves that declared Contract without a compatible implementation. Owner decision: 2026-07-24.
- **D-280 — Class header clause order is fixed: frozen.** Canonical grammar order is `class Name<T...> extends Base for ContractA, ContractB mixin ModuleA, ModuleB where ... { ... }`. Each clause kind appears at most once, omitted clauses are skipped without reordering, and formatters emit this order. The sequence expresses nominal base, static Contract promises, static behavior composition, then generic constraints. `extends` remains single-Class, while `for`/`mixin` accept comma-separated lists. Owner decision: 2026-07-24.
- **D-281 — Module and Contract header grammars are fixed: frozen.** Module grammar is `module M<T...> mixin A, B where Self: ContractExpr, T: ConstraintExpr { ... }`; it supports neither `extends` nor `for`. Contract grammar is `contract C<T...> extends A, B where T: ConstraintExpr { ... }`; it supports neither `for` nor `mixin`. Each allowed clause appears at most once and in shown order. `Self` is intrinsic only where defined for Module host constraints. Owner decision: 2026-07-24.
- **D-282 — `where` separates parameter constraints with commas: frozen.** Grammar is `where T: A & B, U: C | D`. Each comma starts a different type-parameter/Self constraint assignment; each constrained parameter appears at most once. `&`, `|`, precedence, and parentheses exclusively compose the type expression for one parameter. Comma never means intersection/all-of. Owner decision: 2026-07-24.
- **D-283 — Omitted Class `extends` means `Object`: frozen.** `class A { ... }` and `class A extends Object { ... }` have the same static spine/direct superclass; Object alone has no superclass. Origin/open distinction comes solely from `class` versus `open class`, not presence/order. No second root Class may be declared. Source formatting may preserve explicitness while reflection normalizes it. Owner decision: 2026-07-24.
- **D-284 — Omitted Contract/Module clauses use empty composition and Object bounds: frozen.** A Contract without `extends` has no parent Contracts. A Module without `mixin` composes no Modules. A Module without explicit `where Self:` has implicit `Self: Object`; any other unconstrained generic parameter likewise has Object upper bound. No implicit Contract parent or NonNil constraint is added. Whether built-in NilClass may compose Modules remains separate. Owner decision: 2026-07-24.
- **D-285 — Nil Class participates in ordinary Module composition: frozen.** Nil's stable Class may statically mix and transactionally include/remove Modules like other Classes, subject to Module `Self` constraints, static-spine/Contract preservation, atomic revision commit, and JIT/cache invalidation. The unique nil singleton uses the Class's new active revision for subsequent sends; composition creates no new nil instances. Static visibility follows declarative versus programmatic open rules. Owner decision: 2026-07-24.
- **D-286 — Built-in Bool/numeric Classes are structurally open within safety bounds: frozen.** Bool, Integer, Float32, and Float64 stable Classes may be opened, gain/remove dynamic members/Modules/properties, and replace compatible Method implementations like user Classes. Their instance value bits/mathematical representation/layout immutability and built-in static Contracts/native/GC safety cannot be broken. Primitive/interpreter/JIT fast paths depend on active revision and exact Method/slot versions and invalidate/deopt after commit. Static API visibility follows declarative/programmatic open rules. Runtime-superclass mutation remains separate. Owner decision: 2026-07-24.
- **D-287 — Built-in value Class superclass mutation is rejected by the meta API: frozen.** Nil, Bool, Integer, Float32, and Float64 remain behaviorally open for compatible Method/Module/property-protocol changes, but their runtime superclass cannot be changed. Any declarative or programmatic attempt to invoke the structural `superclass=` operation on these protected Classes raises a meta-operation exception and publishes no candidate revision. Protection is an intrinsic Class/meta-API capability flag owned by the runtime, not a user-implementable `ValueSuperclass` Contract or unsafe escape hatch. This preserves tagged/unboxed representation, GC/native ABI, and primitive assumptions while keeping ordinary behavior open. Owner decision revised and confirmed: 2026-07-24.
- **D-288 — Structural protection is enforced at the unified runtime meta-operation boundary: frozen.** Every syntax/API path that can request superclass mutation lowers to the same runtime structural operation and unforgeable capability check. Protection applies equally to `open class`, `Class#open`, aliases, reflection, Dynamic calls, qualified/unqualified meta messages, nested transaction groups, package upgrade/rollback, deserialization, native/plugin/host APIs, and indirect helper calls. No alternate method-table replacement, raw metadata write, custom setter, monkey patch, or unsafe user flag may bypass it. Attempting `superclass=` on a protected Class aborts the complete transaction group before publication; unrelated candidate targets in that group also roll back. Runtime/native bugs aside, user code can never acquire or fabricate the internal capability required to alter a protected superclass. Owner decision: 2026-07-24.
- **D-289 — Metaprogramming protection uses uniform immutable `MetaCapabilities`: frozen.** Every Class static spine contains a read-only, reflectable `MetaCapabilities` policy describing which structural operations are permitted (e.g. method open/replacement, Module composition, dynamic members, runtime-superclass change, instance-shape/native-layout change). Every syntax, reflection, Dynamic, package, native, and host meta path invokes the same operation-level capability check. Absence raises ordinary catchable `MetaCapabilityError` carrying target, operation, policy origin, and reason, and aborts the transaction atomically. Built-ins are not name-based magic exceptions: they use the same policy. User Class origins may only narrow the language/default capability set, not grant runtime-internal powers or later widen their immutable policy. Exact declaration syntax remains separate. Owner decision: 2026-07-24.
- **D-290 — Class meta restrictions use header `meta deny`: frozen.** Class origin header order extends to `extends -> for -> mixin -> where -> meta`. Syntax `meta deny capability_a, capability_b` records immutable static-spine restrictions. Only denial/narrowing is source-expressible; omitted capabilities inherit defaults, and no source `allow` can grant unavailable runtime powers. Open/conditional code cannot change the policy. Reflection exposes it and all meta APIs enforce it through D-289. Exact capability vocabulary/dependencies remain separate. Owner decision: 2026-07-24.
- **D-291 — V1 MetaCapabilities use explicit structural/implementation categories: frozen.** Vocabulary includes `method_set`, `method_body`, `property_set`, `property_body`, `modules`, `superclass`, `subclass`, `shape`, `class_state_set`, `class_state_write`, `instance_state`, and `native`. `instance_state` controls creation/recreation of undeclared per-instance ivars; deletion remains cleanup under D-306. - **D-292 — MetaCapabilities are orthogonal and operations require explicit sets: frozen.** Denying one capability does not implicitly deny another. - **D-293 — Common meta-operation capability mapping: frozen.** Method slot/signature changes require `method_set`; compatible Method body replacement `method_body`; property/accessor slot/signature changes `property_set`; compatible accessor body replacement `property_body`; stored instance-property changes additionally `shape`; Module composition `modules`; runtime-superclass change `superclass`; selecting a Class as declared/runtime superclass requires target effective `subclass`; class/shared slots `property_set & class_state_set`; existing class/shared value writes `class_state_write`; native involvement adds `native`. - **D-301 — Class/shared storage structure and writes are separate capabilities: frozen.** `class_state_set` controls adding/removing/changing class/shared storage slots; `class_state_write` controls assignment/mutation of an existing slot's stored value through Class meta/property state APIs. - **D-302 — `modules` remains one composition capability: frozen.** One `modules` capability controls Module include/mixin, removal, replacement, and ordering/recomposition because all alter MRO/dispatch and membership operations could otherwise emulate order changes. - **D-303 — `shape` governs Class-wide layout; `instance_state` governs per-object expansion: frozen.** `shape` is required for revision-level typed storage, shared layout/shape descriptors, all-instance slots, native layout, and GC tracing structure. - **D-305 — Identity-less values cannot acquire undeclared dynamic ivars: frozen.** Identity-less immutable values, including Integer, Float32, and Float64, cannot create, recreate, or retain undeclared per-instance dynamic ivars because such state would create observable identity or value-keyed global state. Their effective Class policy intrinsically denies `instance_state` through the same MetaCapabilities model, enforced across source, reflection, Dynamic, native, and host paths. Identity-bearing nil/Bool singletons follow their own Class policies. Owner decision: 2026-07-24.
- **D-304 — `instance_state` controls undeclared dynamic instance-variable expansion: frozen.** When effective `instance_state` is present, instances may create undeclared dynamic ivars under ordinary object rules. `meta deny instance_state` causes first assignment to an absent undeclared ivar (including recreation after deletion) to raise ordinary catchable `InstanceStateError`. Re-including an already-present closed Module is idempotent: it creates no duplicate, does not move/reorder the existing occurrence, and causes no structural revision unless other edge metadata changes. Events cannot veto or roll back the committed transaction; subscriber failure handling and payload/access remain separate. Owner decision: 2026-07-24.

Payload is filtered through subscriber reflection permissions; private Method bodies, raw private data, native secrets, and inaccessible values are not exposed. Immutable events enter a runtime queue ordered by `commit_id`; within one event/commit subscribers run in subscription order. Subscriber code never runs in the safepoint/commit path. A flush/wait API is available for tests and controlled shutdown. Backpressure/loss policy remains separate. Owner decision: 2026-07-24.

Dropped event ranges are never silent: the queue coalesces them into a `GapEvent(from_commit, to_commit)` and continues with newer events. Consumers may recover from audit history. Zero-loss audit requirements use a separately configured persistent host/runtime sink rather than unbounded in-memory queues. Recovery API/retention guarantees remain separate. - **D-327 — Audit history exposes explicit range recovery with unavailable errors: frozen.** `RevisionHistory.events(from_commit:, to_commit:) -> Iterator<RevisionAuditEvent>` returns retained lightweight events in commit order. GapEvent consumers may use it; persistent sinks define stronger retention externally. Iterator follows Iteration/close rules. Owner decision: 2026-07-24.
- **D-328 — Raw ivar reflection uses runtime/package `ReflectionPolicy`, not capability tokens: frozen.** V1 has no first-class ReflectionCapability token, token argument, delegation, derivation, or revocation graph. Reflection calls are ordinary APIs (`Reflection.list_ivars/get_ivar/set_ivar/remove_ivar`) and authorization is ambient to the currently executing package/module context under a runtime policy configured by the external Host/CLI and constrained by package manifest permissions. Method visibility, Dynamic typing, Module private authorization, and MetaCapabilities do not themselves grant reflection. Denial raises `ReflectionAccessError`; creating/recreating a slot additionally checks target effective `instance_state`, and identity-less values remain prohibited. Owner decision revised and confirmed: 2026-07-24.
- **D-329 — ReflectionPolicy separates inspect/mutate and scope: frozen.** Runtime policy grants `inspect` (list/get) and `mutate` (set/remove) independently to an executing package. Scope may be own package, selected packages/Classes, or runtime-wide according to Host policy; mutate does not imply inspect. Every operation checks caller package identity, granted permission/scope, target Class `instance_state`, identity-less restrictions, and host/native safety. Ordinary Iris code and native extensions cannot enlarge policy; package manifests request but do not self-grant permissions. `ReflectionAccessError` reports caller package, operation, target scope, and denial origin without leaking inaccessible data. Finer first-class delegated tokens are deferred beyond v1. Owner decision revised and confirmed: 2026-07-24.

Requests are declarative requirements, never self-authorization. The Host/CLI must explicitly grant a subset; unspecified permissions default deny, and startup/link may fail if the package marks an ungranted request required. Runtime-wide reflection cannot be requested by a package and exists only by Host configuration for trusted tooling. Dependency propagation remains separate. Owner decision: 2026-07-24.

A privileged package cannot implicitly lend rights to an unprivileged helper; it must perform reflection itself and pass ordinary filtered results. This prevents confused-deputy escalation. Closure/Method package ownership remains separate. Owner decision: 2026-07-24.
- **D-332 — Callable ReflectionPolicy uses lexical definition package: frozen.** Method reflection calls use the package defining that exact Method body; Closure calls use the package of its creating code and retain it after escape/cross-package invocation; BoundMethod inherits its Method package. Extension-open Methods belong to the extension package, not target Class origin. Caller/receiver/stack do not alter rights. Hot-upgraded replacement Methods use the new body artifact's package identity. Owner decision: 2026-07-24.
- **D-333 — Executable Class/Module bodies use their concrete source package policy: frozen.** Origin body code executes under the origin source package's ReflectionPolicy. Declarative extension/open body code executes under the extension source package, never the target Class/Module package. - **D-334 — Native callables use native-artifact package policy: frozen.** Each native artifact/callable belongs to its manifest package identity and performs reflection under that package's Host grants, never caller/receiver/stack or ambient Host superuser rights. Host built-ins use a dedicated host package identity with explicit policy. Manifestless native artifacts default to no reflection unless Host loads them under an explicitly trusted package identity. Process-local code execution alone grants no reflection privilege. Owner decision: 2026-07-24.
- **D-335 — Raw ivar Reflection uses Ruby-like missing/return behavior: frozen.** Authorized `get_ivar(obj,name)` returns nil for absent slot and creates nothing. `set_ivar` returns the assigned value; creating/recreating an absent slot additionally requires effective `instance_state`. `remove_ivar` returns the removed old value and raises `InstanceVariableNotFoundError` when absent, avoiding nil ambiguity. `list_ivars` returns an immutable `Array<Symbol>` of currently existing names with unspecified order. Identity-less values and ReflectionPolicy checks still apply. Name validation remains separate. Owner decision: 2026-07-24.
- **D-336 — Raw ivar reflection names are source-expressible `@` Symbols: frozen.** Reflection raw-ivar operations require a Symbol whose canonical name begins with exactly one `@` followed by a valid ordinary identifier; Strings never implicitly convert. Source `@name` and Symbol `:@name` denote the same receiver slot, and `list_ivars` returns those Symbols. Empty names, repeated `@`, method suffix `?`, or source-inexpressible identifiers raise `InvalidInstanceVariableNameError`; reflection cannot create hidden-only ivars. General Symbol literal syntax remains separate. Owner decision: 2026-07-24.
- **D-337 — Symbol literals use colon simple/quoted forms: frozen.** `:name`, operator forms such as `:+`, and ivar forms such as `:@x` create simple Symbols; `:"arbitrary text"` creates an arbitrary-text Symbol using String escape rules but no interpolation. Symbols are immutable and runtime-interned by exact canonical content. Raw-ivar APIs further restrict accepted Symbol content under D-336. Identity/equality/hash remain separate. Owner decision: 2026-07-24.
- **D-338 — Symbols are identity-less immutable values: frozen.** Symbol equality is exact canonical-content value equality; `same?` raises `IdentityError`. Runtime interning/storage sharing is unobservable and not semantic identity. Symbols may be reconstructed across serialization/runtime, are valid Hash keys, and require stable content hashing. Case/Unicode canonicalization remains separate. Owner decision: 2026-07-24.
- **D-339 — Symbol public hash is stable domain-separated BLAKE3: frozen.** Use BLAKE3 derive-key context exact ASCII `Iris Language v1 stable symbol hash`; input is canonical shortest ULEB128 of canonical UTF-8 byte length followed by those UTF-8 bytes. Reduce digest by first eight bytes interpreted little-endian to `0..2^64-1`. Domain is independent from String/numeric/singleton hashes. Canonical Unicode/case rules remain separate. Owner decision: 2026-07-24.
- **D-340 — Identifier/Symbol normalization and case: frozen.** Ordinary identifiers are case-sensitive and lexer-normalized to Unicode NFC before name/selector/Type identity. Simple Symbols reuse the corresponding normalized identifier/operator/ivar canonical content. Quoted arbitrary-text Symbols preserve the exact post-escape Unicode scalar sequence with no normalization; case and canonically equivalent sequences remain distinct there. Stable hashing encodes the resulting canonical content. Allowed identifier character classes remain separate. Owner decision: 2026-07-24.
- **D-341 — Identifiers use Unicode XID rules with security exclusions: frozen.** Before/with NFC canonicalization, identifier start is Unicode XID_Start or `_`; continuation is XID_Continue or `_`. Pattern_Syntax, Pattern_White_Space, controls, and default-ignorable code points are forbidden even if otherwise classified. CJK and other scripts are supported. Mixed-script/confusable identifiers are valid language syntax but tooling emits configurable security lint warnings. Suffix punctuation remains separate. Owner decision: 2026-07-24.
- **D-342 — Method/property selectors may end in one `?` or `!`: frozen.** Callable/property selector identifiers may carry at most one trailing `?` or `!`, included in selector identity. Ordinary locals/parameters/constants/Class/Module/Contract/type-parameter names cannot. `?` and `!` have no mandatory return/mutation semantics; they are naming conventions available to APIs and lint tools. Combined setter suffix rules remain separate. Owner decision: 2026-07-24.
- **D-343 — Properties are explicit Method selectors: frozen.** Getter declaration is `property fun name() -> T`; setter declaration is `property fun name=(value: T) -> Nil` (or its declared result contract). Property read `obj.name` sends the zero-argument property selector; assignment `obj.name = value` sends the one-argument `name=` selector. Full selectors may include suffix punctuation before `=`, including `ready?=` and `value!=`. Declaration/property-assignment grammar uses contextual longest-selector recognition, while expression `a != b` remains inequality. No hidden getter/setter is generated merely by naming. Assignment result remains separate. Owner decision: 2026-07-24.
- **D-344 — Property assignment returns the setter Method result: frozen.** `obj.name = value` is a message expression equivalent to `obj.name=(value)` and yields that Method's actual declared/runtime result. Iris does not force the right-hand value or nil. Setters may return old value/status/other typed result; ordinary setters commonly return Nil by declaration. Chained assignment semantics remain separate. Owner decision: 2026-07-24.
- **D-345 — Assignment is right-associative and property chains pass setter results: frozen.** `a.x = b.y = v` parses/evaluates as `a.x=(b.y=(v))`; the outer setter receives the inner setter's actual result, not necessarily original v. Static checking uses the inner result type against the outer parameter; Dynamic paths use normal runtime guards/errors. Evaluation follows the expression tree once per receiver/RHS. Local/index mixed assignment remains separate. Owner decision: 2026-07-24.
- **D-346 — Binding writes return stored values; message writes return Method results: frozen.** Local/class/shared/raw-ivar assignment yields the actual value stored in the binding/slot. Property and index assignment yield their setter Method result (`name=`/`[]=`). All assignment forms are right-associative, so mixed chains pass each inner expression's actual result outward. Binding assignment is not customizable; message assignment remains dynamic dispatch. Compound assignment remains separate. Owner decision: 2026-07-24.
- **D-347 — Compound assignment is single-evaluation read/operator/write: frozen.** `target OP= rhs` is not an independent selector. It evaluates receiver/index/key and RHS once, reads target once, sends ordinary `OP` to the read value, then writes the operation result once through the target's normal binding/property/index setter. The compound expression yields that write-back operation's result: new stored value for bindings/raw ivars, setter Method result for property/index. Side effects are never duplicated. Supported OP set remains separate. Owner decision: 2026-07-24.
- **D-348 — V1 symbolic compound-assignment set is fixed: frozen.** Supported forms are `+=`, `-=`, `*=`, `/=`, `**=`, `&=`, `|=`, `^=`, `<<=`, and `>>=`, each using D-347 with its corresponding ordinary operator. No independent compound selector exists. Named infix methods such as `div`/`mod` do not acquire `div=`/`mod=` syntax. Removed rotate operators have no compound forms. Logical short-circuit assignment remains separate. Owner decision: 2026-07-24.
- **D-349 — Logical short-circuit assignments are supported: frozen.** `target &&= rhs` and `target ||= rhs` are control-flow assignment syntax, not Method/operator selectors. Target location/receiver/index is evaluated/read once. `&&=` evaluates/writes RHS only when current value is truthy; `||=` only when current value is falsy. No-write path yields the current value. Write path yields the normal write-back result (stored RHS for binding/raw ivar, setter result for property/index). RHS is never evaluated on the short-circuited path. Truthiness remains to be formally reaffirmed. Owner decision: 2026-07-24.
- **D-350 — Truthiness is the dynamic `to_bool() -> Bool` protocol: frozen.** Initially every object inherits or defines ordinary dynamically replaceable `to_bool() -> Bool`; after permitted removal, D-353 fallback applies. Root Object returns true; Nil's Class returns false; Bool returns self, so false/true preserve their Bool values. Conditions evaluate operand once, send `to_bool` once, require actual Bool, and never recursively convert the result. Wrong return raises `TypeContractError`; exceptions propagate. Optimizers depend on exact Method/revision versions. Owner decision revised and confirmed: 2026-07-24.
- **D-351 — `!`, `&&`, `||`, `&&=`, and `||=` are non-overloadable core control flow using `to_bool`: frozen.** No Class/Module may install Method selectors for these tokens. `!x` sends `x.to_bool()` once and returns its Bool negation; `!!x` normalizes through two core negations without invoking a second custom conversion beyond each `!` operand's required truth test semantics. `a && b` tests a via `to_bool`; when false returns original a without evaluating b, otherwise evaluates/returns b. `a || b` tests a; when true returns original a, otherwise evaluates/returns b. RHS short-circuit is guaranteed and `&&=`/`||=` follow D-349. `&`, `|`, `^`, `~` remain overloadable messages. Error propagation from `to_bool` remains separate. Owner decision revised and confirmed: 2026-07-24.
- **D-352 — `to_bool` failures propagate unchanged: frozen.** If truth testing invokes `to_bool` and it raises, the same propagation continues without wrapping/coercing to false. Conditional bodies/RHS and logical-assignment writeback do not run. Any target-location evaluation already performed is not rolled back. A non-Bool normal return remains a `TypeContractError` under D-350. Owner decision: 2026-07-24.
- **D-353 — Missing `to_bool` uses one ordinary `method_missing` fallback: frozen.** Object initially provides `to_bool() -> Bool { true }`; Nil overrides false and Bool returns self. The Method may be removed when `method_set` permits. Truth testing performs normal zero-argument lookup; if absent, runtime invokes `method_missing(:to_bool, [], nil)` once. Result must be Bool or raises `TypeContractError`. Missing/recursive fallback terminates with ordinary message-missing failure and never recursively truth-tests fallback results. Owner decision revised and confirmed: 2026-07-24.
- **D-354 — General missing-message protocol is `method_missing`: frozen.** Root Object declares ordinary dynamically replaceable `method_missing(selector: Symbol, arguments: Array<Object>, block: Closure?) -> Object`. The handler is not recursively re-entered for a missing `method_missing` lookup itself. Qualified Contract-slot behavior remains separate. Owner decision: 2026-07-24.

Absence/invalidation of the exact qualified slot raises `ContractDispatchError` with receiver Class/revision, Contract identity, selector/signature, source location, and current Contract/MRO metadata. - **D-356 — Visibility denial bypasses `method_missing`: frozen.** If ordinary selector lookup finds a Method/property but the caller lacks private/protected visibility, dispatch raises `MethodVisibilityError` directly. It does not invoke `method_missing`, conceal the distinction as absence, or permit fallback to bypass/probe hidden members. `method_missing` handles only selectors genuinely absent from ordinary lookup. Arity/type mismatch remains separate. Owner decision: 2026-07-24.
- **D-357 — Existing selector call mismatches fail directly: frozen.** When ordinary lookup resolves a selector, arity mismatch raises `ArgumentError` and runtime argument/block Contract failure raises `TypeError`; neither invokes `method_missing`. Iris performs no overload fallback or implicit coercion after selector resolution. `method_missing` applies only to genuinely absent ordinary selectors. Owner decision: 2026-07-24.
- **D-358 — Iris supports no Method overloading: frozen.** One complete selector in one Class revision/MRO slot namespace maps to at most one Method. Iris has no overload by parameter type, return type, arity, generic constraints, static expected type, or runtime argument types; it performs neither compile-time overload resolution nor runtime multi-dispatch. Defining the same complete selector again is replacement and requires explicit `override`, not an overload. APIs use optional/variadic parameters, union/intersection types, generic Methods, narrowing, distinct selector names, receiver dynamic dispatch, or `method_missing` only for true absence. Contract-qualified selectors such as `Parser::process` and `Validator::process` are distinct namespaced selectors explicitly chosen with a Contract view and `..`, not overload candidates. Each qualified selector likewise has at most one Method. Owner decision: 2026-07-24.
- **D-359 — `&&`/`||` static results are normalized operand unions: frozen.** Dynamic `to_bool() -> Bool` controls only which original operand value is returned; its Bool result is not the expression value. Therefore the static result type is the normalized union of reachable operand result types, e.g. `String && Integer` or `String || Integer` yields `String | Integer` absent compile-time-unreachable constant branches. Arbitrary `to_bool` implementations are not type predicates and cause no implicit narrowing. Explicit `is`, nil comparisons, and other dedicated flow tests perform narrowing separately. Runtime/JIT may optimize branch reachability under version guards without changing the stable source type. Owner decision: 2026-07-24.
- **D-360 — Condition testing creates a Bool temporary without retyping the operand: frozen.** `if/while` and other condition contexts evaluate the source once, call `to_bool() -> Bool` once, and branch on that Bool result. The original variable/expression value and static type remain unchanged in either branch unless a separate explicit narrowing predicate applies; `String | Integer` does not become Bool. Explicit `to_bool`, `!`, and `!!` expressions yield Bool, while operand-returning `&&`/`||` retain union result types. Owner decision: 2026-07-24.
- **D-361 — Static types of logical negation and short-circuit assignment: frozen.** `!x` and `!!x` always have static type Bool. `target &&= rhs` and `target ||= rhs` have the normalized union of the no-write path's current target-read type and the write path's actual write-back result type. Binding/raw-ivar writes contribute the RHS value type; property/index writes contribute the setter Method return type. Proven unreachable paths may be eliminated through ordinary normalization. Owner decision: 2026-07-24.
- **D-362 — Legacy statement-leading semicolons are removed: frozen.** Revived Iris does not lex/parse `;statement` as a compatibility or deprecated form. Legacy examples require migration. A leading semicolon is not an optional marker and produces syntax error except where another explicitly defined grammar later uses it. Owner decision: 2026-07-24.
- **D-363 — Statements use syntax-aware newlines, explicit backslash continuation, and optional trailing semicolons: frozen.** A newline terminates when grammar can complete the statement/expression; parser-expecting-more contexts continue automatically. Formatter prefers delimiter-based continuation and omits unnecessary semicolons/backslashes when safe. Owner decision revised and confirmed: 2026-07-24.
- **D-364 — Empty statements are illegal: frozen.** One complete statement may end with one semicolon and one semicolon may separate same-line statements. The rule is uniform for CLI/package/module source; formatter preserves/moves no shebang except keeping an existing one first. Owner decision: 2026-07-24.
- **D-367 — Source encoding is strict UTF-8: frozen.** Source accepts UTF-8 only, optionally one UTF-8 BOM at file start. UTF-16/local encodings/other BOMs and malformed UTF-8 are compile errors with byte offset and source position; lexer never substitutes U+FFFD. LF, CRLF, and isolated CR are recognized as physical newlines; formatter emits LF canonically. Owner decision: 2026-07-24.
- **D-368 — String literals have escaped/interpolated, non-interpolated, raw, and multiline forms: frozen.** `"..."` processes escapes and `${expr}` interpolation; `'...'` processes escapes but never interpolation. Prefix `r` on either quote form disables escapes and interpolation. Triple-double/triple-single quotes are multiline counterparts inheriting interpolation/no-interpolation respectively, and may also be raw-prefixed. Exact escapes, delimiter inclusion, indentation, and interpolation conversion remain separate. Owner decision: 2026-07-24.
- **D-369 — Escaped Strings use a strict escape set and Unicode-scalar validation: frozen.** Supported escapes are `\\`, `\"`, `\'`, `\n`, `\r`, `\t`, `\0`, `\b`, `\f`, `\v`, `\xNN` (exactly two hex digits), and `\u{H...}` (1-6 hex digits). Unicode escape values must be valid scalar values, excluding surrogates and values above U+10FFFF. Unknown/incomplete escapes are compile errors. Exact `\x` byte-versus-Unicode semantics remain separate. Owner decision: 2026-07-24.
- **D-370 — String always contains valid Unicode scalars; `\xNN` is a scalar escape: frozen.** Strings never contain invalid UTF-8 or surrogate code points. `\xNN` denotes Unicode scalar U+0000..U+00FF (e.g. `\xFF` is U+00FF encoded as UTF-8 C3 BF), not a raw byte injection. `\u{}` covers other scalars. Arbitrary binary data belongs in ByteArray/bytes APIs. Index/length units remain separate. Owner decision: 2026-07-24.
- **D-371 — Core String indexing/length use Unicode scalar units: frozen.** `length`, integer `[]`, and ordinary slicing count Unicode scalar values/code points and never split UTF-8 sequences. Explicit `byte_length`/`bytes` expose encoded bytes, while `graphemes`/grapheme APIs expose Unicode grapheme clusters with their own versioned behavior. Units are never mixed implicitly. Complexity/caching and boundary errors remain separate. Owner decision: 2026-07-24.
- **D-372 — Strings are immutable identity-less values: frozen.** String equality is value-based over its Unicode scalar sequence and `same?` raises `IdentityError`. Concatenation, replacement, slicing, case conversion, and edits produce new String values. Runtime may intern, rope, share substrings, use small-string/copy-on-write representations, or fold constants without observable identity/storage. String Class behavior remains open but existing contents cannot mutate. Normalization/case equality remains separate. Owner decision: 2026-07-24.
- **D-373 — String equality/hash use exact scalar sequence and case: frozen.** Built-in String equality compares exact Unicode scalar sequence, case-sensitively, with no implicit NFC/NFD/NFKC/NFKD normalization, case folding, locale, or grapheme equivalence. Canonically equivalent source sequences may be unequal. Explicit `normalize(form)`, `casefold`, and locale-aware APIs produce values for alternate comparisons. Hash must match exact equality. Algorithm remains separate. Owner decision: 2026-07-24.
- **D-374 — String public hash is stable domain-separated BLAKE3: frozen.** Use exact ASCII derive-key context `Iris Language v1 stable string hash`; input shortest ULEB128 of exact UTF-8 byte length plus exact valid UTF-8 bytes. Digest reduces by first-eight-bytes little-endian. No normalization/case folding occurs. String and Symbol domains remain distinct; container bucket mixing remains runtime-secret. Owner decision: 2026-07-24.
- **D-375 — String interpolation uses dynamic `to_string() -> String`: frozen.** Each `${expr}` evaluates expr once. If already String, append directly; otherwise send ordinary `to_string` dynamically. Missing lookup may use `method_missing`; normal result must be String or raises `TypeContractError`. Exceptions propagate and abort interpolation. Nil's standard representation is `"nil"`. Concatenation may be optimized without changing evaluation order. Default Object representation remains separate. Owner decision: 2026-07-24.
- **D-376 — Default `Object#to_string` is stable Class-name text: frozen.** Root implementation returns `<fully.qualified.ClassName>` using nominal Class identity. It omits memory address, identity hash, runtime ID, revision number, properties, and ivars, so it is stable across runs for stable package/type identity. Classes may dynamically replace it subject to normal Method rules. Detailed debug representation belongs to `inspect`. Owner decision: 2026-07-24.
- **D-377 — Default `Object#inspect` is privacy-safe and dynamically replaceable: frozen.** Root `inspect() -> String` delegates to current `to_string()` and does not enumerate ivars/properties, expose identity/address/revision, or bypass ReflectionPolicy. Classes may override it normally. Debuggers/profilers use separate structured permission-checked reflection rather than trusting/depending on inspect. Standard value/container Classes may provide richer safe inspect forms. Owner decision: 2026-07-24.
- **D-378 — String display/debug representations are distinct: frozen.** `String#to_string` returns the String value itself. `String#inspect` returns a reparsable double-quoted escaped literal, escaping controls/backslash/quote/interpolation opener as needed while preserving printable Unicode; parsing it recreates an exact scalar-equal String and no interpolation executes. Interpolation of a String adds no quotes. Owner decision: 2026-07-24.
- **D-379 — Triple-quoted multiline Strings use strict closing-indent stripping: frozen.** If opening triple quote is immediately followed by newline, that newline is omitted. If closing delimiter is alone on its line, the immediately preceding final newline is omitted and the exact whitespace prefix before the closing delimiter is removed from every non-empty content line. Any non-empty line lacking that exact prefix is a compile error. Empty lines normalize accordingly. Inline triple-quoted forms perform no automatic indentation stripping. Tab/space prefix matching remains separate. Owner decision: 2026-07-24.
- **D-380 — Multiline indent prefixes match exact whitespace characters: frozen.** Closing-indent stripping compares raw prefix code points/characters exactly; tabs are not expanded to columns and never equal spaces. Each non-empty line must begin with the same tab/space sequence as the closing delimiter prefix. Formatter preserves that prefix composition and literal content. Semantics never depend on editor tab width. Owner decision: 2026-07-24.
- **D-381 — Raw Strings use Rust-style variable `#` fences: frozen.** Raw literals may place 0-255 `#` characters between `r` and the quote delimiter, with the exact same count after the closing delimiter, for single/double/triple quote forms (e.g. `r#"..."#`, `r#"""..."""#`). Only quote sequence plus matching fence closes; content performs no escapes or interpolation. Fence-count mismatch/overflow is lexical error. Raw multiline indentation remains separate. Owner decision: 2026-07-24.
- **D-382 — Raw triple Strings still use strict closing-indent stripping: frozen.** Raw disables escapes/interpolation only. Triple-quoted raw forms apply D-379/D-380 first/final newline and exact-prefix dedent; `#` fences do not affect indentation. Exact whitespace preservation requires an inline/non-standalone-closing form rather than a second raw mode. Owner decision: 2026-07-24.
- **D-383 — Interpolation accepts full expressions without format mini-language: frozen.** `${...}` in interpolated double/triple Strings contains a full expression grammar with balanced nesting, nested Strings/interpolations, and normal evaluation. In escaped forms `\${` emits literal `${`; raw/single-quoted forms never interpolate. V1 has no `${expr:format}` syntax; formatting uses explicit Methods before `to_string`. Evaluation/partial-result behavior remains separate. Owner decision: 2026-07-24.
- **D-384 — Interpolation evaluates left-to-right and fails without a partial value: frozen.** Each segment expression and its required `to_string` completes before the next interpolation. On any failure, later segments do not run, the exception propagates, prior side effects remain, and no partially built String is returned/observable. Runtime may builder/fuse/preallocate only while preserving ordering and failure semantics. Owner decision: 2026-07-24.
- **D-385 — String `+` converts via `to_string`; adjacent literals concatenate: frozen.** Standard `String#+(other: Object) -> String` appends other directly if String, otherwise invokes its dynamic `to_string() -> String`, with normal errors/order; the Method remains replaceable. Lexically adjacent String literal segments concatenate at compile time/one expression without `+`, preserving each segment's own escape/raw/interpolation semantics and left-to-right interpolation effects. Cross-family adjacency remains separate. Owner decision: 2026-07-24.
- **D-386 — Adjacent String segments may mix literal families: frozen.** Double/single/raw/triple String literal segments may concatenate adjacently. Each parses under its own escape/interpolation/fence/dedent rules, then contributes in source order. Only String literal segments participate; Symbols, ByteArrays, and arbitrary expressions do not implicitly join. Whitespace/comments may separate segments. Newline adjacency remains separate under statement termination. Owner decision: 2026-07-24.
- **D-387 — Bare newline ends a completed adjacent-String expression; continued contexts may join: frozen.** A complete String segment followed by an ordinary terminating newline does not concatenate with a String on the next statement. Cross-line adjacency is allowed inside automatic continuation contexts or through D-388 explicit backslash continuation. No indentation-based inference applies. Owner decision: 2026-07-24.
- **D-388 — Explicit line continuation uses a strict physical-line-end backslash: frozen.** A backslash must be immediately followed by LF, CRLF, or CR; lexer removes both. No spaces, comments, or tokens may intervene, otherwise it is a lexical error outside a literal. It applies to any expression/statement, including `"a" \` newline `"b"`. Automatic delimiter/incomplete-grammar continuation remains available without backslash. Owner decision: 2026-07-24.
- **D-389 — String scalar indexing supports negative indices and nil bounds failure: frozen.** `str[i]` indexes Unicode scalars and returns a one-scalar String. Nonnegative indices count from start; negative from end (`-1` last). Out-of-range returns nil without mutation/structural side effect, so static type is `String?`. V1 introduces no separate Character type for this operation. Slice semantics remain separate. Owner decision: 2026-07-24.
- **D-390 — String Range slicing clamps and always returns String: frozen.** `str[range]` slices Unicode scalar positions. Negative endpoints resolve from end; effective boundaries then clamp to `[0, length]`. Range open/closed endpoints determine included scalar boundaries. Empty or start-after-end ranges return empty String rather than nil/error/reverse. Static result is String. Step/reverse slicing remains separate. Owner decision: 2026-07-24.
- **D-391 — V1 String slicing accepts unit-forward Ranges only: frozen.** String `[]` slice has no step/stride or reverse-range semantics. It accepts only unit-forward Range behavior; unsupported stepped/reverse forms are statically rejected when known or raise `ArgumentError` dynamically. Start-after-end still yields empty String. Use `reverse()` or iterator transformations for other traversal. Owner decision: 2026-07-24.
- **D-392 — Standard String has no index assignment; mutable text uses `MutableString`: frozen.** Immutable identity-less String defines no standard `[]=` and cannot mutate in place. Functional APIs such as `replace_range` return new Strings. Efficient accumulation/editing uses separate mutable identity-bearing `MutableString` (future TextBuffer optional), which owns mutation/alias/concurrency semantics and converts to immutable String. The former design name `StringBuilder` is not the formal standard type. User-added String `[]=` cannot mutate intrinsic String scalar content. Owner decision revised and confirmed: 2026-07-24.
- **D-393 — `MutableString#to_string` returns an immutable snapshot: frozen.** Each call returns immutable String content at that moment; later MutableString mutation never alters prior snapshots. Runtime may share rope/buffer storage with copy-on-write/immutable segments, but sharing is unobservable and eager deep copy is not required. `to_string` does not clear/freeze/mutate the MutableString. Owner decision revised and confirmed: 2026-07-24.
- **D-394 — MutableString uses scalar indexing and mutable slicing: frozen.** `value[i]` uses String's Unicode-scalar/negative-index/nil-out-of-range semantics. `value[i]=replacement` requires a one-scalar String, raises `IndexError` out of range, mutates in place, and returns Nil. `value[range]=replacement` uses clamped unit-forward scalar Range semantics, accepts any String, may change length, mutates in place, and returns Nil. Aliases observe mutation; prior String snapshots remain unchanged. Owner decision: 2026-07-24.
- **D-395 — `m` literals construct fresh MutableString values: frozen.** Prefix `m` applies to every String literal family: escaped/interpolated `m"..."`, escaped non-interpolated `m'...'`, multiline triple forms, and raw forms with fixed prefix order `mr#"..."#` / `mr#"""..."""#` and matching fences. Content parsing/interpolation/dedent follows the corresponding immutable String literal rules, then yields a new identity-bearing MutableString on every evaluation, even for identical text. Runtime may construct directly without an intermediate String. `rm...` is invalid. Owner decision: 2026-07-24.
- **D-396 — MutableString has content equality, identity, and no default Hash-key eligibility: frozen.** MutableString is mutable/identity-bearing; `same?` compares identity. Built-in `==` compares current exact Unicode scalar content and is cross-type equal to immutable String with identical content. Built-in `hash` raises `InvalidKeyError`, so it is not a Hash key by default. `to_string` returns immutable snapshot; `inspect` returns a reparsable escaped `m"..."` form. Equal/hash contract scope remains separate. Owner decision: 2026-07-24.
- **D-397 — Equal-implies-same-hash applies only when both values are hashable: frozen.** If `a == b` and both public hash calls succeed, results must match. Equality does not require an intentionally unhashable value to provide a hash. MutableString may equal String by content while MutableString hash raises `InvalidKeyError` and cannot be inserted as a key. User-added MutableString hashing must honor String-compatible equality and assumes mutation/rehash responsibility. Owner decision: 2026-07-24.
- **D-398 — MutableString separates allocating `+` from mutating `<<`/`append`: frozen.** Standard `MutableString#+(other: Object) -> MutableString` obtains text directly from String, snapshots MutableString content, or fully invokes other `to_string() -> String`, then returns a fresh MutableString identity without mutating receiver. Standard `MutableString#<<`/`append(other: Object) -> MutableString` use the same conversion but append in place and return receiver identity. Conversion completes before mutation; failure leaves receiver unchanged. Source text is snapshotted before mutation, making self/alias append deterministic. Owner decision revised and confirmed: 2026-07-24.
- **D-399 — MutableString `+=` rebinds to a fresh MutableString: frozen.** Under D-347, `target += other` reads target, calls `MutableString#+(Object)` including its `to_string` conversion, then writes the fresh MutableString back. For local/raw-ivar storage the result is that new value; for property/index targets the result is the setter result. Existing aliases to the old MutableString observe no append. Explicit `<<`/`append` is required for in-place mutation. Conversion failure prevents writeback. Owner decision revised and confirmed: 2026-07-24.
- **D-400 — MutableString append conversion is atomic with respect to receiver content: frozen.** `+`, `<<`, and `append` evaluate/convert the operand exactly once. Non-text `to_string` must return String or raises `TypeContractError`; exceptions propagate. `<<`/append mutate only after the complete source String is available, so conversion failure leaves the receiver content unchanged. If source is receiver or an alias to it, source content is snapshotted before append, e.g. `s << s` duplicates the original once. Allocation/resource failure during commit follows ordinary ResourceError and must not expose partial appended scalar content. Owner decision: 2026-07-24.
- **D-401 — MutableString `clear` and `replace` mutate atomically and return self: frozen.** `clear() -> MutableString` empties receiver in place and returns the same identity. `replace(other: Object) -> MutableString` evaluates/converts other through String/MutableString snapshot/`to_string` exactly once, then atomically replaces all content and returns self. Conversion/allocation failure leaves previous content unchanged and propagates the error. Prior immutable snapshots remain unchanged. Owner decision: 2026-07-24.
- **D-402 — Standard text transform naming uses non-bang copy and bang mutation: frozen.** String transforms such as `upcase/downcase/normalize` return new immutable Strings. MutableString non-bang counterparts return fresh MutableStrings without mutating receiver; `upcase!/downcase!/normalize!` mutate receiver atomically and return self. Failure exposes no partial transformed content. `!` remains a naming convention generally, but the standard library follows this rule. Owner decision: 2026-07-24.
- **D-403 — MutableString is not thread-safe but remains memory-safe: frozen.** Concurrent unsynchronized read/write or write/write is unsupported at the logical API level and may raise `ConcurrentMutationError`/be detected by runtime, but must never cause undefined behavior, memory corruption, invalid Unicode, or partial committed content. Each public mutation publishes complete old-or-new content atomically to correctly synchronized observers. Users coordinate via Mutex/actors/higher-level concurrency. Iterator interaction remains separate. Owner decision: 2026-07-24.
- **D-404 — MutableString iterators fail fast on any content mutation: frozen.** Scalar/grapheme iterators capture a content version. Append, clear, replace, index/range assignment, bang transforms, or any content change increments it; next advance on mismatch raises `ConcurrentModificationError`, even if scalar length is unchanged. No remove/replace-current or weak traversal exists. Stable traversal uses an explicit immutable `to_string` snapshot. Owner decision: 2026-07-24.
- **D-405 — Default String/MutableString iteration yields scalar Strings: frozen.** `for x in text` and default iterator produce one-scalar immutable String values in scalar order, matching `length`/`[]`. Index pairs require `each_with_index`/enumerate; graphemes/code points/bytes use explicit APIs. MutableString iterator follows fail-fast D-404 and still yields immutable scalar values. Owner decision: 2026-07-24.
- **D-406 — `bytes` and `graphemes` expose lazy Iterable views: frozen.** String/MutableString `bytes` and `graphemes` do not eagerly allocate Arrays. `bytes` yields Integer 0..255 for exact UTF-8 encoding; `graphemes` yields immutable String clusters. Consumers obtain iterators/pipelines or explicitly materialize via `to_array()`. MutableString views capture content version and fail-fast under D-404. Unicode grapheme-version binding remains separate. Owner decision: 2026-07-24.
- **D-407 — Iris language major fixes the Unicode data version: frozen.** Iris language major version 1 uses Unicode 17.0.0 data for identifier XID tables, grapheme segmentation, normalization, Unicode properties, case mapping, and casefold. OS/runtime library/package/Host configuration cannot change default results. Changing default Unicode data is language-major breaking unless exposed through a separately explicit versioned Unicode API. Owner decision revised and confirmed: 2026-07-27.
- **D-408 — Binary data uses immutable `Bytes` and mutable `ByteArray`: frozen.** `Bytes` is immutable/identity-less and may be stably hashed; `ByteArray` is mutable/identity-bearing and default-unhashable. Both contain bytes 0..255, support negative index reads/out-of-range nil; ByteArray writes range-check and out-of-range raise `IndexError`. `b"..."` / `br#"..."#` (and multiline counterparts) produce Bytes; `mb"..."` / `mbr#"..."#` produce a fresh ByteArray identity. Prefix order is mutable `m`, bytes `b`, optional raw `r`, fence/quotes; alternatives are invalid. Non-ASCII source text contributes UTF-8 bytes; escaped byte literal `\xNN` injects one raw byte. `ByteArray#to_bytes` returns immutable snapshot; `Bytes#to_byte_array` returns mutable copy with COW sharing permitted. Equality/hash details remain separate. Owner decision revised and confirmed: 2026-07-24.
- **D-409 — Bytes and ByteArray compare by byte content across types: frozen.** Built-in `==` compares exact current byte sequence and permits Bytes/ByteArray cross-type equality. Bytes is identity-less (`same?` error) and hashable; ByteArray is identity-bearing (`same?` identity) and built-in-unhashable. Equal-implies-same-hash applies only when both hash calls succeed. User-added ByteArray hashing must match Bytes equality and assumes mutation/rehash risk. Owner decision: 2026-07-24.
- **D-410 — Bytes public hash is stable domain-separated BLAKE3: frozen.** Use exact ASCII derive-key context `Iris Language v1 stable bytes hash`; input is shortest ULEB128 byte length plus exact byte content. Digest reduces to first eight bytes little-endian Integer. Domain is distinct from String/Symbol even when byte sequences coincide. Hash containers may apply runtime-secret mixing. Owner decision: 2026-07-24.
- **D-411 — Bytes/ByteArray slicing returns same mutability family; ByteArray slice write is atomic: frozen.** Bytes Range slice returns Bytes; ByteArray Range slice returns an independent ByteArray snapshot identity (COW allowed). Both use negative endpoints, clamped unit-forward boundaries, and empty result for empty/reverse. `ByteArray[range]=replacement` accepts Bytes|ByteArray, snapshots aliasing source, may change length, atomically replaces, returns Nil, and exposes no partial content. Owner decision: 2026-07-24.
- **D-412 — Binary concatenation mirrors mutability without text coercion: frozen.** `Bytes + (Bytes|ByteArray) -> Bytes` allocates immutable result. `ByteArray + (Bytes|ByteArray) -> ByteArray` allocates fresh mutable identity without changing receiver. `ByteArray <<`/`append` mutate in place, snapshot aliases, return self, and commit atomically; `+=` uses `+` then rebinds. String/Object are never implicitly encoded or `to_string`-converted for binary operations. Owner decision: 2026-07-24.
- **D-413 — Text/binary convenience conversion is strict UTF-8: frozen.** `String#to_bytes` and `MutableString#to_bytes` return immutable UTF-8 Bytes snapshots. `Bytes#to_string` strictly decodes UTF-8; invalid sequences raise `EncodingError`. ByteArray snapshots then decodes equivalently. Lossy replacement/ignore behavior requires explicit decoding API/options such as `decode_utf8(errors: :replace)` and is never default. General encodings remain separate. Owner decision: 2026-07-24.
- **D-414 — Core UTF-8 plus standard-library Encoding API: frozen.** Language core guarantees UTF-8 source/text-binary convenience conversion only. Standard library exposes explicit Encoding objects (at least UTF-8, UTF-16LE/BE, Latin-1) with strict default errors and explicit replace/ignore options; packages may add encodings. String remains Unicode scalar content and never retains source encoding. OS locale/code page is never implicitly selected. Owner decision: 2026-07-24.
- **D-415 — Iris callable runtime kinds are Method, BoundMethod, and Closure only: frozen.** Iris has no separate Function runtime kind. Every named `fun` defines a Method on its lexical owner. Top-level/module-level `fun` defines a Method on that executable module's unique identity-bearing `main` receiver. BoundMethod captures a receiver plus Method; Closure is anonymous lexical code/capture. BoundMethod and Closure share ordinary callable typing after binding, while unbound Method remains reflective and requires explicit receiver/binding. Owner decision: 2026-07-24.
- **D-416 — Each executable module has one private-by-default `main` receiver: frozen.** All source files in one module share its unique `main` object. Top-level `fun f` creates a private Method on main, and top-level `f()` is a privileged implicit send to main. Importers cannot call private top-level helpers. `export fun` explicitly publishes a public Method through the module object/API. Runtime-wide or per-file main objects do not exist. Owner decision: 2026-07-24.
- **D-417 — Method and Closure declaration syntax is fixed: frozen.** Named Methods use `fun name(parameters) -> Return { body }`; placement determines instance/Module/main ownership, while Class Methods use `class fun`. Closure/trailing-block syntax is `{ |parameters| -> ReturnType body }`; multiline body starts after header newline and single-line uses semicolon (`{ |x: String| -> Nil; print(x) }`). Empty parameters use `{ || -> R ... }` or formatter-standardized unambiguous shorthand. Closure return annotation may be omitted when expected callable context uniquely supplies a closed type. Method annotation omissions follow D-452 and become `Dynamic<Object>`. No second arrow/lambda syntax exists. Owner decision revised and confirmed: 2026-07-24.
- **D-418 — Parameter categories and order are fixed: frozen.** Declaration order is required positional; optional positional (`x: T = expr`); at most one positional rest (`*args: T`); required keyword-only (`key name: T`); optional keyword-only (`key name: T = expr`); at most one keyword rest (`**kwargs: V`); and trailing-block binding last (`&block: (P...) -> R`, optionally `= nil`). Calls spell keywords `name: value`. Iris has no positional-only/keyword-only separator tokens and no overloads. Owner decision: 2026-07-24.
- **D-419 — Parameter defaults are per-call and bindings immutable: frozen.** Defaults evaluate on each invocation left-to-right and may reference receiver, module scope, and earlier parameters but not later ones. Parameter bindings are immutable. Rest arguments form a fresh `Array<T>` and keyword rest a fresh `Hash<Symbol,V>`; bindings cannot be rebound but container values retain ordinary mutability. Omitted optional block binds nil. Arity/category/Contract failures raise `ArgumentError`/`TypeError` after selector resolution. Owner decision revised and confirmed: 2026-07-24.
- **D-420 — Closures capture lexical bindings by reference and capture self: frozen.** Closures capture binding cells, not value snapshots. Immutable captures are read-only; explicitly mutable bindings are shared so outer/Closure updates agree. Closure captures its current receiver and receiver-name ivar access; receiver is not rebindable. Named Methods never capture dynamic body locals; explicit Closure installation is required. Owner decision: 2026-07-24.
- **D-421 — Closure control flow is local and cannot cross Closure boundaries: frozen.** `return` inside a Closure ends only that Closure invocation. `break`/`continue` cannot target loops outside a Closure call boundary and are compile errors in that use. V1 has no Proc/lambda split, nonlocal-return Closure, or LocalJumpError model. Owner decision: 2026-07-24.
- **D-422 — Method and Closure bodies return their last expression: frozen.** Normal fallthrough returns the final expression; empty body returns nil. `return expr` exits early with expr and bare `return` returns nil. Every normal exit is checked against any explicit return Contract. Omitted annotation meaning belongs to the global type-default decision. Owner decision: 2026-07-24.
- **D-423 — Trailing blocks use a dedicated `&block` channel: frozen.** A trailing Closure is not a final positional argument and binds only to the final declared `&block` parameter. Existing Closure may be passed with `&closure`. A call has at most one block. Unexpected block raises `ArgumentError`; optional omission binds nil. The block's type is ordinary `(P...) -> R`; `&` marks call channel/binding. Owner decision: 2026-07-24.
- **D-424 — Ordinary calls require parentheses: frozen.** Ordinary zero/nonzero positional/keyword calls use parentheses. Only property getter syntax omits them. A trailing block follows a completed call, including `method() { ... }`. This avoids ambiguity with control blocks, Hashes, named infix messages, and newline rules. Owner decision: 2026-07-24.
- **D-425 — Closure and BoundMethod share callable function types: frozen.** Bound callable types use `(P1, P2, ...) -> R`. Closure and compatible BoundMethod values assign using parameter contravariance, return covariance, and arity/mode/Contract compatibility. Unbound Methods use a distinct reified `Method<Self, (P...) -> R>`-style type and require explicit binding/receiver. Trailing block types are ordinary function types. Owner decision: 2026-07-24.
- **D-426 — Local bindings use `let` immutable and `mut` mutable declarations: frozen.** `let name[: T] = expr` declares immutable; `mut name[: T] = expr` or typed deferred `mut name: T` declares mutable. Bare `name = expr` only assigns an existing mutable binding and never implicitly declares, preventing typo-created locals. Parameters/catch bindings/iteration bindings default immutable. Owner decision: 2026-07-24.
- **D-427 — Binding initialization and inferred types are definite and fixed: frozen.** `let` requires initialization. `mut` may defer initialization only with explicit type and cannot be read before definite assignment; untyped/uninitialized mut is invalid. Annotation is mandatory runtime/static contract. Without annotation, initializer yields a precise local inferred type that remains fixed for later assignments and never auto-widens; use explicit union/Dynamic when needed. Owner decision: 2026-07-24.
- **D-428 — Shadowing is nested-only and binding identity is lexical: frozen.** Same lexical scope cannot redeclare a name. Nested scopes may shadow, with default lint warning. A new declaration's initializer resolves the outer binding because the new binding enters scope only after initialization. Closures capture the specific binding cell; later nested shadowing does not retarget capture. Owner decision: 2026-07-24.
- **D-429 — Ruby-style state sigils remain but declarations are explicit: frozen.** `@name` is current-receiver raw dynamic ivar under D-309; `@@name` is a hierarchy-shared Class variable requiring explicit origin declaration; `$name` is a package-qualified runtime-global requiring explicit declaration. Sigils never create bindings merely by read/assignment except ordinary `@` dynamic slot creation governed by `instance_state`. Typed/property/Class-state alternatives remain available. Owner decision: 2026-07-24.
- **D-430 — Class variables are one declared ancestor slot with no shadowing: frozen.** `class let @@x: T = expr` or `class mut @@x: T = expr` declares a slot owned by one logical Class and shared through its subclass hierarchy. Descendants resolve/read/write the nearest/unique declared ancestral slot but cannot redeclare/shadow the same `@@x`. Missing declaration is static error or dynamic access error. Handles belong to one runtime and cannot be mixed or assumed numerically stable across runtimes/restarts. Owner decision: 2026-07-24.
- **D-493 — V1 Iris ABI calls are runtime-thread-affine; external threads post only: frozen.** All APIs touching Iris handles/heap/Class/meta/scheduler run on the owning runtime event-loop thread. Native libraries may use worker threads for external work but cannot dereference/use Iris handles there. A thread-safe post/message API schedules data/completion onto runtime thread. Violations return thread-affinity error and never race the managed heap. Future no-GIL ABI requires a later ABI version. Owner decision: 2026-07-24.
- **D-494 — Native errors use status plus ExceptionContext handles: frozen.** C ABI functions return IrisStatus and expose error/result through out handles, preserving raised Iris value and ExceptionContext graph. Native callbacks may create/raise Iris errors through ABI. Rust panic/C++ exception never crosses C ABI; wrappers catch/translate to NativeError where safe, while unrecoverable memory corruption may abort. Iris unwinding never longjmps across native frames. String-only error channels are insufficient. Owner decision: 2026-07-24.
- **D-495 — Native static APIs use compiler metadata plus verified runtime binding: frozen.** Native packages ship Iris-readable compile-time metadata for Classes/Contracts/Methods/properties/generics/MetaCapabilities and package identity, with digest/ABI requirements. Compiler imports it as static API. Runtime load verifies matching metadata/artifacts then binds implementations. Additional runtime-only registration creates dynamic-only members through open transactions/capabilities and never expands already compiled static APIs. Owner decision: 2026-07-24.
- **D-496 — Native payloads use runtime-owned descriptors and explicit Closeable resources: frozen.** Native-backed Classes register validated opaque payload descriptors/external handles with size/alignment/construct/drop/trace as applicable. Runtime controls allocation/lifetime; trace only reports managed handles/roots and drop runs at GC-safe context, cannot raise into Iris, and is final memory cleanup. Files/sockets/GPU/etc use idempotent Closeable for deterministic release; GC timing is not resource management. Raw extension-owned object-pointer conventions are prohibited. Owner decision: 2026-07-24.
- **D-497 — Native async completion uses one-shot tokens and runtime post queue: frozen.** Native async Method obtains runtime-owned `Task<T>` completion source/opaque token. Worker threads perform external work and use only thread-safe post API with copied/owned data/status; runtime thread converts to Iris values/handles and completes Task exactly once. Duplicate completion errors; posts after runtime shutdown return closed status. Workers never resolve Task or touch heap directly. Owner decision: 2026-07-24.
- **D-498 — C ABI evolves through negotiated versioned function tables: frozen.** Runtime/extension negotiate required ABI major/minor/features and size-tagged structures/function tables. Major mismatch rejects load; compatible minors append fields/functions and use struct sizes/feature tests without reinterpreting old layouts. Symbol/Type/handle IDs are runtime-local unless specified. Rust wrapper crate pins ABI versions and supplies RAII handles, checked runtime ownership, panic barriers, and safe callback abstractions. Owner decision: 2026-07-24.
- **D-499 — `FFI` is the sole script-level external binary integration path: frozen.** Ordinary Iris scripts cannot directly use Host ABI, extension function tables, raw runtime handles, loader internals, or arbitrary native symbol APIs. All script-originated binary calls use the standard FFI subsystem under manifest/Host grants (at least `ffi.load`/`ffi.call` scopes). Runtime/package loader alone uses formal extension ABI. V1 FFI supports stable C ABI only; Rust/C++/other languages export C-compatible wrappers and representations. Owner decision: 2026-07-24.
- **D-500 — `FFI.open` returns an identity-bearing `FFI::Library`: frozen.** `FFI` is the standard namespace/service Class; `FFI.open(path, declarations: ...) -> FFI::Library` loads one authorized dynamic library. Library owns/pins native library lifetime, bound functions/callbacks/pointers, close state, and is idempotent Closeable. Multiple libraries are independent. Scripts call bound symbols as Methods on the Library object. Owner decision: 2026-07-24.
- **D-501 — FFI calls require explicit sidecar or programmatic signatures; no raw unsafe invoke: frozen.** `FFI.open(..., declarations: "lib.ffi")` loads verified declarations, or `library.bind(:symbol, (CType...) -> CType, options)` binds explicitly. Bound symbols become Library dynamic-only Methods with declared C calling convention, widths, encoding, ownership/lifetime, nullability, error/result, and callback metadata. Unbound symbols cannot be invoked and v1 exposes no signature-less `unsafe_call`. Sidecar and programmatic declarations have equivalent validation and Reflection metadata. Owner decision: 2026-07-24.
- **D-502 — Serialization is explicit and Contract-driven, never automatic object dumping: frozen.** Language core does not reflectively serialize arbitrary objects/ivars. Standard library supports JSON-compatible values and an Iris binary value format for primitives/immutable values/collections plus Classes explicitly participating through a `Serializable` Contract/representation. Class/Module/Method/Closure/Task/FFI pointers/native resources are not automatically serializable. ReflectionPolicy/private data is never bypassed. Owner decision: 2026-07-24.
- **D-503 — V1 ships a separately specified versioned `IrisValue` binary format: frozen.** Format has magic/version and compatibility metadata (including relevant language/Unicode/hash/schema versions), strict bounded lengths/counts, full input validation, and no trusted allocation from unvalidated sizes. It represents supported primitives, arbitrary Integer, Float widths/bits, String/Symbol/Bytes, Tuple/Array/Hash, and explicit Serializable representations. Exact byte/tag schema belongs to a dedicated format specification and is not further micro-designed in the language spec. Owner decision: 2026-07-24.
- **D-504 — Core versus standard-package boundary is frozen: frozen.** V1 core/stable runtime packages include core object/type/Contract/reflection, collections/text/bytes/Regex, Async Task/event loop, IO/File/Path, Encoding/Unicode, JSON/IrisValue, FFI, Package, diagnostics/testing. HTTP, general networking protocols, cryptography APIs, databases, GUI, and similar facilities ship as separately versioned official standard packages, not language core ABI. Internal BLAKE3 use does not imply a public core crypto suite. Owner decision: 2026-07-24.
- **D-505 — Regex is an immutable identity-less core value with literals and explicit match operators: frozen.** `/pattern/flags` creates Regex and supports `${expr}` interpolation by `to_string` then default Regex escaping; `r/.../flags` is raw/non-interpolated (fence details follow raw literal conventions). `text =~ regex -> Match?` returns immutable Match or nil; `text !~ regex -> Bool`. Regex equality/hash are by canonical pattern+flags and stable. Owner decision: 2026-07-24.
- **D-506 — Core Regex uses a fixed Unicode-aware safe subset: frozen.** V1 specifies a deterministic linear-time-oriented engine language comparable to Rust-regex capabilities, excluding backreferences, lookbehind, and constructs requiring unbounded catastrophic backtracking. Flags are fixed/documented (`i`, `m`, `s`, `x`, Unicode behavior default/major-version-bound). Match is immutable and exposes full match, scalar/byte ranges, numbered/named captures without global match variables. Advanced PCRE-style engines belong in separate standard packages and use distinct types. Owner decision: 2026-07-24.
- **D-507 — Operator precedence is fully ordered: frozen.** High-to-low: primary/call/index/property/Contract-view `..`; exponent `**`; unary `+ - ~ !` with the already frozen exponent-vs-negation grammar; multiplicative `* /`; additive `+ -`; shifts `<< >>`; bitwise `&`; `^`; `|`; Range `..= ..<`; relational/type/regex `< <= > >= <=> =~ !~ is as as?`; equality `== !=`; named infix Method; `&&`; `||`; assignment/compound/logical assignment. D-022 named-infix placement and D-033 exponent rules remain authoritative. Owner decision: 2026-07-24.
- **D-508 — Associativity and non-chainable operators are fixed: frozen.** `**` and assignment families are right-associative; ordinary binary arithmetic/bitwise/logical/named-infix are left-associative as applicable. Range, relational, equality, `<=>`, regex match, `is`, `as`, and `as?` are non-associative and cannot chain (`a<b<c`, `a==b==c`, chained Range/casts require parentheses/`&&`). Call/member/index chains associate left through primary parsing. Owner decision: 2026-07-24.
- **D-509 — V1 reserved keyword inventory is closed: frozen.** Reserved words are: `class module contract open extends for mixin where meta deny public protected private override impl property shared key async await fun let mut const global import from as export type if else while in break continue match try catch finally raise return is nil true false self super`. Legacy/unused `and or not repeat switch when groan order serve ignore defer implements satisfies interface goto retry redo static alias undef` are not keywords/reserved solely for history; alias/undef/remove functionality uses Method APIs. `new`, `using`, `close`, and `method_missing` remain ordinary Method names. Owner decision: 2026-07-24.
- **D-510 — Lexer/parser use contextual longest-match for conflicting tokens: frozen.** Lexer prefers `..=`/`..<` over `..`, `!=` over `!`+`=`, and other longest fixed operators. Parser recognizes `..identifier` as Contract-view call in primary/postfix context, `::` as qualified name/declaration slot, `=>` as match arm, `%{` as Hash literal opener, and `${` only inside interpolated String. `as?` parses as cast operator; method `?`/`!` suffix and property setter selectors (including `name!=`) use declaration/property contexts without changing expression token meanings. Owner decision: 2026-07-24.
- **D-511 — Decorators are constrained typed declaration transformers: frozen.** Syntax `@decorator(args)` precedes Class, Module, Contract, Method, or property declarations. A decorator transforms the declaration candidate/metadata rather than replacing its nominal identity or kind. Multiple decorators execute in written top-to-bottom order. Result remains the same typed declaration category. V1 decorators are neither unrestricted Python replacement functions nor AST macros. Owner decision: 2026-07-24.
- **D-512 — Declarative decorators use deterministic static plans plus runtime transaction application: frozen.** Compiler/linker resolves each directly imported decorator and executes/validates a pure deterministic static planning phase that may contribute compiler-visible metadata/API transformations. Runtime construction/open applies its runtime transform inside the declaration's candidate transaction. Runtime-dependent/conditional programmatic decoration is dynamic-only and cannot alter already compiled static API. Static plan cannot depend on IO, time, random, ambient runtime state, or untracked environment. Owner decision: 2026-07-24.
- **D-513 — Decorators obey target static spine and MetaCapabilities without privilege escalation: frozen.** Decorators carry no inherent structural authority. Metadata attachment and compatible body wrapping use declared operation requirements (`method_body`, `property_body`, etc.); generated/removal changes require corresponding set/shape/state capabilities. They cannot change declaration kind/nominal identity, immutable superclass bound, Contract set/requirements, generic arity/invariance, package identity, or other forbidden static-spine facts. Contract decorators cannot hide/add required obligations outside explicit Contract source/static API. Target policy and caller/decorator package permissions all remain enforced. Owner decision: 2026-07-24.
- **D-514 — Decorator Contracts, failure, replay, and reflection are fixed: frozen.** Built-in typed generic Decorator Contracts receive immutable declaration metadata plus a controlled transform context and return same-kind candidate transformations. Static phase is pure/deterministic; runtime phase is synchronous/non-awaiting and may execute code, but external side effects are not rollbackable and remain author responsibility. Origin/open/hot-upgrade rebuilds reapply declaration decorators in source order to new candidates; any transform/validation failure aborts the whole transaction. Reflection exposes ordered decorator identity, arguments, package/source, phases, and permission-filtered generated diff. Owner decision: 2026-07-24.
- **D-300 — Property set and accessor implementation are separately controllable: frozen.** `property_set` controls adding/removing/changing property/getter/setter slots and contracts; `property_body` controls compatible getter/setter implementation replacement. Stored instance property set changes additionally need `shape`; class/shared property slot changes additionally need class-state capability. This permits immutable property API with hotfixable accessors without special bypasses. Owner decision: 2026-07-24.
- **D-299 — Method set and implementation replacement are separately controllable: frozen.** `method_set` and `method_body` are orthogonal. A Class/Contract/Module may deny API/member-set evolution while allowing compatible bug-fix/hot-upgrade body replacement, or deny body replacement while permitting other authorized member-set operations. Contract/static signature compatibility remains mandatory regardless of capability. No privileged “hotfix” bypass exists; permission follows these normal capabilities. Owner decision: 2026-07-24.
- **D-294 — Meta denies accumulate monotonically through superclass inheritance: frozen.** A Class's effective capabilities are language/runtime defaults minus every deny inherited from its superclass chain minus its own origin denies. A subclass may further narrow but cannot re-enable a capability denied by an ancestor, preventing policy bypass and protecting inherited layout/native/static invariants. Reflection exposes local denies, inherited denies with origin, and effective set. Runtime-superclass revision interaction remains separate. Owner decision: 2026-07-24.
- **D-295 — Effective capabilities include static and runtime superclass-chain denies: frozen.** A Class revision's effective MetaCapabilities subtract local origin denies, immutable declared-superclass-chain denies, and every deny from its current runtime-superclass/MRO Class chain. Runtime ancestry may further narrow but can never restore static-chain capabilities. Candidate validation computes the full set before applying/committing operations; operations losing authorization cause atomic failure. Reflection exposes local/static/runtime deny origins and final set. Owner decision: 2026-07-24.
- **D-296 — Module `meta deny` propagates through composition: frozen.** A Module may declare immutable `meta deny` restrictions in its origin header. Any static mixin or dynamic include adds those denies, with Module identity as policy origin, to the host Class revision's effective MetaCapabilities. Removing the Module removes only that Module-sourced restriction; static superclass/local/other Module denies remain, so capabilities restore only when no remaining source denies them. Composition/removal recomputes policy transactionally before other operations/commit. Module open cannot alter its static deny policy. Owner decision: 2026-07-24.
- **D-297 — Contracts may require immutable meta denies: frozen.** A Contract may declare `meta deny` requirements as part of its static promise. Any Class using header `for Contract` must have an effective policy at least as restrictive; conformance permanently absorbs those denies into the Class static spine and they cannot disappear through runtime superclass/Module changes. Contract multiple inheritance unions deny requirements. Contracts never grant/allow capabilities. Reflection/diagnostics expose Contract origins. Header placement remains separate. Owner decision: 2026-07-24.
- **D-298 — `meta` is the final header clause for every declaration kind: frozen.** Class order is `extends -> for -> mixin -> where -> meta`; Module is `mixin -> where -> meta`; Contract is `extends -> where -> meta`. `meta deny` is static header syntax only and never appears in executable/conditional body code. Owner decision: 2026-07-24.
