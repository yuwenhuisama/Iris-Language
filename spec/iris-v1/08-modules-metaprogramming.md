# Iris v1 Modules And Metaprogramming

Status: Iris v1 draft, frozen semantics.

IRIS-V1-META-C001: This chapter defines Iris v1 package identity, Module source structure, imports, exports, re-exports, initialization order, manifest and lock semantics, declaration-body execution, declarative and programmatic open transactions, candidate isolation, safepoint commit, conflict handling, revision audit and rollback entry points, Module composition authorization, decorators, MetaCapabilities, ReflectionPolicy, reflection views, `respond_to?`, raw ivar reflection, and static versus dynamic member visibility. It MUST be read after [README.md](README.md), [01-language-identity.md](01-language-identity.md), [02-lexical-grammar.md](02-lexical-grammar.md), [03-runtime-object-model.md](03-runtime-object-model.md), [04-bindings-callables-control-flow.md](04-bindings-callables-control-flow.md), and [05-types-contracts-generics.md](05-types-contracts-generics.md).

IRIS-V1-META-C002: This chapter MUST NOT redefine ordinary dispatch, Method and BoundMethod identity, Contract type algebra, Contract view hashing, async scheduling, ExceptionContext ownership, native ABI handles, source token inventory, or stable serialization formats. Those rules remain owned by the earlier runtime, callable, type, async, native, and library chapters. This chapter only states the Module, package, transaction, decorator, capability, and reflection obligations that those surfaces must preserve.

## Package Identity, Manifests, And Locks

IRIS-V1-META-C003: A publishable package MUST declare a globally unique reverse-domain-style `package_id`, an `api_major`, a package semantic version, an Iris language major or version range, ordered source or Module entries, dependency constraints, permission requests, native artifact declarations where applicable, and entry Modules in `iris.toml`. Manifestless local scripts MAY run with runtime-local package identity only, as defined by [01-language-identity.md](01-language-identity.md).

IRIS-V1-META-C004: Package identity for named nominal Types, Modules, Classes, Contracts, and package-owned reflection metadata MUST use `(package_id, api_major, Iris language major, fully qualified name, type kind, generic arity, closed arguments where applicable)`. It MUST NOT depend on filesystem path, display name, source hash, machine-local build data, load context, or source enumeration order.

IRIS-V1-META-C005: A runtime MUST activate at most one package implementation revision for each `(package_id, api_major)`. Same-major minor or patch revisions share nominal identity and cannot coexist as hidden load-context identities. Incompatible coexistence requires a different `api_major`.

IRIS-V1-META-C006: Dependency resolution MUST select exact package versions and artifact digests before initialization and record them in an exact lockfile. Build and runtime loading MUST consume the selected lock result and MUST NOT fetch, resolve, or prefer latest versions implicitly.

IRIS-V1-META-C007: Package dependency constraints use SemVer-compatible ranges constrained by package API-major identity. Resolution failure, incompatible API-major unification, missing required artifacts, or digest mismatch MUST abort package linking before any dependent Module body executes.

IRIS-V1-META-C008: Manifest `permissions` entries are namespaced requests, not grants. A package MAY request names such as `reflection.inspect`, `reflection.mutate`, `filesystem.read`, `network.connect`, or `native.load`, with required or optional status and scope metadata. The Host or CLI MUST explicitly grant a subset. Unspecified permissions default deny, and an ungranted required request MUST prevent package load.

IRIS-V1-META-C009: Runtime-wide trusted reflection policy cannot be requested by an ordinary package manifest. It exists only through Host configuration for trusted tooling or a dedicated host package identity. A package, dependency, native artifact, or dynamic import MUST NOT self-authorize permissions.

IRIS-V1-META-C010: The following package table is normative:

| Surface             | Source                                              | Identity rule                                     | Failure rule                                | Reflection exposure                  |
| ------------------- | --------------------------------------------------- | ------------------------------------------------- | ------------------------------------------- | ------------------------------------ |
| Publishable package | `iris.toml` with `package_id` and `api_major` | Stable across compatible minor and patch releases | Missing or invalid manifest aborts load     | Package metadata view                |
| Manifestless script | Host-chosen local entry                             | Runtime-local only                                | Cannot claim stable public Type identity    | Local package metadata view          |
| Dependency          | SemVer range plus API major                         | One selected exact version in lockfile            | Resolution or digest failure aborts link    | Selected package and digest metadata |
| Permission request  | Manifest`permissions`                             | Request only, not grant                           | Required ungranted request aborts load      | Request and grant origin metadata    |
| Hot upgrade         | `Package.upgrade(...)`                            | Same`(package_id, api_major)`                   | Candidate failure leaves old package active | Old and new revision audit metadata  |

## Module Source Model, Imports, Exports, And Initialization

IRIS-V1-META-C011: A source file MAY contain multiple explicit `module` and `open module` blocks. Outside Module blocks, source MAY contain only package or file imports, exports, re-exports, and package-level declarative metadata. Ordinary executable statements and source `fun` declarations MUST belong to a Module body.

IRIS-V1-META-C012: Within one package, each qualified Module name has exactly one origin declaration written `module Name ... { ... }`. Additional same-package or cross-file extension of that Module MUST use `open module Name ... { ... }`. Multiple implicit origins for one qualified Module MUST be rejected.

IRIS-V1-META-C013: Imports are static, explicit, aliasable, and selective. The supported forms are `import pkg::Module`, `import pkg::Module as Alias`, and `from pkg::Module import Name, Other as Alias`. Wildcard imports and runtime-string imports are not part of Iris v1 source.

IRIS-V1-META-C014: Static imports are resolved before executable Module body statements. They introduce only the named Modules or items requested by source and MUST NOT implicitly re-export names, activate extension members through indirect imports, or add runtime-loaded names to already compiled lexical namespaces.

IRIS-V1-META-C015: `export` marks public package API for named Classes, Modules, Contracts, Type aliases, constants, globals, Module-body Methods on `main`, and exported open-extension artifacts. Re-export is explicit through `export import` or `export from` facade declarations.

IRIS-V1-META-C016: Re-export exposes names and Contracts but MUST NOT count as the direct import required to activate another Module's exported static open extension. A consumer that wants static extension members MUST directly import the Module that exports that open extension.

IRIS-V1-META-C017: Module initialization forms an acyclic deterministic DAG. Static dependencies initialize before dependents. A Module executes its origin body, then its applicable open blocks in manifest-declared source and block order. Dependency or initialization cycles MUST be compile or link errors.

IRIS-V1-META-C018: A conforming runtime MUST NOT expose partially initialized or lazy cyclic Modules. If Module initialization fails, that Module and dependents are marked failed for that load attempt. The runtime MUST NOT automatically retry; explicit package reload or upgrade is required.

IRIS-V1-META-C019: Direct import source order determines compatible extension override order after each dependency initializes. Filesystem enumeration, concurrent scheduling, Module-name sorting, hash-map iteration, or arbitrary topological choice MUST NOT determine static extension replacement behavior.

IRIS-V1-META-C020: Language imports never accept runtime strings or values. Permission-controlled `Package.load(id, version...)` MAY dynamically load and initialize a package or Module and return a `Dynamic<Module>` bounded handle or reflection metadata. It MUST NOT retroactively add names, Types, or static extensions to an already compiled namespace.

IRIS-V1-META-C021: The following Module initialization table is normative:

| State        | Entered by                                   | Visible to dependents                     | Failure behavior                                  | Retry behavior                           |
| ------------ | -------------------------------------------- | ----------------------------------------- | ------------------------------------------------- | ---------------------------------------- |
| Unlinked     | Resolver has not selected exact dependencies | Nothing                                   | Resolution failure aborts before Module execution | Re-run package resolution explicitly     |
| Linked       | Lockfile and imports are resolved            | Static names only, no executed body state | Link cycle or missing artifact aborts             | Re-run after inputs change               |
| Initializing | Origin or open body transaction is running   | No partial body state to dependents       | Failure marks Module failed                       | No automatic retry                       |
| Initialized  | Origin and applicable opens committed        | Exported API and runtime state visible    | Later revision event failure cannot undo it       | Package reload or upgrade may replace it |
| Failed       | Initialization raised or validation failed   | No usable initialized Module              | Dependents fail                                   | Explicit reload or upgrade only          |

## Executable Declaration Bodies

IRIS-V1-META-C022: Class and Module origin bodies are executable construction transactions over a candidate Class or Module. They may run ordinary synchronous control flow, declare members, call metaprogramming APIs, and use lexical locals. Success validates the complete candidate and publishes atomically. Failure publishes nothing from that candidate.

IRIS-V1-META-C023: During Class or Module origin or open body execution, `self` is the stable logical Class or Module object. Structural meta messages sent to `self`, such as `include`, `define_method`, or `superclass=`, target the current transaction candidate rather than mutating the published active revision directly.

IRIS-V1-META-C024: Unqualified calls inside an executable Class or Module body first resolve lexical locals, parameters, captures, constants, Types, and imports. If no callable binding or declaration is found, they are equivalent to privileged sends to the current `self` or Module `main` receiver under the callable chapter rules.

IRIS-V1-META-C025: Instance Methods enter candidate instance Method tables only through explicit declaration syntax or explicit meta-operation APIs. Ordinary body calls do not implicitly define instance Methods, properties, storage slots, or Contract requirements.

IRIS-V1-META-C026: A Method declaration inside an executable Class or Module body does not close over lexical locals created by that body execution. Its lexical environment contains definition or Module scope, type parameters, owner metadata, and Method parameters, not transaction-temporary locals.

IRIS-V1-META-C027: Class and Module body locals are ordinary lexical locals. Nested Closures may capture them, and escaping Closures may extend their lifetime. Such locals do not become properties, class state, Module state, or persistent storage merely because the body transaction commits.

IRIS-V1-META-C028: Top-level unconditional declarations in an origin or compiler-resolvable declarative open body may contribute compiler-visible static API under the static visibility rules in this chapter. Members or composition executed conditionally inside `if`, loops, nested blocks, or other runtime control flow affect only the candidate dynamic surface when that path executes.

IRIS-V1-META-C029: Contract bodies are not executable declaration transactions. A Contract body may contain only static requirements and metadata allowed by the type chapter. It MUST NOT contain Method bodies, stored state, initializers, raw ivars, private requirements, executable statements, or open operations.

## Open Transactions And Candidate Isolation

IRIS-V1-META-C030: `class Name ... { ... }` and `module Name ... { ... }` are origin declarations. Later structural metaprogramming MUST use explicit `open class Name { ... }`, `open module Name { ... }`, or the programmatic `Class#open` and `Module#open` transaction APIs.

IRIS-V1-META-C031: `contract` declarations are static and cannot be opened. Any source or programmatic attempt to open a Contract MUST be rejected before publication and MUST NOT create a candidate.

IRIS-V1-META-C032: Within one compilation unit, an `open class` or `open module` MAY appear before the origin declaration because declaration collection and static-spine resolution precede open scheduling. Across Modules or packages, the opener MUST explicitly depend on the origin-defining Module, and origin linking and initialization MUST complete before the open transaction executes.

IRIS-V1-META-C033: Declarative `open class` and `open module` are statically resolvable syntax over the same transaction model as `Class#open` and `Module#open`. Programmatic open accepts aliases, reflection results, or dynamically selected Class and Module objects, but it MUST NOT target Contracts or closed generic Classes or Modules.

IRIS-V1-META-C034: An open transaction body receives stable logical identity for its target while structural operations mutate one implicit candidate for each target in the current transaction group. Normal completion validates and commits. Exception, invalid control transfer, validation error, capability denial, permission denial, or conflict rolls back every candidate in the group.

IRIS-V1-META-C035: The open block and its synchronous dynamic call chain read their own candidate structural metadata after writes. Code outside that transaction context, other Tasks, and ordinary instance sends continue observing the published active revision until successful atomic publication.

IRIS-V1-META-C036: Ordinary instance sends inside an open transaction MUST use the published active revision. Candidate Methods, MRO, Modules, and properties are visible only through transaction-aware Class or Module metadata and reflection reads. Iris v1 has no candidate-instance preview.

IRIS-V1-META-C037: Open and revision transaction bodies are synchronous, thread-confined, non-suspending, and non-escaping. They MUST NOT `await`, scheduler-yield with resumable transaction state, transfer to another thread, share candidate mutation with child threads, or let a candidate or transaction authority escape. Static violations are compile errors; dynamic violations raise `MetaTransactionError`.

IRIS-V1-META-C038: Same-thread nested open calls join the outermost transaction group. Inner opens never commit independently. Reopening a target already present in the group reuses that target's candidate. All candidates in the group validate together and publish together, or all roll back.

IRIS-V1-META-C039: Candidate construction MUST NOT hold long-lived exclusive Class or Module locks. Each candidate records every target's base active revision. At commit, if any overlapping target changed since the base revision, the transaction MUST raise `MetaTransactionConflictError`, roll back every candidate, and publish nothing.

IRIS-V1-META-C040: Iris v1 provides no automatic open retry, rebase, merge, or hidden block re-execution after `MetaTransactionConflictError`. User code MAY catch the conflict and retry explicitly, and owns external effects, compensation, backoff, retry limits, and idempotency.

IRIS-V1-META-C041: Structural open commits use a global runtime safepoint. After validation, commit stops participating runtime execution at safepoints, publishes all active Class and Module revisions plus affected state and invalidation metadata atomically, then resumes execution. Threads MUST NOT observe a partial structural mix.

IRIS-V1-META-C042: Runtime rollback for origin, open, package upgrade, decorator application, closed generic materialization, migration hook, and rollback reconstruction covers only runtime-owned candidate state. Filesystem, network, database, external process, native-internal, logging, mutation to already published objects, or other external effects are not automatically reversed.

IRIS-V1-META-C043: The following transaction state table is normative:

| Transaction state          | Ordinary instance sends                               | Candidate metadata reads        | Exit path                                    | Published state                     |
| -------------------------- | ----------------------------------------------------- | ------------------------------- | -------------------------------------------- | ----------------------------------- |
| No transaction             | Published active revision                             | Published metadata only         | Ordinary control                             | Current active revision             |
| Candidate executing        | Published active revision                             | Transaction reads own candidate | Body may complete or raise                   | No candidate state globally visible |
| Nested candidate executing | Published active revision                             | Same outer transaction group    | Inner completion returns to outer            | No independent inner commit         |
| Validation                 | Published active revision                             | Frozen candidate snapshot       | Success enters safepoint, failure rolls back | No partial state                    |
| Safepoint commit           | Paused or old entered frames continue selected bodies | Commit-owned immutable data     | Atomic publish                               | New revisions visible after resume  |
| Rollback                   | Published active revision remains                     | Candidate discarded             | Failure or conflict propagates               | Nothing from candidate published    |

## Static And Dynamic Member Visibility

IRIS-V1-META-C044: Iris v1 has three member visibility layers for metaprogramming: origin static API, compiler-resolvable declarative open static API, and dynamic-only runtime API. The origin static API is universal for the declaring package and importers according to export rules.

IRIS-V1-META-C045: A top-level unconditional member in a declarative open may extend static API inside the defining Module. Cross-Module static visibility requires `export open ...`, and each consumer MUST directly import the extension Module. Transitive imports and re-exports MUST NOT activate static extension members.

IRIS-V1-META-C046: Programmatic open additions and conditional executable-body additions are dynamic-only. They are discoverable through permitted reflection, usable through ordinary runtime dispatch, and usable statically only through `Dynamic<T>` or after a new static artifact that declares or exports them is compiled and directly imported.

IRIS-V1-META-C047: Runtime cannot promote dynamic-only members into already compiled static Type APIs. Dynamic-only metadata MUST record origin package, source or artifact identity, revision, commit, visibility, and dynamic-only static visibility status.

IRIS-V1-META-C048: When multiple directly imported declarative extensions contribute the same member to one Class or Module, a later direct import in source order replaces the earlier implementation only when its complete static signature, visibility, and Contract obligations are compatible. No overload set is formed.

IRIS-V1-META-C049: A direct import that would replace an already merged static extension member requires explicit import-site replacement authorization using the language's accepted `override` import marker. If no such accepted marker exists in the current grammar profile, the replacement MUST be rejected rather than silently accepted. This rule preserves the semantic requirement without granting a hidden syntax.

IRIS-V1-META-C050: Any same-Module origin or open declaration that replaces an already resolved member MUST carry member-level `override`. Missing `override`, `override` with no target, and incompatible replacement are errors. This applies to instance Methods, class-object Methods, getters, setters, qualified Contract implementations, Module Methods, and conditional dynamic replacement paths.

IRIS-V1-META-C051: A member intended to satisfy a declared Contract requirement MUST use `impl` as specified by the type chapter. If the same declaration replaces an ancestor or Module member, both `override` and `impl` are required where applicable.

IRIS-V1-META-C052: Dynamic and static member boundaries MUST preserve ordinary selector identity. Static type, expected return Type, generic argument, union branch, or extension import order MUST NOT create overload dispatch or choose among incompatible implementations.

## Module Composition And Private Authorization

IRIS-V1-META-C053: Declarative header `mixin` in Class and Module declarations contributes static composition. Programmatic `include`, removal, and re-inclusion inside origin or open transactions affect the candidate runtime dynamic surface unless the composition is also part of a compiler-visible static declaration.

IRIS-V1-META-C054: Class and Module composition operations MUST validate Module `Self` constraints, generic Module arguments, static spine promises, Contract implementation obligations, MRO validity, MetaCapabilities, and native or layout safety before publication.

IRIS-V1-META-C055: One `modules` MetaCapability controls Module include, mixin, removal, replacement, ordering, and recomposition. Iris v1 does not split add, remove, order, or per-Module composition capability flags.

IRIS-V1-META-C056: Module composition grants no private Method access by default. Private Method access from composed Module Methods to a host Class requires explicit authorization at the static or dynamic composition edge, such as a `private` composition option accepted by the grammar or API.

IRIS-V1-META-C057: Module private authorization is scoped to `(host logical Class, closed Module identity, composition edge, edge revision)`. A grant in one host, package, generic instantiation, or old edge MUST NOT grant access in another. Removal of the Module edge atomically revokes that edge's private authorization.

IRIS-V1-META-C058: Composed Module Methods may read and write unqualified `@name` raw ivars on the current receiver according to raw ivar rules whether or not the edge grants private Method access. Private authorization affects private selectors only.

IRIS-V1-META-C059: Protected Methods declared by a host Class may be called from composed Module Methods as part of that host implementation layer, subject to the runtime chapter's protected receiver rule. This does not grant private access and does not alter raw ivar current-receiver semantics.

IRIS-V1-META-C060: Module reordering in v1 uses explicit remove plus include inside one transaction. Re-including an already present closed Module is idempotent and MUST NOT move it. Re-inclusion after removal creates a new edge and requires edge metadata, including private authorization, to be stated again.

## Revisions, Audit, Rollback, And Hot Upgrade

IRIS-V1-META-C061: Each successful structural transaction group receives one runtime-wide monotonic `commit_id`. Each affected Class or Module receives its own per-owner monotonic revision number. Failed or rolled-back candidates MUST NOT consume a per-owner revision number or runtime `commit_id`.

IRIS-V1-META-C062: Superseded executable revisions remain loaded while retained by entered frames, retained Method or BoundMethod objects, Closures or code artifacts, native handles or pins, revision reflection objects, JIT dependencies, debugger or profiler pins, or other explicit old-revision references. Ordinary instances do not by themselves pin old dispatch revisions.

IRIS-V1-META-C063: Lightweight audit history MAY remain after heavy executable revision state is reclaimed. Audit records identify owner, revision number, commit ID, package, source or artifact, initiator, timestamps or context, immutable artifact locator, digest, and change summary. Audit records are non-executable unless exact artifacts are retrieved.

IRIS-V1-META-C064: `Class.rollback(target)` and corresponding Module or package rollback entry points are new structural transactions. They reconstruct a candidate from current active state plus exact historical artifacts, validate current static spine, Contracts, MRO, visibility, native obligations, and MetaCapabilities, then publish a new revision and commit ID on success.

IRIS-V1-META-C065: Rollback MUST NOT directly reactivate historical revisions. Same-major rollback MUST NOT downgrade the current static spine. Missing later required members, Contracts, generic arity, visibility obligations, native obligations, or superclass bounds MUST cause rollback failure and publish nothing.

IRIS-V1-META-C066: Audit rollback artifact retrieval MUST resolve the exact source, bytecode, native artifact, or manifest through the active package store or an explicit user resolver and verify the stored digest. Missing, inaccessible, or mismatched artifacts MUST raise `RevisionArtifactUnavailableError` and publish nothing.

IRIS-V1-META-C067: Revision artifact integrity uses a full BLAKE3-256 canonical manifest covering semantics-affecting Iris source blobs, bytecode or IR, native binaries, dependency package IDs, API majors, exact revisions, Iris language, compiler and runtime ABI versions, and build options or path-to-content mappings. Locator bytes are excluded from the digest.

IRIS-V1-META-C068: Same-major package upgrade through `Package.upgrade(...)` is explicit and transactional. The runtime builds candidates for affected Modules, generic definitions and interned closed constructions, Classes, Methods, properties, native ABI obligations, and extension effects, validates them as one transaction, and switches active revisions atomically on success.

IRIS-V1-META-C069: A same-major package upgrade reuses existing Module, Class, shared, and per-closed storage whose static Contracts remain compatible and does not rerun their ordinary initializers. Newly introduced storage runs its initializer inside the candidate transaction. An explicit `upgrade(from_version, state_or_context)` migration hook MAY transform or validate candidate state.

IRIS-V1-META-C070: Package upgrade hook failure, validation failure, native binding failure, or capability or permission denial MUST leave the old package and state fully active. External side effects from upgrade hooks are the package author's responsibility under IRIS-V1-META-C042.

IRIS-V1-META-C071: After-commit revision events are read-only observations owned for scheduling and delivery by [07-async-resources-diagnostics.md](07-async-resources-diagnostics.md). This chapter requires each structural commit to produce the immutable commit metadata needed for those events, and it forbids any event subscriber from vetoing, mutating, retrying, or rolling back a completed commit.

## MetaCapabilities

IRIS-V1-META-C072: Every Class static spine and every Module or Contract declaration where grammar admits `meta deny` carries immutable, reflectable `MetaCapabilities` policy data. The policy describes which structural operations are permitted. Every syntax, reflection, Dynamic, package, native, and Host meta path MUST invoke the same operation-level capability checks.

IRIS-V1-META-C073: The v1 MetaCapabilities vocabulary is exactly `method_set`, `method_body`, `property_set`, `property_body`, `modules`, `superclass`, `subclass`, `shape`, `class_state_set`, `class_state_write`, `instance_state`, and `native`. Unknown names in `meta deny` MUST be compile errors.

IRIS-V1-META-C074: Source `meta deny` is denial-only. No source `allow` form can grant unavailable runtime power, restore an ancestor denial, widen a Module or Contract denial, or create a runtime-internal capability. Open blocks and conditional executable body code MUST NOT change `MetaCapabilities` policy.

IRIS-V1-META-C075: `meta` is the final header clause for every declaration kind that admits it. Class order is `extends`, `for`, `mixin`, `where`, `meta`. Module order is `mixin`, `where`, `meta`. Contract order is `extends`, `where`, `meta`. `meta deny` is static header syntax only and MUST NOT appear in executable or conditional body code.

IRIS-V1-META-C076: A Class's effective capabilities are the language and runtime defaults minus every denial from the declared superclass chain, minus local origin denies, minus every denial from the current runtime-superclass or MRO Class chain, minus active Module-sourced denies, minus Contract-required denies. Candidate validation computes this full set before operations commit.

IRIS-V1-META-C077: A subclass may further narrow effective capabilities but MUST NOT re-enable a capability denied by an ancestor static chain. Runtime superclass changes may narrow capabilities through the active runtime chain but MUST NOT restore a denied static-chain capability.

IRIS-V1-META-C078: A Module may declare immutable `meta deny` restrictions. Static mixin and dynamic include add those denies, with Module identity as policy origin, to the host Class revision's effective capabilities. Removing the Module removes only that Module-sourced restriction, and only when no remaining source denies it.

IRIS-V1-META-C079: A Contract may declare immutable `meta deny` requirements as part of its static promise. A Class that declares `for Contract` MUST have an effective policy at least as restrictive, and conformance absorbs those denies into the Class static spine. Contract inheritance unions deny requirements.

IRIS-V1-META-C080: MetaCapabilities are orthogonal. Denying one capability MUST NOT implicitly deny another. Each meta operation declares all required capabilities, and missing any required capability raises `MetaCapabilityError` with target, operation, policy origin, and reason. The whole transaction group rolls back.

IRIS-V1-META-C081: The following capability matrix is normative and complete for v1 core meta operations:

| Operation                                                           | Required MetaCapabilities                                                             | Additional checks                                                       | Static API effect                                          |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------- |
| Add, remove, alias, undef, or change Method slot or signature       | `method_set`                                                                        | Static spine, visibility,`override`, `impl`, callable compatibility | Static only for origin or exported direct declarative open |
| Replace compatible Method body                                      | `method_body`                                                                       | Same slot signature and Contract compatibility                          | No new static member                                       |
| Add, remove, or change property getter or setter slot or signature  | `property_set`                                                                      | Property Contract, visibility,`override`, storage rules               | Static only for origin or exported direct declarative open |
| Replace compatible property accessor body                           | `property_body`                                                                     | Same accessor contract                                                  | No new static member                                       |
| Add, remove, or change stored instance property or shape descriptor | `property_set`, `shape`                                                           | Layout, GC, Contract, native safety                                     | Static only when compiler-visible                          |
| Add or remove native-backed storage or native structural metadata   | operation capabilities plus`native`                                                 | Native ABI and safety validation                                        | Depends on operation source                                |
| Include, remove, reorder, or replace Module composition edge        | `modules`                                                                           | Self constraints, MRO, Contract satisfaction, edge authorization        | Static only for header or exported direct declarative open |
| Change runtime superclass                                           | `superclass`                                                                        | Declared superclass bound, MRO, layout, built-in protection             | Dynamic runtime ancestry only within static bounds         |

IRIS-V1-META-C082: Built-in protected Classes such as Nil, Bool, Integer, Float32, and Float64 use the same immutable MetaCapabilities and operation checks as user Classes. Their runtime superclass mutation is rejected at the unified meta-operation boundary and aborts the complete transaction group.

IRIS-V1-META-C083: `shape` governs Class-wide layout, declared storage, native layout, and GC tracing structure. `instance_state` governs per-object creation and recreation of absent undeclared raw ivars. `meta deny shape` alone does not seal undeclared dynamic ivars. `meta deny instance_state` prevents new undeclared raw ivar expansion while leaving declared typed properties governed by their own Contracts.

IRIS-V1-META-C084: Identity-less immutable values cannot create, recreate, or retain undeclared dynamic ivars. Their effective policy intrinsically denies `instance_state` through the same model. Assignment that would create such state MUST raise `InstanceStateError` across source, reflection, Dynamic, native, and Host paths.

## Decorators

IRIS-V1-META-C085: Decorator syntax `@decorator(args)` precedes Class, Module, Contract, Method, or property declarations. A decorator transforms declaration candidate metadata rather than replacing nominal identity, declaration kind, package identity, or target static spine.

IRIS-V1-META-C086: Multiple decorators execute in written top-to-bottom order. Each decorator result MUST remain the same typed declaration category as its input. Iris v1 decorators are constrained typed declaration transformers, not unrestricted replacement functions, compiler AST macros, or arbitrary compile-time execution.

IRIS-V1-META-C087: Declarative decorators have two phases. The compiler or linker resolves directly imported decorators and executes a pure deterministic static planning phase that may contribute compiler-visible metadata or API transformations. Runtime origin or open execution applies the runtime transform inside the declaration's candidate transaction.

IRIS-V1-META-C088: A decorator static plan MUST NOT depend on IO, time, randomness, ambient runtime state, untracked environment, mutable global process state, current package load race, or unspecified ordering. Inputs are the decorator identity, arguments, immutable declaration metadata, direct imports, package metadata, and explicitly tracked configuration.

IRIS-V1-META-C089: Runtime-dependent or conditional programmatic decoration is dynamic-only. It MUST NOT alter already compiled static API, and any discoverability comes through reflection metadata or Dynamic dispatch until a new static artifact is compiled and directly imported.

IRIS-V1-META-C090: Decorators carry no inherent structural authority. Every generated Method, property, storage, Module, metadata, or body-wrapping operation MUST declare and pass the same MetaCapabilities, static-spine checks, package permissions, ReflectionPolicy checks where applicable, `override` rules, and Contract compatibility as an equivalent handwritten operation.

IRIS-V1-META-C091: Decorators MUST NOT change declaration kind, nominal identity, package identity, immutable superclass bound, declared Contract set, Contract requirements, generic arity, generic invariance, native layout obligation, or any other forbidden static-spine fact. Contract decorators MUST NOT hide or add required obligations outside explicit Contract source or deterministic static API.

IRIS-V1-META-C092: Built-in typed generic Decorator Contracts receive immutable declaration metadata plus a controlled transform context and return same-kind candidate transformations. Runtime transform phases are synchronous and non-awaiting. External side effects from decorator runtime code are not rollbackable by Iris and remain the decorator author's responsibility.

IRIS-V1-META-C093: Origin construction, declarative open, hot upgrade, rollback reconstruction, and closed generic materialization MUST reapply declaration decorators in source order to the new candidate. Transform or validation failure aborts the whole candidate transaction and publishes nothing.

IRIS-V1-META-C094: Reflection exposes ordered decorator identity, arguments, package and source identity, static and runtime phase participation, and permission-filtered generated diff metadata. It MUST NOT expose mutable transform internals or candidate mutation handles.

## ReflectionPolicy And Reflection Views

IRIS-V1-META-C095: Reflection returns permission-filtered immutable metadata snapshots or lazy immutable views of identity-bearing metadata objects. It MUST NOT expose mutable internal maps, raw tables, candidate mutation handles, compiler AST as a general API, or eval-string primary mutation.

IRIS-V1-META-C096: Default reflection views include only members and metadata visible to the caller package and visibility context. Privileged `all_*` or raw metadata views require ReflectionPolicy inspect scope. Structural mutation always uses open or meta transactions and MUST NOT occur by mutating a returned reflection view.

IRIS-V1-META-C098: `respond_to?(selector, include_non_public: false)` reports actual visible ordinary slots on the receiver's current active ordinary MRO. It MUST NOT invoke or consult `method_missing`. Visibility denial returns false or raises only as specified by the API contract, but it MUST NOT use `method_missing` as a probe.

IRIS-V1-META-C099: Optional `respond_to_missing?` is a separate dynamic hint and MUST NOT change `respond_to?` truth. Qualified Contract slots use Contract-view-specific `respond_to_contract?`. Ordinary and qualified namespaces MUST NOT merge.

IRIS-V1-META-C100: Raw ivar reflection uses ordinary APIs `Reflection::Object.list_ivars(obj)`, `Reflection::Object.get_ivar(obj, name)`, `Reflection::Object.set_ivar(obj, name, value)`, and `Reflection::Object.remove_ivar(obj, name)`. Authorization is ambient to the currently executing package or Module context under Host-configured ReflectionPolicy and manifest grants.

IRIS-V1-META-C101: Iris v1 has no first-class reflection token system. Reflection calls MUST NOT accept, create, derive, delegate, revoke, or transitively pass a historical `ReflectionCapability` token. Method visibility, Dynamic typing, Module private authorization, MetaCapabilities, Host code execution, and native extension execution do not by themselves grant reflection.

IRIS-V1-META-C102: ReflectionPolicy grants `inspect` and `mutate` independently. `inspect` covers list and get operations. `mutate` covers set and remove operations. Mutate does not imply inspect, and inspect does not imply mutate.

IRIS-V1-META-C103: ReflectionPolicy scope MAY cover own package, selected package IDs or Classes, or runtime-wide trusted tooling under Host policy. Every reflection operation checks caller package identity, granted operation, granted scope, target identity, target Class `instance_state` where creation is requested, identity-less restrictions, and host or native safety rules.

IRIS-V1-META-C104: Reflection grants do not flow through callers, dependency importers, receiver owners, stack frames, or helper call chains. Authorization is determined by the package owning the currently executing callable or call site that performs the reflection call.

IRIS-V1-META-C105: Method reflection calls use the package defining the exact Method body. Closure reflection calls use the package of the Closure creating code and retain it after escape or cross-package invocation. BoundMethod inherits its Method package. Extension-open Methods belong to the extension package, not the target Class origin.

IRIS-V1-META-C106: Origin Class and Module body code executes under the origin source package's ReflectionPolicy. Declarative extension or open body code executes under the extension source package. Programmatic `Class#open` or `Module#open` runs the supplied block under that Closure's lexical definition package.

IRIS-V1-META-C107: Native callables use the native artifact's manifest package identity for reflection. Host built-ins use a dedicated host package identity with explicit policy. Manifestless native artifacts default to no reflection unless the Host loads them under an explicitly trusted package identity.

IRIS-V1-META-C108: `ReflectionAccessError` MUST report caller package, operation, target scope, and denial origin without leaking inaccessible data. Reflection denials, capability denials, type failures, and transaction failures are ordinary Iris failures and MUST NOT expose host-only error channels.

IRIS-V1-META-C109: Authorized `get_ivar(obj, name)` returns `nil` for an absent raw ivar and creates nothing. `set_ivar` returns the assigned value; creating or recreating an absent slot additionally requires target effective `instance_state`. `remove_ivar` returns the removed old value and raises `InstanceVariableNotFoundError` when absent. `list_ivars` returns an immutable `Array<Symbol>` of existing names in unspecified order.

IRIS-V1-META-C110: Raw ivar reflection names MUST be Symbols whose canonical content begins with exactly one `@` followed by a valid ordinary identifier with no selector suffix. Strings never convert implicitly. Empty names, repeated `@`, selector suffixes, and source-inexpressible identifiers MUST raise `InvalidInstanceVariableNameError`.

IRIS-V1-META-C111: Raw ivar reflection cannot create hidden-only ivars. Source `@name`, Symbol `:@name`, and reflection name `:@name` denote the same current-receiver slot name. External source syntax `other.@name` remains invalid, and reflection is the only external raw-ivar access path.

IRIS-V1-META-C112: Reflection mutation of raw ivars MUST still respect identity-less value restrictions, receiver state policy, runtime/native safety, and the transaction or ordinary assignment boundary that owns the operation. ReflectionPolicy alone is not a transaction bypass and not an `instance_state` bypass.
