# Iris v1 Bindings, Callables, And Control Flow

Status: Iris v1.15, frozen semantics with owner-approved errata.

IRIS-V1-CONTROL-C001: This chapter defines bindings, scopes, name lookup, callable runtime kinds, parameter binding, Closure capture and return, calls and trailing blocks, assignment, conditionals, loops, match, Iterator lowering, exceptions, and control-transfer results for Iris v1. It MUST be read after [README.md](README.md), [02-lexical-grammar.md](02-lexical-grammar.md), and [03-runtime-object-model.md](03-runtime-object-model.md).

IRIS-V1-CONTROL-C002: This chapter MUST NOT define new tokens, alternate parser productions, object layout, type algebra details, async scheduling, resource helper APIs, package loading, or conformance runner format. It refines the grammar forms already named by [02-lexical-grammar.md](02-lexical-grammar.md) and the runtime callable, dispatch, property, truthiness, and storage anchors in [03-runtime-object-model.md](03-runtime-object-model.md).

## Binding Declarations And Definite Assignment

IRIS-V1-CONTROL-C003: Local bindings use `let` for immutable bindings and `mut` for mutable bindings. `let name[: T] = expr` MUST declare an initialized immutable lexical binding. `mut name[: T] = expr` MUST declare an initialized mutable lexical binding. `mut name: T` MAY declare a mutable binding with deferred initialization. A bare `name = expr` MUST assign an existing mutable binding and MUST NOT declare a new local.

IRIS-V1-CONTROL-C004: `let` MUST have an initializer. Untyped uninitialized `mut name` MUST be rejected with `BINDING_MISSING_TYPE_FOR_DEFERRED_INIT`. Reading a deferred mutable binding before definite assignment MUST raise or diagnose `DefiniteAssignmentError` according to compile-time knowledge. After a binding has a declared or inferred local type, later assignments MUST satisfy that fixed type and MUST NOT widen it implicitly.

IRIS-V1-CONTROL-C005: A binding annotation is a static and runtime contract for the binding cell. Without an annotation, the initializer's precise static type becomes the binding's fixed local type. Programs that need a wider target type MUST write it explicitly, such as `mut value: String | Integer = "ready"` or `mut value: Dynamic<Object> = source`.

IRIS-V1-CONTROL-C006: Parameter bindings, catch bindings, and per-iteration `for` bindings are immutable unless their own declaration form explicitly uses `mut`. `_` is a discard binding. It accepts a value without creating a readable binding, MAY appear repeatedly where binding patterns allow it, MUST NOT be captured, and MUST be a compile-time error when read as an expression.

IRIS-V1-CONTROL-C007: The following binding table is normative:

| Source form                | Binding category             | Initialization rule               | Reassignment rule                                      | Read before init            | Result of assignment |
| -------------------------- | ---------------------------- | --------------------------------- | ------------------------------------------------------ | --------------------------- | -------------------- |
| `let x = expr`           | Immutable local              | Required                          | Prohibited                                             | Impossible if accepted      | Not applicable       |
| `let x: T = expr`        | Immutable typed local        | Required and checked against`T` | Prohibited                                             | Impossible if accepted      | Not applicable       |
| `mut x = expr`           | Mutable inferred local       | Required                          | Allowed within inferred type                           | Impossible if accepted      | Stored value         |
| `mut x: T = expr`        | Mutable typed local          | Required and checked against`T` | Allowed within`T`                                    | Impossible if accepted      | Stored value         |
| `mut x: T`               | Mutable typed deferred local | Deferred                          | First assignment initializes, later assignments update | `DefiniteAssignmentError` | Stored value         |
| Parameter or catch binding | Immutable lexical binding    | Bound by call or catch            | Prohibited                                             | Impossible if accepted      | Not applicable       |
| `_`                      | Discard                      | Value accepted and ignored        | Not addressable                                        | Read is compile-time error  | Not applicable       |

IRIS-V1-CONTROL-EX001: Informative example, local binding and definite assignment:

```iris
let name: String = "Iris"
mut count: Integer
count = 1

mut value: String | Integer = "ready"
value = 42
```

## Storage Sigils, Scopes, And Lookup

IRIS-V1-CONTROL-C008: `@name` denotes current-receiver raw storage under [03-runtime-object-model.md](03-runtime-object-model.md). It MUST NOT be used as `other.@name`. `@@name` denotes a declared hierarchy Class-variable binding cell anchored to a logical Class. `$name` denotes a package-qualified runtime global declared by `global let` or `global mut`. Reads or writes through `@@name` or `$name` MUST require a matching declaration.

IRIS-V1-CONTROL-C009: Sigil syntax MUST NOT create bindings merely by use. Assignment to absent undeclared `@name` MAY create a raw current-receiver slot only under the receiver's `instance_state` policy. Assignment to absent `@@name` or `$name` MUST fail as missing declared storage. Assignment to absent ordinary local `name` MUST fail as `NameError` or a static unresolved-binding diagnostic.

IRIS-V1-CONTROL-C010: A lexical scope is created by a Module executable body, Method body, Closure body, braced block, conditional branch, loop body, match arm, catch body, and `finally` body. The same lexical scope MUST NOT redeclare one ordinary binding name. Nested scopes MAY shadow an outer name, and a new declaration's initializer MUST resolve the outer binding because the new binding enters scope only after its initializer completes.

IRIS-V1-CONTROL-C011: Unqualified name resolution MUST search local lexical bindings from innermost outward, then visible constants, Types, Module declarations, package declarations, and explicit imports. A syntactic call `name(...)` with no callable lexical or declaration binding MUST become an implicit privileged send to current `self` or module `main`. A non-call unresolved bare `name` MUST raise or diagnose `NameError`; it MUST NOT implicitly read a property, Method, global, or runtime-added member.

IRIS-V1-CONTROL-C012: Top-level executable code exists only inside a Module body. Each executable Module owns one identity-bearing `main` receiver. A top-level `fun f(...)` inside that Module creates a Method on `main`, private by default. A top-level `f(...)` inside the same Module body is a privileged implicit send to `main`. Importers can call a top-level helper only when it is exported or otherwise made public through Module API rules.

IRIS-V1-CONTROL-C013: The following lookup table is normative:

| Source form       | Lookup target                                                                     | Missing behavior                                      | Creation behavior                                     |
| ----------------- | --------------------------------------------------------------------------------- | ----------------------------------------------------- | ----------------------------------------------------- |
| `name`          | Lexical binding, then visible declarations and imports                            | `NameError`                                         | Never creates                                         |
| `name(args...)` | Lexical/declaration callable, otherwise current`self` or `main` ordinary send | Ordinary dispatch failure or`method_missing`        | Never creates a local                                 |
| `@name`         | Current receiver raw slot                                                         | Missing read returns`nil` only under raw ivar rules | May create only when raw ivar expansion is authorized |
| `@@name`        | Declared hierarchy Class-variable cell                                            | Missing declaration error                             | Declaration only                                      |
| `$name`         | Declared package-qualified runtime global                                         | Missing declaration error                             | `global let` or `global mut` only                 |
| `obj.name`      | Ordinary property getter selector`name`                                         | `method_missing` only if genuinely absent           | Never creates storage                                 |

IRIS-V1-CONTROL-EX002: Informative example, shadowing and implicit self call:

```iris
module Demo {
  fun helper() -> String { "module" }

  fun run() -> String {
    let helper_value = helper()
    {
      let helper_value = "inner"
      helper_value
    }
    helper_value
  }
}
```

## Callable Runtime Kinds And Declarations

IRIS-V1-CONTROL-C014: Iris v1 has exactly three ordinary callable runtime kinds: Method, BoundMethod, and Closure. It MUST NOT expose a separate Function runtime kind. Every named `fun` declaration defines a Method on its lexical owner. Reading or binding an instance Method creates a BoundMethod under runtime rules. A Closure is anonymous lexical code and capture.

IRIS-V1-CONTROL-C015: Named Method syntax is `fun selector(parameter_list) -> ReturnType { body }`, with optional visibility, `override`, `impl`, `async`, `class`, generic parameters, `where`, and property modifiers exactly as defined by grammar. Method ownership is determined by placement. Instance and Module Methods attach to the enclosing Class or Module. `class fun` installs a singleton Method on the Class object. Module-body `fun` installs a Method on that Module's `main` receiver.

IRIS-V1-CONTROL-C016: Closure syntax is `{ |parameters| -> ReturnType body }`. For a single-line body, the header MUST end with `;`, as in `{ |x: String| -> Nil; print(x) }`. For a multiline body, the body starts after the header terminator. Empty parameters use `{ || -> R body }`. The explicit return-type form is `|parameters| -> ReturnType`; the return annotation MAY be omitted only when an expected callable context uniquely supplies one closed function type.

IRIS-V1-CONTROL-C017: Method return annotation omission defaults under the global type-default rule and MUST be treated as `Dynamic<Object>` where no explicit annotation exists. Closure return annotation omission MUST NOT default the Closure's public type when no unique expected callable type exists; it MUST be diagnosed as `CALLABLE_MISSING_CLOSURE_RETURN_TYPE`.

IRIS-V1-CONTROL-C018: Superseded by IRIS-V1-TYPES-C094 and IRIS-V1-TYPES-C096 in the v1.11 errata; the callable Type now names its kind as `Closure<S>` or `BoundMethod<S>`, and signature compatibility is checked at the call site rather than by variance. The superseded text read: BoundMethod and Closure values share ordinary callable function types after binding, written `(P1, P2, ...) -> R`. Assignability MUST use function compatibility: parameter positions are contravariant, return positions are covariant, and arity, parameter category, keyword names, block channel, and runtime Contracts MUST be compatible. Unbound Method values remain reflective Method objects and require explicit binding or receiver invocation.

IRIS-V1-CONTROL-C019: Normal Method and Closure fallthrough returns the final expression value. A body with no value-producing statement returns `nil`. `return expr` exits the current Method or current Closure invocation with `expr`; bare `return` exits it with `nil`. Every normal return path MUST satisfy the callable's explicit return Contract, and a callable declared `-> Never` MUST NOT complete normally.

IRIS-V1-CONTROL-C020: `return` inside a Closure targets only that Closure invocation. `return` inside a Method targets only that Method frame. `break` and `continue` inside a Closure MUST NOT target a loop outside the Closure call boundary. Such target crossing MUST be a compile-time error when statically visible and otherwise a control-target error before executing an invalid transfer.

IRIS-V1-CONTROL-C021: The following callable-kind table is normative:

| Kind        | Created by                                                                       | Identity                           | Receiver or capture                                  | Invocation result rule                                                         |
| ----------- | -------------------------------------------------------------------------------- | ---------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------ |
| Method      | Named`fun`, `property fun`, generated accessor, or compatible meta operation | Identity-bearing definition object | Lexical owner, not receiver-bound                    | Requires receiver or explicit binding unless invoked through ordinary dispatch |
| BoundMethod | Reading or binding a Method on a receiver                                        | Identity-bearing callable object   | Captures receiver relation and exact Method identity | Revalidates current owner membership and returns Method body result            |
| Closure     | Evaluating a Closure literal or trailing block                                   | Identity-bearing callable object   | Captures lexical binding cells and current receiver  | Runs Closure body and returns local result only                                |

IRIS-V1-CONTROL-EX003: Informative example, Method, BoundMethod, and Closure forms:

```iris
class Counter {
  fun initialize() -> Nil {
    @value = 0
  }

  fun add(delta: Integer) -> Integer {
    @value += delta
  }
}

let counter = Counter.new()
let bound: BoundMethod<(Integer) -> Integer> = counter.add
let closure: Closure<(Integer) -> Integer> = { |delta: Integer| -> Integer; counter.add(delta) }
```

## Parameters, Defaults, And Key Arguments

IRIS-V1-CONTROL-C022: Parameter declaration order MUST be required positional, optional positional, at most one positional rest, required keyword-only, optional keyword-only, at most one keyword rest, then one trailing-block binding. A declaration that places a later category before an earlier category, repeats a rest category, or declares more than one block binding MUST be diagnosed as `PARSE_BAD_PARAMETER_ORDER` or a stricter callable diagnostic.

IRIS-V1-CONTROL-C023: Required positional parameters use `name: T`. Optional positional parameters use `name: T = default`. Positional rest uses `*args: T` and binds a fresh `Array<T>` containing extra positional arguments. Required keyword-only parameters use `key name: T`. Optional keyword-only parameters use `key name: T = default`. Keyword rest uses `**kwargs: V` and binds a fresh `Hash<Symbol,V>` containing unmatched keyword arguments. The trailing-block binding uses `&block: Block<(P...) -> R>` and MAY use `= nil` to mark omission as accepted.

IRIS-V1-CONTROL-C024: Parameter default expressions evaluate on each invocation, left-to-right, after earlier parameters have been bound and before later parameters exist. Defaults MAY reference current receiver, Module scope, globals, and earlier parameter bindings. Defaults MUST NOT reference later parameters. A default that raises aborts the call before body entry and propagates the exception.

IRIS-V1-CONTROL-C025: Parameter bindings are immutable binding cells. Rest and keyword-rest containers are fresh per call, but the container values retain their ordinary mutability. Omitted optional block binds `nil`. Arity, duplicated keyword, unknown keyword without `**kwargs`, missing required keyword, missing required positional, unexpected block, and parameter Contract failures MUST raise `ArgumentError` or `TypeError` after selector resolution and MUST NOT invoke `method_missing`.

IRIS-V1-CONTROL-C026: Calls spell keyword arguments as `name: value`. Positional arguments MUST bind positional parameters first. Keyword arguments MUST bind keyword parameters by name, independent of source order, after detecting duplicates. `*expr` expands positional arguments from an iterable or Array according to collection rules. `**expr` expands keyword arguments from a Hash keyed by Symbol or accepted keyword-name representation specified by the collection/type chapters. `&expr` supplies the block channel.

IRIS-V1-CONTROL-C027: The following parameter table is normative:

| Category               | Declaration example               | Call example                      | Binding result               | Failure example                               |
| ---------------------- | --------------------------------- | --------------------------------- | ---------------------------- | --------------------------------------------- |
| Required positional    | `value: String`                 | `write("x")`                    | Immutable`value`           | Missing argument raises`ArgumentError`      |
| Optional positional    | `limit: Integer = 10`           | `take()` or `take(5)`         | Immutable`limit`           | Default failure aborts call                   |
| Positional rest        | `*items: String`                | `join("a", "b")`                | Fresh`Array<String>`       | Element Contract failure raises`TypeError`  |
| Required keyword       | `key path: String`              | `open(path: "a.ir")`            | Immutable`path`            | Missing`path:` raises `ArgumentError`     |
| Optional keyword       | `key mode: Symbol = :read`      | `open(path: "a", mode: :write)` | Immutable`mode`            | Duplicate`mode:` raises `ArgumentError`   |
| Keyword rest           | `**options: Object`             | `build(debug: true)`            | Fresh`Hash<Symbol,Object>` | Non-key expansion failure raises`TypeError` |
| Block binding          | `&block: Block<(String) -> Nil>`       | `each() { block body }`         | Callable block value         | Unexpected block raises`ArgumentError`      |
| Optional block binding | `&block: Block<(String) -> Nil> = nil` | `each()`                        | `nil` when omitted         | Non-callable block value raises`TypeError`  |

IRIS-V1-CONTROL-EX004: Informative example, all parameter categories:

```iris
fun render(
  title: String,
  count: Integer = 1,
  *items: String,
  key path: String,
  key mode: Symbol = :read,
  **options: Object,
  &block: Block<(String) -> Nil> = nil
) -> Nil {
  if block != nil { block.call(title) }
}

render("report", "a", "b", path: "out.txt", verbose: true) { |line: String| -> Nil; print(line) }
```

## Closure Capture And Trailing Blocks

IRIS-V1-CONTROL-C028: A Closure captures lexical binding cells by reference, not by value snapshot. Captured immutable bindings are read-only. Captured mutable bindings are shared, so writes through the outer scope and writes through the Closure observe the same cell. Later nested shadowing MUST NOT retarget an existing Closure capture.

IRIS-V1-CONTROL-C029: A Closure created in an instance, Module, Class-object, or main Method captures the current receiver relation and receiver-name storage access. Source, reflection, Dynamic, native, and Host APIs MUST NOT rebind that captured receiver. Raw `@name` inside the Closure refers to the captured receiver when the Closure was created in receiver-owning code.

IRIS-V1-CONTROL-C030: A trailing Closure is passed only through the dedicated `&block` call channel. It is not a final positional argument. A call MUST supply at most one block, either through `&expr` in the argument list or through one trailing Closure. A trailing Closure following a completed postfix expression binds to the final declared block parameter of that call target. If no compatible block parameter exists, invocation MUST raise `ArgumentError`.

IRIS-V1-CONTROL-C031: Closure invocation MUST bind parameters by the same category rules as other bound callables. Closure result is the value from its own `return` or final expression. An exception raised inside a Closure propagates through the call site with ordinary ExceptionContext rules. If a Closure exits through invalid loop transfer, the runtime MUST report a control-target error and MUST NOT continue an outer loop by accident.

IRIS-V1-CONTROL-EX005: Informative example, capture by reference and local Closure return:

```iris
mut total: Integer = 0
let add: Closure<(Integer) -> Integer> = { |value: Integer| -> Integer
  total += value
  return total
}

add(2)  // returns 2
add(3)  // returns 5
```

## Calls, Properties, And Assignments

IRIS-V1-CONTROL-C032: Ordinary zero-argument and nonzero-argument calls MUST use parentheses. Property getter syntax is the only ordinary call-like syntax that omits parentheses. Named infix calls are ordinary one-argument Method sends at their grammar precedence. Contract-view calls use the qualified `..` namespace defined by the runtime chapter.

IRIS-V1-CONTROL-C033: Call evaluation order is receiver expression, callee or selector resolution inputs, positional arguments left-to-right, keyword argument values in source order, splat operands at their source positions, block operand or trailing Closure creation, then invocation. If any earlier evaluation raises, later argument evaluations and invocation MUST NOT occur. Selector resolution and arity/type validation occur after the receiver and call operands required for that call shape have been evaluated.

IRIS-V1-CONTROL-C034: Property read `obj.name` MUST send getter selector `name`. Property assignment `obj.name = value` MUST send setter selector `name=` with one argument. Setter selectors may include suffix punctuation before `=`, such as `ready?=` and `value!=`, only in declaration and property-assignment contexts that the grammar permits. Expression `a != b` remains inequality.

IRIS-V1-CONTROL-C035: Assignment is right-associative. Binding, class-variable, global, and raw-ivar assignment MUST yield the actual stored value. Property and index assignment MUST yield the setter Method result. In `a.x = b.y = v`, the inner setter executes first and the outer setter receives the inner setter's actual result.

IRIS-V1-CONTROL-C036: Compound assignment `target OP= rhs` MUST evaluate the target location and `rhs` exactly once, read the target exactly once, send ordinary operator `OP` to the read value with `rhs`, write the operator result exactly once through the target's normal write path, and yield that write operation's result. Supported symbolic compound assignments are `+=`, `-=`, `*=`, `/=`, `**=`, `&=`, `|=`, `^=`, `<<=`, and `>>=`.

IRIS-V1-CONTROL-C037: Logical assignment `target &&= rhs` and `target ||= rhs` are control-flow assignment forms. The target location MUST be evaluated and read exactly once. `&&=` MUST evaluate and write `rhs` only when the current target value is truthy. `||=` MUST evaluate and write `rhs` only when the current target value is falsy. A no-write path yields the current value. A write path yields the normal write-back result.

IRIS-V1-CONTROL-C038: The following assignment table is normative:

| Form               | Read count                               | Write count     | Dispatch used                    | Result value                       | Error rule                                                     |
| ------------------ | ---------------------------------------- | --------------- | -------------------------------- | ---------------------------------- | -------------------------------------------------------------- |
| `x = rhs`        | None after binding resolution            | One             | Binding write                    | Stored value                       | Immutable or missing binding fails                             |
| `@x = rhs`       | None                                     | One             | Raw storage write                | Stored value                       | Identity-less or denied expansion raises`InstanceStateError` |
| `@@x = rhs`      | None after declaration lookup            | One             | Class-variable cell write        | Stored value                       | Missing declaration fails                                      |
| `$x = rhs`       | None after declaration lookup            | One             | Global cell write                | Stored value                       | Missing declaration fails                                      |
| `obj.name = rhs` | Getter not required by assignment itself | One setter call | `name=` Method                 | Setter result                      | Missing setter follows ordinary dispatch failure               |
| `obj[key] = rhs` | Index receiver and key once              | One setter call | `[]=` Method                   | Setter result                      | Setter failure propagates                                      |
| `target += rhs`  | One                                      | One             | `+` then normal write          | Write-back result                  | Operator or write failure prevents later steps                 |
| `target &&= rhs` | One truth-tested value                   | Zero or one     | `to_bool`, then optional write | Current value or write-back result | `to_bool` failure prevents RHS and write                     |

IRIS-V1-CONTROL-EX006: Informative example, assignment results:

```iris
mut x: Integer = 1
x += 2                    // yields 3

object.status = :ready     // yields status= setter result
target &&= compute()       // compute runs only when target is truthy
```

## Truthiness And Conditional Expressions

IRIS-V1-CONTROL-C039: Conditions use the dynamic `to_bool() -> Bool` protocol from [03-runtime-object-model.md](03-runtime-object-model.md). `if`, `while`, match guards where grammar admits them, `!`, `&&`, `||`, `&&=`, and `||=` MUST evaluate their operand once for each test, call `to_bool` once, require an actual `Bool`, and branch on that Bool result. A `to_bool` exception MUST propagate unchanged.

IRIS-V1-CONTROL-C040: `!x` returns the Bool negation of `x.to_bool()`. `a && b` tests `a`; if false, it returns the original `a` without evaluating `b`; if true, it evaluates and returns `b`. `a || b` tests `a`; if true, it returns the original `a` without evaluating `b`; if false, it evaluates and returns `b`. The Bool produced by `to_bool` is not the value of `&&` or `||`.

IRIS-V1-CONTROL-C041: `if condition { then } else if other { middle } else { last }` is value-producing. Each branch has its own lexical scope. The result is the final expression of the selected branch, or `nil` for a selected body with no value. A missing `else` contributes an implicit `nil` branch. Result type is the normalized union of reachable branch result types.

IRIS-V1-CONTROL-C042: Conditional testing MUST NOT retype the tested operand by itself. Arbitrary `to_bool` is not a type predicate. Explicit predicates such as `is`, nil comparisons, and later type rules may narrow flow types, but the truthiness protocol alone leaves the source binding's type unchanged.

IRIS-V1-CONTROL-EX007: Informative example, conditional value and operand-returning logical operators:

```iris
let chosen = if config.ready? { "ready" } else { nil }
let cached = value || compute_default()
let both = label && label.length()
```

## Loops, Labels, And Iterator Lowering

IRIS-V1-CONTROL-C043: `while condition { body }` MUST test `condition` with `to_bool` before each iteration. Natural completion, including zero iterations, yields `nil`. `break expr` exits the target loop with `expr` as the loop result. Bare `break` exits with `nil`. `continue` starts the next iteration of the target loop and has no value.

IRIS-V1-CONTROL-C044: `for pattern in iterable { body }` MUST evaluate `iterable` once, obtain an `Iterator<T>` through the canonical `Iterable<T>` protocol, repeatedly call `next() -> Iteration<T>`, exit normally on `Iteration.done`, and bind each yielded value to `pattern` in a fresh per-iteration lexical scope. Natural completion yields `nil`. `break` supplies the loop result as for `while`.

IRIS-V1-CONTROL-C045: `for` destructuring MUST use the binding, Tuple, Array, rest, and `_` pattern subset specified by match and collection rules. A destructuring mismatch MUST raise `PatternMatchError`. The Iterator MUST be closed before that error propagates. Each iteration creates fresh binding cells, so escaping Closures capture the value for that iteration rather than a shared final loop variable.

IRIS-V1-CONTROL-C046: Iterators used by language traversal MUST close on every exit path: natural exhaustion, `break`, `continue` targeting an outer loop, `return`, body exception, Iterator exception, pattern error, and outer unwinding. Natural exhaustion releases through `Iteration.done`. Early exit MUST invoke idempotent `close()` before the pending transfer commits.

IRIS-V1-CONTROL-C047: If Iterator `close()` fails during traversal cleanup while a primary ExceptionContext exists, the close failure's ExceptionContext MUST be appended to the primary context's protected suppressed list in occurrence order. If no primary exception exists, the close failure becomes the primary propagated exception and prevents the pending normal, `break`, `continue`, or `return` transfer from completing.

IRIS-V1-CONTROL-C048: Loop labels explicitly target loops when the parser accepts forms such as `outer: while condition { ... }` or `outer: for pattern in iterable { ... }`. Unlabeled `break` and `continue` target the nearest enclosing loop. `break outer: expr` and `continue outer` target the named lexical loop. Unrestricted unlabeled `break expr` remains valid and targets the nearest enclosing loop. A label MUST NOT duplicate another active label in overlapping scope, label a non-loop construct, or cross a Closure boundary. Labeled break values contribute to the target loop's result type.

IRIS-V1-CONTROL-N001: Informative note: The grammar chapter currently includes `loop_label`, labeled `break`, `continue`, and `return` productions. This chapter owns label target validity, duplicate-label errors, Closure-boundary restrictions, cleanup, and result typing.

IRIS-V1-CONTROL-C049: The following loop control table is normative:

| Transfer                    | Valid target               | Result at target | Cleanup before commit                                        | Error rule                                 |
| --------------------------- | -------------------------- | ---------------- | ------------------------------------------------------------ | ------------------------------------------ |
| `break`                   | Nearest loop               | `nil`          | Close active traversal iterators crossed by the transfer     | No loop target raises control-target error |
| `break expr`              | Nearest loop               | `expr`         | Close active traversal iterators crossed by the transfer     | No loop target raises control-target error |
| `break label: expr`       | Named loop                 | `expr`         | Close active traversal iterators crossed by the transfer     | Target across Closure boundary is invalid  |
| `continue`                | Nearest loop or named loop | No value         | Close iterators for inner traversals crossed by the transfer | Cannot target a completed or absent loop   |
| Natural`while` completion | The loop itself            | `nil`          | None beyond body scopes                                      | Condition failure propagates               |
| Natural`for` completion   | The loop itself            | `nil`          | Iterator already done and released                           | Iterator fault propagates                  |
| Pattern mismatch in`for`  | No normal target           | No loop result   | Close Iterator before propagation                            | Raises`PatternMatchError`                |

IRIS-V1-CONTROL-EX008: Informative example, `for` lowering and Closure capture:

```iris
mut callbacks: Array<() -> Integer> = []
for value in 1 ..= 3 {
  callbacks.append({ || -> Integer; value })
}

callbacks[0]()  // returns 1
callbacks[1]()  // returns 2
```

## Match Expressions And Patterns

IRIS-V1-CONTROL-C050: `match value { arms }` MUST evaluate the scrutinee once, then test arms in source order. The first matching arm executes and produces the match result. No fallthrough exists. If no arm matches, source MUST be rejected unless the arm set is provably exhaustive or includes `else` where grammar admits it. Dynamic or open-ended domains require an explicit fallback arm.

IRIS-V1-CONTROL-C051: The v1 pattern vocabulary is literal patterns, `nil`, Bool literals, nominal type tests with binding, union alternatives, Tuple destructuring, fixed or rest Array destructuring, binding patterns, and `_`. V1 match MUST NOT use arbitrary object deconstruction, Regex matching, user-defined pattern protocol, or fallthrough. Pattern bindings are immutable and scoped to the selected arm.

IRIS-V1-CONTROL-C052: A guard where grammar admits it MUST run after pattern structural success and after provisional pattern bindings exist. The guard condition MUST use `to_bool`. If the guard returns false, the provisional bindings are discarded and matching continues with the next arm. If the guard raises, matching stops and the exception propagates.

IRIS-V1-CONTROL-C053: Union alternatives MUST bind identical names with compatible merged types. `_` discards and creates no binding. Destructuring mismatch in a binding-only destructuring context MUST raise `PatternMatchError`; mismatch during ordinary match arm testing means that arm does not match unless the pattern form has already committed through a guard or binding context specified by later type rules.

IRIS-V1-CONTROL-N002: Informative note: The grammar chapter currently includes match guards, fallback arms, block or expression bodies, and richer match patterns. This chapter owns match selection, guard truthiness, binding lifetime, exhaustiveness, and pattern failure behavior.

IRIS-V1-CONTROL-C054: The following match table is normative:

| Pattern form                         | Match rule                                        | Bindings                                     | Failure behavior                                     |
| ------------------------------------ | ------------------------------------------------- | -------------------------------------------- | ---------------------------------------------------- |
| Literal,`nil`, `true`, `false` | Compare by the literal's equality rule            | None                                         | Arm does not match                                   |
| `is T` with binding                | Runtime checked type or Contract match            | Immutable narrowed binding                   | Arm does not match on failed check                   |

## Raise, Catch, Finally, And ExceptionContext

IRIS-V1-CONTROL-C055: `try { ... }` MUST be followed by at least one `catch` clause or a `finally` clause. Zero or more catches precede the optional final `finally`. Execution order is try body, selected first-match catch if any, finally if present, then outward commitment of the resulting normal value, `return`, loop transfer, or exception.

IRIS-V1-CONTROL-C056: `raise value` accepts any Iris object or value and creates a fresh propagation event with a distinct identity-bearing, runtime-owned `ExceptionContext`. The caught object is the original value unchanged. Stack, cause, suppressed cleanup failures, re-raise sites, and source location belong to the ExceptionContext, not to the raised object.

IRIS-V1-CONTROL-C057: `raise value from context` MUST accept an identity-bearing `ExceptionContext` as the explicit cause. `raise value from nil` MUST suppress cause chaining. If `raise value` occurs while handling an active propagation, the active ExceptionContext becomes the automatic cause unless an explicit `from` form replaces or suppresses it. Passing a plain raised object as `from` MUST fail because it does not identify a propagation event.

IRIS-V1-CONTROL-C058: Bare `raise` continues the currently handled propagation record during the synchronous dynamic extent of a catch and while helper calls made before that catch exits are still on the stack. It appends one re-raise site and does not create a fresh context. Outside that dynamic extent, including a stored Closure invoked later, bare `raise` MUST raise `NoActiveExceptionError`.

IRIS-V1-CONTROL-C059: Typed catch matching MAY name a nominal Class or explicit Contract. Class matching accepts that Class and subclasses. Contract matching accepts Classes with explicit nominal conformance and MUST NOT use structural auto-conformance. Catch clauses are tested in written order, and only the first matching catch executes. Statically unreachable later catches MUST be compile-time errors. Dynamic matching uses current Class hierarchy and Contract conformance when selection begins.

IRIS-V1-CONTROL-C060: Catch forms bind immutable lexical values. `catch error: Type {}` binds the raised object narrowed to `Type`. `catch error: Type, context {}` binds both the raised object and its ExceptionContext. `catch error {}` catches every raised object and binds it as `Object`. `catch error, context {}` catches every raised object and binds object plus context. `catch {}` catches all without binding. `catch _, context {}` and `catch _: Type, context {}` discard the object and bind only the context. A catch-all MUST be final.

IRIS-V1-CONTROL-C061: Normal catch completion handles the exception. Its final expression becomes the provisional `try` result. The original propagation does not continue unless the catch executes bare `raise`. Executing `raise value`, even when `value` is the caught object, creates a fresh ExceptionContext and links the active context as cause unless explicit `from` changes that relationship.

IRIS-V1-CONTROL-C062: `try/catch/finally` is value-producing. On normal try completion, the try body's final expression is the provisional result. When a catch handles normally, that catch body's final expression is the provisional result. A body with no value yields `nil`. A normally completing `finally` evaluates its body for effects, discards its ordinary final value, and MUST NOT replace the provisional result.

IRIS-V1-CONTROL-C063: `finally` always runs after try and any selected catch. `return`, `break`, or `continue` from `finally` overrides any pending normal result or exception. If it discards a pending ExceptionContext, that discarded context is recorded only in a protected runtime diagnostic channel, not as cause or suppressed metadata. Ordinary callers observe only the new control transfer.

IRIS-V1-CONTROL-C064: If `finally` raises a new value while a pending exception context exists, the new propagation becomes primary and the pending context becomes its cause unless explicit `from` replaces or suppresses it. The pending context MUST NOT be placed in discarded diagnostics or suppressed cleanup failures for this case. Bare `raise` in `finally` continues the pending propagation when one exists; if none exists, it raises `NoActiveExceptionError`.

IRIS-V1-CONTROL-C065: `ExceptionContext` exposes get-only public properties `value: Object`, `cause: ExceptionContext?`, `suppressed: ReadonlyArray<ExceptionContext>`, `original_stack: ReadonlyArray<StackFrame>`, `re_raise_sites: ReadonlyArray<RaiseSite>`, and `raise_location: SourceLocation`. Public getters may be dynamically replaced for ordinary property reads, but runtime unwinding, diagnostics, native bridges, and uncaught formatting MUST use the protected internal records.

IRIS-V1-CONTROL-C066: Suppressed cleanup failures are runtime-owned ordered `ExceptionContext` entries. User code MUST NOT insert, delete, replace, reorder, or fabricate suppressed entries. Raised objects themselves MUST NOT gain `suppressed`, `cause`, stack, or re-raise metadata from being raised. Runtime-owned cause and suppressed edges MUST remain acyclic; a cycle attempt MUST raise `ExceptionChainError` and leave the existing graph unchanged.

IRIS-V1-CONTROL-C067: `ExceptionContext` equality and hashing use identity by default. Distinct propagation events are unequal even when they carry the same raised object, stack, cause, and suppressed graph. A retained ExceptionContext remains readable and valid as a future explicit `from` cause, strongly retaining its reachable propagation graph and raised values. Retaining a context does not make bare `raise` valid after catch dynamic extent ends.
